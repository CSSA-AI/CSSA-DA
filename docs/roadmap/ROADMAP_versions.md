## 里程碑 ≠ 版本号

**本文写的 v1–v4 是产品里程碑,不是发布版本号。** 两者是**多对一**:

```
v1「能跑」这个里程碑
   ├── v0.1.0  首次部署上线
   ├── v0.1.1  修了拒答的 bug
   ├── v0.1.2  加了 chat_interactions 的一列
   └── v0.2.0  换了 reranker
        ↓ 都还在 v1 里程碑内
```

| | 回答什么 | 在哪里 |
|---|---|---|
| **里程碑**(本文) | 什么时候能给谁用 | 本文 |
| **版本号** | 线上这一刻跑的是哪一份东西 | git tag |

发布流程、commit 规范、四种版本坐标见
[CONTRIBUTING.md](../../CONTRIBUTING.md#5-版本与发布)。

### 四种版本坐标

出事时要能在一分钟内回答「这个坏回答是哪份代码 + 哪个镜像 + 哪份语料 + 哪个模型
产生的」:

| 坐标 | 形式 | 现状 |
|---|---|---|
| 代码版本 | git tag | ❌ **仓库里零个 tag** |
| 制品版本 | 镜像 tag = git sha(immutable) | 📋 已计划 |
| API 契约版本 | `/v1/chat` | ❌ 没有 —— **v1 窗口期** |
| 数据版本 | 语料 `sha256` | ✅ 已设计 |

第四种你们**已经做对了**(`corpus_sha256`、`data/eval/v1/` 递增保留、报告必须带
hash)。那套纪律搬到代码上就是标准的版本管理。

线上每条 `chat_interactions` 记录都要带齐这四个坐标 —— 见
[ROADMAP_rag.md](ROADMAP_rag.md) Phase 4.5 的 `config` 指纹。

## 划分原则

**按能力承诺划,不按技术里程碑划。** 版本要能回答「什么时候能给谁用、承诺他能得到
什么」,而不是「哪个模块做完了」。

一句话概括四个版本:**能跑 → 能用 → 能信 → 能活**。

| 版本 | 一句话 | 卡在什么上 |
|---|---|---|
| **v1 能跑** | 链路验证 + 开始攒真实 query | 平台线 Phase 2(长杆)+ 前端架构决策 |
| **v2 能用** | 知识库第一次真的有内容 | **能拿到多少个源**(小助手是其中之一,不是全部) |
| **v3 能信** | 质量有据可依,而不是感觉 | 标注人力(4–5 人天)+ v2 的数据 |
| **v4 能活** | 系统能自己变好 | 前面都做完 + 有人持续运营 |

**v2 最不可控的部分是外部依赖。** 小助手导出探索的周期不由我们控制,所以虽然不阻塞
v1,**应该现在就派人去做**。但它已经不是 v2 的唯一入口 —— 见
[多源不是预案,是主线](#多源不是预案是主线2026-08-11-改口径)。

### 退出标准

1. 新生用中文提问,能得到基于 handbook 的正确课程回答,**答不了时明确说资料不足**
2. 匿名/无效客户端调不动 `/chat`;超频返回 429
3. 每次请求有结构化日志(request_id、query、检索到的 doc_id、各段耗时)
4. 每次请求在 `chat_interactions` 落一行,**带 config 指纹**
5. 新 task 通过 `/ready` 后,首请求与稳态延迟差 < 200ms
6. 滚动发布不丢在途请求;migration 作为部署关卡执行
7. 能从日志 + `chat_interactions` 复盘任意一次坏回答
8. **打出第一个 git tag `v0.1.0`**;镜像 tag = git sha(immutable,禁止用 `latest` 部署)

### 风险

**知识库只有 handbook,能答的问题很窄。** 所以必须是内测,**不能对外宣传成
「留学助手」** —— 期望管理比技术更重要。

### 长杆

Platform Phase 2。RAG 那几项加起来不到一周,**塞进 IaC 的等待窗口**。

### v2 的候选源

按**「能不能稳定合法地拿到」**排序,不按内容多少排 —— 这才是真正的筛子:

| 源 | 模态 | 拿得到吗 | 备注 |
|---|---|---|---|
| CSSA 自己整理的 FAQ / 新生手册 | `qa` | ✅ 最省事 | **先问一句有没有现成的**,成本最低 |
| 墨大官网(Stop 1、注册、选课、census date、special consideration) | `doc` | ✅ 公开网页 | 复用 handbook 修好的抓取脚本 |
| Trinity 语言班页面 | `doc` | ✅ | 高频问题,handbook 里没有 |
| Home Affairs 签证页(500 签、8105 工时、续签) | `doc` | ✅ 公开 | ⚠️ **变更频繁,过期即错**,且后果比社团推文重得多 |
| Services Australia / ATO(Medicare、TFN、报税) | `doc` | ✅ | 同上 |
| PTV concession 资格 | `doc` | ✅ | 留学生高频,规则常年有争议 |
| 小红书 | `qa` + `doc` **混合** | ⚠️ 见下 | 内容相关性最高,获取难度也最高 |
| 论坛帖子 | `qa` + `doc` **混合** | ⚠️ 取决于站点 | 同样是混合模态 |
| 群聊 | `qa` | ❌ 隐私路径未定 | 已在 Phase 4 |

#### 关于小红书

**内容上它可能是相关性最高的源** —— 留学生活的真实经验(租房、开卡、看病、
选课踩坑)正是 handbook 和官网答不了、而新生最想问的那一类。

但它有三层别的源没有的阻力,**排期时要按最坏情况估**:

1. **没有公开 API,且有较强的反爬** —— 这不是「写个脚本抓一下」的量级
2. **ToS 与合规** —— 批量抓取第三方平台的用户内容,和抓学校官网不是一回事,
   需要先想清楚立场
3. **可信度低且参差** —— 民间经验帖里错误信息很常见(签证、税务尤其)。它落在
   [四根正交的轴](ROADMAP_data.md#四根正交的轴)里 `authority` = 民间那一档,
   **这也是 `authority` 这根轴第一次真的需要被实现的时点**

**它还是 `modality` 混合源的第一个真实案例** —— 同一个源里,提问帖是 `qa`、
长经验帖是 `doc`。这正是[「不要从 `source` 推导 `modality`」](ROADMAP_rag.md#222-源会越来越多索引不能跟着源走)
那条约束防的情况。

> **建议的顺序**:先做 CSSA FAQ 和墨大官网(便宜、无阻力、能立刻验证多源链路
> 通不通),把小红书放在它们之后 —— 而不是反过来。否则很可能在最难的源上卡住,
> 而整条多源链路一次都没跑通过。

## 多源不是预案,是主线(2026-08-11 改口径)

> ⚠️ **本节原标题是「分支预案:小助手数据导不出来」**,把「其他数据源」写成导不出来
> 时才走的备胎。**这个口径已经作废** —— 已经确定**只靠小助手问答覆盖不了新生真正
> 会问的东西**,学校官网、政府签证页这类文档源是必需品,不是替代品。

```
原口径:  v1 ──► v2  小助手进库 ──► v3 选型 ──► v4 运营
         （导不出来才走）v2' 其他数据源

新口径:  v1 ──► v2  知识库覆盖到新生真会问的领域 ──► v3 选型 ──► v4 运营
                    └─ 小助手问答是其中一个来源，不是全部
```

**v2 的定义随之改变**:从「小助手数据进库」改成「**知识库第一次真的覆盖新生会问的
领域**」。小助手能不能导出仍然重要,但它现在只决定 v2 的**成色**,不再决定 v2 的
**有无**。

由此产生的三个后果:

1. **语料永久异构。** 问答类 + 文档类会长期并存 —— 这是
   [ROADMAP_data](ROADMAP_data.md#一个必须先说清楚的前提) 开篇那条前提改写的原因,
   也让 [ROADMAP_rag](ROADMAP_rag.md#phase-2可插拔的检索方案) Phase 2 从「三选一的
   候选」变成「结构性决定」。
2. **小助手导出调研的分量下降。** 它原先被记为「blocks 整条数据线」,现在只 blocks
   自己那一块。数据线可以在它有结论之前就开始推进别的源。
3. **时效性成为一等问题。** 政府签证页、学校注册截止日期这类内容**变更频繁,过期
   即错**,而且后果比社团推文重得多 —— 签证信息答错不是体验问题。每个源都必须带
   `post_date` 和一个复查周期。

### 若小助手确实导不出来

- gold set 退回**闭卷编写 150 条**,基于 handbook + 已有语料。仍然能做选型,
  **成色打折但不是死路**
- **真实 query 从哪来?** —— **v1 的 `chat_interactions` 就是备份来源**

> 原来的预案意味着两条纪律,在新口径下**更该守**:
> **① v1 不要依赖小助手数据 ② v1 的交互记录必须早做**

## 明确不在任何版本里

写下来免得反复讨论:

- **自托管 LLM** —— 生成走 OpenAI,除非账单失控
- **多实例水平扩容 / Redis 分布式限流** —— 社团规模用不上,单实例足够
- **GPU 推理** —— 除非 CPU 实测数据证明必要
- **LangSmith 生产 tracing** —— 开发环境用,生产走自己的结构化日志
- **Prompt 脱离 git 的云端管理** —— 生产行为要留在版本控制里
