## 一个必须先说清楚的前提

**本系统的主任务是「问题匹配」,不是 document RAG。**

知识库主体是小助手(**真人**)的历史问答,检索的两端都是问句 —— 新问题去匹配历史
问题,答案已经写好了。这与「问题 → 长文档段落」是完全不同的任务。

现有代码其实就是按这个建的(`knowledge_base(question_text, content)`、唯一索引
`(link, question_text)` 允许一个 link 多行、`build_embedding_text` 把问题放最前面、
`question_generator` 现成服务),只是微信管线跳过了生成问题那一步,`question_text`
填的是标题。

这个前提决定了整条路线的三件事:

- **模型候选**:要 paraphrase / STS 族,不是 passage retrieval 族
- **chunking 优先级下调**:问答对本来就短,截断问题只对文档部分成立
- **reranker 分量上升**:典型失败是匹配到「很像但关键条件不同」的问题
  (`master` 语言班 vs `bachelor` 语言班),正是 cross-encoder 补的短板

但知识库是**混合的**(问答对 + handbook + 微信文章),对称与非对称混在一个向量
空间里会导致**分数不可比** —— 这是 [Phase 3](#phase-3架构与模型选型) 要解决的问题。

## Phase 0:解除阻塞

**目标**:把「不解决就没法开工」的五件事清掉。前四件是等结论或做调研,第五件是
写代码。

### 0.1 handbook 重跑抓取 ⚠️ 数据缺陷

`data/unimelb_subjects_2026.json` 2946 门课里 **1589 门五个 section 全空**。按字母
序统计:

```
    0 - 1346   ABPL20056 .. FINA30018    空 = 43
 1346 - 2946   FINA30025 .. XNTS90002    空 = 1546   ← 整段全空
```

断点在 `FINA30025` 之后整段全空 —— **抓取任务中途死掉**(超时 / 限流 / 被中断),
不是学校没提供内容。

后果:**handbook 实际只覆盖字母序 A–F**。

| 有 | 缺 |
|---|---|
| ABPL / AGRI / BMSC / **COMP** / DNCE / EDUC / ECON(部分)/ FINA(部分) | **HLTH / LAWS / MEDS / MGMT / MKTG / MUSI / POLS / SCIE …** |

**MGMT 全缺、FINA 缺一半** —— 而商科是中国留学生最集中的方向。不修就冻结,会得到
一个「课程类问题只覆盖计算机和教育」的数据集,**而且从指标上完全看不出来**。

- **交付物**:补齐的 `unimelb_subjects_2026.json`,约 1.47 万个非空 section
- **验收**:全空的课程数 < 5%,且缺失不按字母序聚集
- **注意**:每行 `base_url` 都在,重跑不难。但**必须在 Phase 1 冻结之前完成** ——
  冻结后再补就是换语料,历史指标全部作废

### 0.2 小助手导出途径 —— 先确认账号类型

需要专人探索。**第一件要确认的不是「怎么导」,而是「这是哪种微信账号」**:

| 类型 | 可行性 |
|---|---|
| **企业微信** | ✅ 有官方**会话存档 API**,完整、合规、可自动化 |
| **公众号客服消息** | ⚠️ 有官方接口,但保留期有限,历史消息可能已丢 |
| **个人微信号** | ❌ 官方无 API,只能靠备份 + 第三方工具,**有合规风险,可能违反用户协议** |

如果是第三种,除技术难度外还有一层:这是求助场景的私密对话,批量导出再入库需要
走学生会内部授权流程,不是技术人员一个人能定的。

- **交付物**:账号类型结论 + 可行的导出方案 + 一份样本(50–100 场对话)
- **验收**:能稳定导出结构化的对话记录(含发送方、时间戳、消息内容)
- **卡住谁**:整个 Phase 1 的主体

### 0.3 微信文章的定位 —— 产品侧拍板

微信语料按标题前缀:推荐 643 / 活动预告 142 / 招聘 70 / 会员福利 66 / 活动反馈 50 /
提醒 50 / 学术 29。**这是学生会宣传号,不是留学知识库。**

如果真正的知识库是小助手问答,这 2312 篇可能是**噪声而非资产** —— 会跟真答案争抢
检索名额。三选一:

- **(a)** 次要补充,主力是小助手问答
- **(b)** 清出知识库,只留少数真正有信息量的
- **(c)** 与问答对平级,各答各的领域

- **验收**:一个明确结论,写进本文档
- **影响**:显著改变分源指标怎么解读,以及 Phase 2 的 query 配比

### 0.4 群聊的隐私路径 —— 只在打算做 Phase 4 时才需要

见 [Phase 4](#phase-4群聊接入v2)。不阻塞 Phase 1–3,但**越早启动越好**,因为它涉及
对外沟通,周期长。

### 0.5 修复 doc_id 链路 🔧 代码活(由 RAG 线执行)

`pg_retriever.py` 的 SQL 没有 `SELECT id`,构造 `Article` 时也没传 id;而
`app/schemas/article.py` 的 `id` 是 `default_factory=lambda: str(uuid.uuid4())`
—— 每次检索都是全新随机 UUID。`app/services/rag/eval/*.py` 里所有基于
`r.article.id` 的命中判断**永远不可能成立,现有指标恒为 0**。

**这同时是公开契约变更**:`app/main.py` 的 `ChatResponse.sources` 会把整个
`Article`(含那个随机 UUID)序列化返回。也就是说当前每次 `/chat` 响应都在吐一个
无意义的随机 id。

- **交付物**:SQL 带上 `id`,一路传到 `SearchResult`;ID 规则与数据集的 `doc_id`
  一致
- **验收**:`/chat` 返回的 id 稳定可复现,且能在 `corpus.jsonl` 里查到
- ⏰ **必须赶在平台线上线、前端接入之前** —— 见[与其他两条线的耦合点](#与其他两条线的耦合点)

> 数据集构造本身**不依赖**这一项(它直接读文件快照)。这是并行的另一件事:让线上
> `/chat` 和在线 eval harness 的 id 与数据集对得上。实施在
> [ROADMAP_rag.md](ROADMAP_rag.md) Phase 0.1,此处只标注它是数据集能落地的前提之一。

## Phase 1:语料建设

**目标**:产出一份冻结的、带稳定 `doc_id` 的 `corpus.jsonl`。

**前置**:0.1 ✅ / 0.2 ✅ / 0.3 ✅

### 1.1 聊天记录 → 问答对

**这是整条路线工程上最难的一步。** 原始数据不是干净的问答对,而是连续聊天流:

```
[10:23] 用户: 你好
[10:23] 用户: 我想问一下
[10:24] 用户: 语言班是不是要提前申请
[10:31] 助手: 是的 建议提前3个月
[10:31] 助手: 具体截止日期看你offer上写的
[10:32] 用户: 好的谢谢
[10:33] 用户: 那学费什么时候交
```

三个问题:消息碎片化、上下文依赖(「那学费什么时候交」)、一场对话多话题。

**做法**:规则粗切(同说话人连续消息合并成 turn,间隔超阈值切话题段)→ LLM 精提取
(输出结构化 QA 列表,**必须消解指代**)→ **人工抽检 50 场**。

**必须丢弃三类**:寒暄、纯确认、**需查个人档案才能答的**(「我的申请到哪一步了」)。
第三类最要注意 —— 它看着正常但知识库**永远**答不了,混进去会污染 unanswerable 子集
的含义。

- **交付物**:结构化 QA 对 + 提取质量抽检报告
- **验收**:抽检 50 场,QA 对准确率 ≥ 90%,指代消解无遗漏
- ⚠️ **产出率按三到五折算**:1000 场对话可能只出 300–500 个可用 QA 对。「对话场数」
  和「可用 QA 对数」是两个数,排期要用打折后的
- ⚠️ **指代消解会改写问题** → 标 `origin_detail: assistant_qa_rewritten`,与用户
  原话区分。否则你以为在测真实 query,实际测的是 LLM 改写过的 query

### 1.2 PII 脱敏 + 个人化内容筛选

小助手问答是**求助场景的私密对话**,入库前必须过两道工序(同一次处理):

1. **PII 脱敏** —— 真名、微信号、学号、手机号、具体地址
2. **个人化内容筛选** —— 1:1 答复常针对个人情况(「你这种情况因为是 packaged
   offer,所以…」),作为通用知识库条目会误导别人,必须剔掉或改写成通用表述

- **交付物**:脱敏后的 QA 对 + 脱敏规则文档 + 人工抽检报告
- **验收**:抽检 100 条,零 PII 残留
- 🔧 **工程硬要求**:这必须是 **pipeline 的一个 stage,在数据入库之前执行**,不能
  放到数据集构造层 —— 否则原始 PII 已经进了 Postgres 和 S3,再脱敏就是掩耳盗铃。
  平台线 Phase 3 需要落实,见[耦合点](#与其他两条线的耦合点)

### 1.3 三源 loader + 统一 schema

三个源(小助手问答 / handbook / 微信)合并进同一份 `corpus.jsonl`,靠 `source`
字段和 `doc_id` 前缀区分:

```
qa_00417                       小助手问答
hb_2026_comp90042_assessment   handbook,含年份
wx_vGqp2DXA34OE8iHxaSaUFg      微信文章
```

**两条 schema 约束**(来自实验矩阵,冻结时就必须满足,否则要重跑):

1. `question` 与 `generated_questions` **两个字段分开存在** —— 后者留给 doc2query
   填充,现在留空但字段必须有
2. **微信标题不填进 `question`** —— 它是标题不是问题,填进去就是重复现在那个退化
   用法,会让实验矩阵 A/B 两格的对比失真

- **交付物**:`corpus.jsonl`
- **验收**:`doc_id` 全局唯一;`source` / `date` / `is_ragable` 三源都有值

### 1.4 聚簇

**cluster 在本项目有两个用途,机制一样但目的相反:**

| | 微信文档簇 | 小助手问答簇 |
|---|---|---|
| 一簇是什么 | 内容近乎相同的文档(合集跨年份发了 19 版) | 问同一件事的不同对话 |
| 用来干什么 | **防止 precision 被低估**(同簇只算一次命中) | **产生 eval query**(抽一条当 query,其余当答案) |

方法:正文归一化后 5-gram MinHash,Jaccard ≥ 0.8。**阈值需人工抽检 20 组确认后
再固化。** handbook 不聚簇(每个 section 天然唯一)。

- **交付物**:`clusters.json` + 阈值抽检报告
- **验收**:抽检 20 组,聚错率 < 10%
- 📊 **关键产出**:「≥2 条的问答簇」的数量 —— **这个数是 eval query 数量的上限**

### 1.5 冻结

产出 `manifest.json`,含版本、git sha、分源行数、**语料 sha256**。

- **验收**:sha256 记录在案;后续任何指标报告必须带上它

> **有利的先验**:小助手是专门对接新生的号,问题高度集中(每年新生问的就是那批事
> —— 语言班、注册、选课、租房、开卡),同一问题被几十人问过的概率很高,对聚簇有利。
> 但必须实测,不能当假设用。
>
> **Fallback**:若簇少得离谱,Phase 2 退回以闭卷编写为主。不是死路,只是 v1 成色打折。

## Phase 2:Gold set 构建

**目标**:150 条 answerable + 30 条 unanswerable 的分级标注数据。

**前置**:Phase 1 ✅

### 2.1 标注 guideline + kappa 门槛

**分级含义按问题匹配定义**:2 = 同一个问题 / 1 = 相关问题(答案部分适用,或已过期
的正确版本)/ 0 = 不同问题。

写完 guideline 后**试标 50 对,两人独立标,算 Cohen's kappa**:

- κ ≥ 0.6 → 继续
- κ < 0.6 → **回去改 guideline,不要硬着头皮把 1.35 万对标完**

- **验收**:κ ≥ 0.6
- 💡 `data/qa_clean_data.json` 的作者记录显示团队有 6 人做过标注,人力足够双标

### 2.2 收集 query

| 来源 | 目标条数 | 说明 |
|---|---|---|
| 小助手问答(按簇抽一条划走) | ~100 | 取决于 1.4 的簇数 |
| 闭卷人工编写 | ~50 | 现在就能做 |
| LLM 合成 + 去措辞化 | 0–20 | 只补 handbook 侧盲区 |

**两条纪律:**

- **采集必须对语料盲。** 人写的 query 一样会泄漏,只要写的时候看着文档 —— 反面
  案例是 `data/qa_clean_data.json`(已弃案):221 条里一半根本不是问句,是文档标题
- **语料与 query 互斥。** 按簇**抽一条**划走(不是整簇划走),划走的那条完全不进
  语料;必须用编辑距离筛掉与留下的一字不差的

**再刻意设计约 20 条跨源竞争 query**(handbook 当期权威 = 2,提到同话题的旧微信
推文 = 1)—— 这是整份数据集里信息量最高的部分。

- **交付物**:`queries.jsonl`,含 `origin`(`human_log` / `authored_blind` / `llm`)
- **验收**:`human_log` + `authored_blind` 占比 ≥ 70%
- 🔧 **`held_out_for_eval: true` 必须落在源头**,由 ingest 阶段强制排除 —— 否则下次
  重跑管线会静默把 held-out 拉回语料,eval set 当场作废且**没有任何报错**

### 2.3 pooling

三路互补召回,**非对称深度**:

| 路 | 深度 | 理由 |
|---|---|---|
| baseline(当前线上) | **50** | 要算 Recall@50 |
| 最强 dense 候选 | **50** | 上线的很可能是它而不是 baseline |
| BM25 | 20 | 不会上线,只补 dense 盲区 |

union 约 90 篇/query,150 条约 **1.35 万次判断**(全量标注是 255 万次)。

### 2.4 标注

LLM 预标注 + 人工复核(复核三类:LLM 打 2 的、判断不确定的、随机 10%)。

**unanswerable 的判定不能由 pool 单独决定** —— 那是循环论证,会把「答案在语料里但
三路检索器全没捞到」这类**信息量最大**的样本当垃圾扔掉。候选 unanswerable 必须由人
做一次**不依赖检索器的定向查找**:

- 人也确认没有 → 真 unanswerable
- **人找到了但检索器没找到 → relevance = 2 + `pool_miss: true`**

- **交付物**:`qrels.jsonl`

### 2.5 挖难负例 + 切分 + 打包

难负例取 baseline top-50 的 **rank 10–50**(rank 1–10 藏着未标注的真正例,当负例
会毒化训练)。按**簇**切 15% 为 test-only,抽样**按源分层**。

- **交付物**:`data/eval/v1/` 完整七件套 + `load_dataset()` helper + baseline 示例
- **验收**:加载数据集**不需要** FastAPI / Postgres / OpenAI key

## Phase 3:架构与模型选型

**目标**:定下检索架构和模型。**全程离线,不碰数据库。**

**前置**:Phase 2 ✅

### 为什么先定架构

知识库是混合的,对称(问答对)与非对称(handbook / 微信)塞进同一个向量空间会
**分数不可比**:问句↔问句余弦天然高(0.85+),问句→段落天然低(0.55–0.65)。
`pg_retriever` 现在是一条 SQL 直接按距离排序 → **问答对会系统性压住文档,与谁更
相关无关**。换任何 bi-encoder 都有这个尺度差,所以架构比模型更上位。

### 步骤

```
3.1  baseline(当前线上配置)              ← 必须有,否则后面的数没有参照系
3.2  doc2query pilot(200 篇,按源分层)   ← 通过了才做全量生成
3.3  2×2 网格                             ← 离线,一格几分钟
3.4  看分源结果 → 决定要不要做 C
3.5  reranker 单独一轮(固定候选池,只比提升量 Δ)
```

**3.3 的网格**(不要排成一条线,否则同时改架构和模型,赢了不知道是哪个带来的):

| | paraphrase 模型 | 检索模型 |
|---|---|---|
| **都当文档** | A1 | **A2** |
| **doc2query** | **B1** | B2 |

**3.4 的 C 是条件分支,不是第三个选项**:B 若全面领先就直接用 B,C 白花力气(还要
付两张表 + 两个模型进镜像的代价);只有「B 在问答对上赢、A 在 handbook 上赢」才
需要 C。**这就是分源报指标的意义** —— 聚合成一个数就永远看不出该不该做 C。

**每一格必须产出**:分源指标 / Recall@50 / judged fraction / 配对显著性 / 成本。

- **验收**:有一个胜出配置,且其相对 baseline 的提升**经过 bootstrap 检验显著**
- 💡 **reranker 先做不会白做** —— 它是三种架构的公共部分。而且当前
  `cross-encoder/ms-marco-MiniLM-L12-v2` 不只是英文模型的问题,**任务类型也是错的**
  (ms-marco 训练的是 query → 段落)。这大概率是投入产出比最高的单点改动

## Phase 4:群聊接入(v2)

**目标**:把学科群聊天记录纳入语料与 query 来源,产出 `data/eval/v2/`。

**可与 Phase 3 并行**,但 4.1 周期长,越早启动越好。

### 4.1 隐私路径 —— 必须先解决,这不是技术问题 🚧

**学科群是所有数据源里风险最高的**:群内数百人,**只有极少数同意过**;记录里必然
有真名、微信号、学号、手机号、约见面地点。

动手前必须先选定一条路径:

- **(a)** 彻底去标识化后**仅用于内部评估**,不进模型训练
- **(b)** 通过学生会正式渠道向群成员告知,并提供退出机制
- **(c)** **只提取「问题」、丢弃回答与上下文** —— 大幅降低信息量,也大幅降低风险

- **验收**:书面结论 + (若走 b)告知与退出机制已落地
- ⛔ **这一项没有结论,4.2 之后全部不许启动**

### 4.2 导出/爬取

与 0.2 同样的账号类型问题,但群聊更麻烦:数据量大、多方参与、且**群主/管理员的
配合是必要条件**。

- **交付物**:结构化群聊记录(发送方、时间戳、消息内容、引用关系)
- ⚠️ **务必保留 WeChat 的「引用」关系** —— 它是 4.3 做话题重建的最强信号,丢了就
  只能靠时间和语义猜

### 4.3 话题窗口切分 —— 比 1:1 难得多

1:1 对话是一问一答的交替流;**群聊是多个对话交织在一起**。两百人的群里,任一时刻
可能有三四个话题并行,消息互相穿插:

```
[19:02] A: 请问COMP90042期末是take home吗
[19:02] B: 有人卖二手自行车吗
[19:03] C: @B 我有 私聊你
[19:03] D: @A 是的 去年是
[19:04] E: 明天的讲座几点开始
```

重建 (问题, 答案) 需要**话题线程重建**,可用的信号按可靠性排序:

1. **引用 / 回复关系**(最可靠,但很多人不用)
2. **@提及**(次可靠)
3. **时间邻近 + 语义相似度**(兜底,噪声大)

还要过滤大量噪声:红包、表情、闲聊、广告、接龙。

- **交付物**:话题窗口切分规则 + 抽检报告
- **验收**:抽检 50 个窗口,话题纯度 ≥ 80%
- ⚠️ **这个切分规则本身是一个待评估的变量**,不要当成既定事实写死

### 4.4 质量筛选

群聊的「答案」是**学生互相给的,可能是错的**。与小助手(真人客服)不同,不能直接
当权威内容入库。

三种处理方式:纳入但降权 / 人工审核后纳入 / 只用来发现「语料缺什么」而不入库。

### 4.5 并入 v2 数据集

同样走[纪律二:语料与 query 互斥](#22-收集-query)。方法完全复用 Phase 1–2,
只需加一个 loader —— **这就是「管线从第一天就按多源写」的回报**。

- **交付物**:`data/eval/v2/`,**保留 `v1/` 不覆盖**
- ⚠️ **接新源 = 换语料 = 所有历史指标作废**(Recall 的分母彻底变了)。保留旧版本
  才能回答「这次提升里换模型占多少、换语料占多少」
- ⚠️ **v1 上选出的模型,接入群聊后结论未必成立** —— 群聊文本是口语、碎片、多轮,
  与现有源风格差别很大,需在 v2 重新验证

## Phase 5:落地与收敛

**目标**:把胜出配置落进 schema 和生产。**这是与平台线的收敛点。**

**前置**:Phase 3 ✅ + 平台线 Phase 2 进行到「定 ECS 规格」

| 决定 | 影响 |
|---|---|
| **向量维度** | `VECTOR(384)` 写死。换 1024 维需 ALTER + 全库重嵌入重导。**必须在建 RDS 前做** —— 现在 DB 是一次性容器,迁移 = 删了重来;上生产后要变成停机窗口 + 回滚方案,成本差一个数量级 |
| **一张表还是两张** | 现有 schema 已支持一表多模型(`embedding_model` 列过滤),**卡住的是维度不是双索引**。两张表会牵动 `pg_retriever` / import 管线 / `/ready` / migration 关卡 |
| **模型文件大小** | 模型烤入镜像。bge-m3 + bge-reranker-v2-m3 约各 2.2GB,镜像会从 3.35GB 冲到 ~7GB,**平台线 Phase 1 的验收基线(冷启动 7.5s / idle 944MiB)全部要重测**,并可能推翻「烤入镜像」的方案本身 |
| **`top_k`** | 5 → 50 让每请求 CPU 差 10 倍,直接决定平台线第 13/14 项(worker/扩容策略、资源基线) |

- **验收**:线上 `/chat` 使用新配置,`/ready` 正常,smoke test 通过,且线上抽样
  结果与离线 eval 一致

## Phase 6:持续运营

**目标**:让数据集和模型持续变好,而不是做完就烂掉。

### 6.1 挖掘 `/chat` 真实日志

`app/services/rag/orchestrator.py` 已经在记录每次查询原文,上 ECS 后自动进
CloudWatch。**已确认可用于分析,并将在隐私声明中告知。**

两项待办(与平台线第 15 项一并做):

- query 改为独立结构化字段 `extra={"query": ...}`,便于 CloudWatch Insights 提取
- 设定 log group 保留期限(当前无限期)

### 6.2 交叉验证「闭卷编写」可不可信

真实流量积累后,**同一批模型在 `authored_blind` 和 `human_log` 上跑,看排名是否
一致**:

- 一致 → 闭卷编可信,以后可放心用它快速扩样本
- 不一致 → 这条路不能走,老实等真实日志

这把「闭卷编到底行不行」从争论变成**能被数据回答的问题**,成本只是多一个字段。

### 6.3 飞轮:unanswerable 是工作队列

问题匹配型知识库自带飞轮:

```
学生问了新问题 → 系统答不上来 → 人工回答 → 这条问答成为新的 KB 条目
```

所以 unanswerable 子集**不只是测试集,还是一份工作队列** —— 它精确指出知识库缺哪些
主题,补齐方式就是让小助手回答一遍。

### 6.4 定期重跑

每次语料有实质变化(新增数据源、大批量补录),开新版本目录重跑 Phase 1–3,**不要
原地覆盖**。
