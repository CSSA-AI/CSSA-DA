## 背景:先搞清楚这个系统在做什么

在设计数据集之前必须先回答一个问题:**检索的两端是不是同一种东西。**

**非对称(document RAG)**

```
"墨大语言班什么时候截止"            ← 问句,15 字
        ↓
"...符合条件的申请人须于 2026 年     ← 陈述段落,2000 字,
   3 月 15 日前完成语言课程注册..."      答案埋在中间
```

**对称(问题匹配)**

```
"墨大语言班什么时候截止"            ← 问句
        ↓
"请问墨尔本大学语言班的申请          ← 也是问句,
   截止日期是哪天"                      长度相仿,形态相同
```

**本项目的知识库主体是小助手(真人)的历史问答,所以主任务是问题匹配,不是
document RAG。** 这一点决定了下面几乎所有设计。

现有代码其实就是按问题匹配建的,只是那一步没接上:

| 证据 | 说明 |
|---|---|
| `knowledge_base(question_text, content)` | 一行 = 一个问题 + 一份内容 |
| 唯一索引 `(link, question_text)` | **允许同一个 link 有多行,每行一个不同的问题** |
| `build_embedding_text = question + "\n\n" + content` | 问题放最前面,是主要检索抓手 |
| `app/services/question_generator/` | 现成的服务,给文章生成 3 个中文问题 |
| `Article.questions: List[str]` | 复数,不是单数 |

拼起来就是「文章进来 → 生成问题 → 展开成多行 → 每行索引问题 + 内容」。而实际的
微信管线**跳过了生成这一步**:`question_text` 填的是标题,2312 篇文章对应 2312 行,
一篇一行。所以现在跑的是退化版 —— 每篇文章只有一个「问题」,而那个问题是标题。

### 但知识库是混合的

| 部分 | 检索类型 | 长度 | 需要 chunking |
|---|---|---|---|
| **小助手问答**(主体) | 对称匹配 | 短 | ❌ |
| handbook section | 非对称查找 | 中 | ⚠️ 部分 |
| 微信文章 | 非对称 | 长(正文 p50 1874 字) | ✅ |

**一个 embedding 模型同时干这三件事是个妥协,而且问题比「不够优」更具体:分数
不可比。** 问句和问句的余弦相似度天然高(同义问法常在 0.85+),问句和答案段落的
天然低(哪怕完美回答也就 0.55–0.65)。塞进同一个向量空间按距离排序,**问答对会
系统性压住文档,与谁更相关无关**。

怎么解决(单索引 doc2query / 双索引 + reranker 合并)是**架构选择**,不属于本文
范围 —— 见
[eval-experiments.md](eval-experiments.md)。本文只需
保证一件事:**数据集的构造对三种架构都成立**,不预设赢家。这就要求 `corpus.jsonl`
的 schema 为 doc2query 留出字段(见 [Step 0](#step-0冻结语料))。

### 对数据集的三处直接影响

1. **相关性的含义变了。** 不是「这段文字答得全不全」,而是「这两个问题问的是不是
   同一件事」。见 [Step 3](#step-3标注)。
2. **chunking 的优先级下调。** 早期判断「chunking 比换模型更重要」只对文档那部分
   成立;问答对本来就短,不涉及截断。
3. **reranker 的分量上升。** 问题匹配的典型失败是匹配到「很像但关键条件不同」的
   问题(`master` 语言班 vs `bachelor` 语言班),而 paraphrase 类 bi-encoder 恰恰
   被训练成对表述差异宽容。cross-encoder 正好补这个短板。

## 先看全局:三种用途,三种数据

DS team 提的三件事 —— 模型选择、微调、PEFT —— 需要的数据形态完全不同:

| 用途 | 数据形态 | 规模 | 可否合成 | 人工要求 |
|---|---|---|---|---|
| **模型选择(eval)** | query → 分级相关文档列表 | 100–200 query | ❌ 不可 | **必须人工验证** |
| **Embedding 微调** | (query, positive, hard negatives) | 数千 | ✅ 可 | 抽检即可 |
| **Reranker PEFT/LoRA** | (query, doc, label) 含难负例 | 数千–数万 | ✅ 可 | 抽检即可 |

三者共享同一份**冻结语料**,这是它们能互相比较的前提。

一条贯穿全文的纪律:**eval set 绝不进训练**。

## 基础知识

### 一、qrels:检索评估的标准数据形态

`qrels`(query relevance judgments)是信息检索领域几十年来的标准格式,一行表达
「某个 query 和某个文档之间的相关程度」:

```
query_id    doc_id                        relevance
q001        qa_00417                      2
q001        hb_2026_comp90042_assessment  1
q001        wx_UpwvMIl1crnGcjFcaiLqQw     0
```

配合 `corpus.jsonl`(所有文档)和 `queries.jsonl`(所有 query),就是 BEIR / MTEB
这些检索 benchmark 通用的三件套。好处是 DS team 可以直接把数据喂给
`sentence-transformers` 的 `InformationRetrievalEvaluator` 或 `mteb` 库,不需要写
任何适配代码。

**分级(graded relevance)而不是二值**,是因为 nDCG 需要区分「完全命中」和「沾边」。
三级的含义按主任务(问题匹配)定义,见 [Step 3](#step-3标注)。

### 二、pooling:为什么不用标 1.7 万篇

`Recall@k` 的分母是「语料里**所有**相关文档的数量」。要严格得到它,每个 query 都得
判断全部约 1.7 万篇(微信 2312 + handbook 补齐后约 1.47 万 + 小助手问答若干):

```
17,000 篇 × 150 个 query = 2,550,000 次判断
```

一次判断至少 30 秒,这条路根本走不通。所以整个信息检索领域从一开始就没走这条路。

**pooling** 的做法是:用**多个不同的检索系统**各跑一遍,每个取 top-N,结果取并集
(pool),只标注这个并集,池外一律默认 relevance = 0。TREC 从 1992 年(50 万篇
文档、50 个 query)起就这么做。它成立的前提是一条经验假设:

> 如果所有像样的检索系统都没把某篇文档排进 top-N,那它几乎肯定不相关。

**关键是「多个不同**范式**的系统」。** 拿三个 dense 模型来 pool,它们失败模式高度
相关 —— 都靠语义向量,都会漏掉精确术语(课程代码 `COMP90042`、签证类别
`subclass 500`)。池子看着有 60 篇,实际只覆盖一个方向。

| 路 | 模型 | 深度 | 作用 |
|---|---|---|---|
| baseline | 当前线上配置 | **50** | 参照系 |
| dense 候选 | 最可能上线的那个模型 | **50** | 候选新模型 |
| 稀疏 | BM25(`rank_bm25` + `jieba`) | 20 | **错误模式与 dense 完全不同** |

**深度为什么不对称。** pool 深度必须 ≥ 你要评估的 k。本项目要用 **Recall@50** 决定
线上 `top_k` 该设多少(候选池召回率是 reranker 的天花板),而 Recall@50 只有在那个
模型的前 50 名都被标注过时才有意义。若只 pool 到 20,rank 21–50 会塞满未标注文档,
这个数就是垃圾。

**为什么 baseline 和 dense 候选都要 50。** Recall@50 是拿来定线上 `top_k` 的,而
上线的很可能**不是 baseline 而是换掉之后的新模型** —— 那你需要的是新模型的
Recall@50。若只给 baseline 深度 50,你会得到一个「只有 baseline 能算 Recall@50」的
数据集,而 baseline 恰恰是准备换掉的那个。

**为什么 BM25 只要 20。** 它不会真的上线,作用只是补 dense 模型的盲区、降低 pool
bias,不需要能算深指标。而且检索结果有明显的**边际收益递减** —— rank 越靠后新增
相关文档的概率越低,第 20–50 名的相关文档密度已经很稀,多标 30 篇换不回多少东西。

三路 union 约 **90 篇/query**,150 个 query 约 **13,500 次判断** —— 比全量标注的
255 万次降了两个数量级。(相比「50/20/20」方案标注量涨三成,但换来新模型也能算
Recall@50,这笔钱值得花。)

每条候选记录 `pooled_by`(被哪几路捞出来),用于分析各路的独特贡献,也是下面这个
健康度指标的依据。

**必须报告 judged fraction** —— 每次评估一个模型,统计「它的 top-k 里多少比例被
标注过」:

- ≥ 90% → 数字可信
- 80–90% → 可信,但注意
- **< 80% → 踩到 pool 盲区,数字不可用,必须把它的 top-10 补进 pool 重标**

pool bias 无法消除,只能被监控。这份数据集适合回答「A 比 B 好吗」,**不适合回答
「A 的真实 recall 是多少」**。

### 三、难负例:训练数据的胜负手

训练 reranker 时,负例的质量比正例更重要。

当前 `app/services/rag/reranker/qa_dataset.py` 用的是**随机负例**
(`random.choice(all_answers)`)。随机抽一条当负例,它和 query 大概率毫无关系 ——
模型只要学会「这俩沾边吗」就能把 loss 降下去。但线上 reranker 面对的是 retriever
送来的 top-50,**这 50 条全都跟 query 沾边**,要判断的是「哪一条真的是同一个问题」。
随机负例训出来的模型在这个任务上基本没有增益。

**难负例必须从检索器里挖**:对每个训练 query 用 baseline 取 top-50,剔除正例及其
同簇成员,剩下的作为候选。

反直觉的细节:**不要取 rank 最靠前的**。rank 1–10 里很可能藏着未被标注的真正例
(false negative),拿它们当负例等于告诉模型「正确答案是错的」。通行做法是取
**rank 10–50**。

本项目的额外约束:微信部分 `tags` 全部是 `['微信公众号', 'CSSA']`、`source` 全部
是同一个账号,**元数据零区分度**。「同 tag 取负例」这条省事路子走不通,只能靠
检索挖。

**好消息**:在问题匹配设定下,训练数据几乎是免费的 —— 正例 = 同簇的其他问题,
难负例 = 别簇里语义相近但答案不同的问题。全是真实数据,不需要合成。

### 四、去重簇:从坑变成机制

#### 先说清楚 cluster 在本文里指什么

**「意思相近、可以当作同一个东西来处理的一组记录」。** 本项目里它有**两个用途,
机制一样但目的相反** —— 这是最容易混的地方:

| | 微信文档簇 | 小助手问答簇 |
|---|---|---|
| **一簇是什么** | 内容近乎相同的文档(「餐饮美食」合集跨年份发了 19 版) | 问同一件事的不同对话(20 个人问过语言班截止日期) |
| **怎么聚** | 正文归一化后 MinHash,Jaccard ≥ 0.8 | 问题语义相似 |
| **用来干什么** | **防止 precision 被低估** —— 同簇的多篇在 `top_k` 里只算一次命中 | **产生 eval query** —— 抽一条当 query,其余当 ground truth |
| **切分时** | 整簇一起分配到 train 或 test | 抽一条划走,其余留在语料 |

一句话:**文档簇是为了「不重复计分」,问答簇是为了「造题」。**

handbook 不聚簇 —— 每个 section 天然唯一,自成一簇。

#### 文档簇:近重复是个坑

**在 document RAG 的设定下,近重复是个坑。** 微信语料里 164 组正文完全相同(涉及
369 行,占 16%),另有大量近重复 —— 「餐饮美食」「生活服务」这类合集跨年份发了
17–19 个版本。query 问「墨尔本推荐的中餐厅」时若只标 1 篇为相关,检索器返回另外
18 篇中任何一篇都算 false positive,precision 被系统性低估到毫无意义。

所以文档部分仍需聚簇,且:

- 标注时同簇共享标签(标一次,广播到全簇)
- 计算指标时 `top_k` 里同簇的多篇只算一次命中(否则一个簇刷满 top-5,recall 虚高)

聚簇方法:正文归一化(去空白、去 `\xa0`、去 emoji)后取 5-gram 的 MinHash,
Jaccard ≥ 0.8 判为同簇。**阈值需人工抽检 20 组确认后再固化。**

#### 问答簇:近重复反而是核心机制

**对小助手问答,近重复簇是整个 eval 的核心机制。**

```
某个近重复问题簇(20 场对话都在问语言班截止日期)
    ├── 抽 1 场划走 → 它的用户提问 = eval query
    └── 其余 19 场留在知识库 → 它们就是这条 query 的 ground truth
```

这样得到的是:

- **真实 query**(学生真打出来的字)
- **真实的措辞差异**(另外 19 个人问法不一样)
- **保证有答案**,但不靠作弊 —— 答案在**别人问的那些**里
- **没有逐字泄漏**(需用编辑距离筛一遍,划走的那条不能与留下的一字不差)

而且这**正是生产环境的真实任务**:来了个新学生,用他自己的话问了个老问题,系统
能不能认出来。

> 早期版本的本文把「整簇划走」当作互斥切分的做法 —— 那是按 document RAG 想的。
> 在 QA 知识库设定下应该反过来:**按簇抽一条,而不是整簇划走**。

> 断点在 **FINA30025** 附近之后整段全空 —— 这是抓取任务在字母序中途死掉了(超时、
> 限流或被中断),**不是学校没提供内容**。
>
> 后果比数量更严重:**handbook 实际只覆盖字母序 A–F**。
>
> | 有 | 缺 |
> |---|---|
> | ABPL / AGRI / BMSC / **COMP** / DNCE / EDUC / ECON(部分)/ FINA(部分) | **HLTH / LAWS / MEDS / MGMT / MKTG / MUSI / POLS / SCIE …** |
>
> **MGMT 全缺、FINA 缺一半、ECON 缺一部分** —— 而商科恰恰是中国留学生最集中的方向。
> 拿这份数据建 eval set,课程类问题会系统性偏向计算机和教育。
>
> **行动:重跑抓取,并且必须排在冻结语料之前。** 每行 `base_url` 都在,重跑不难;
> 但语料一旦冻结再重抓,就等于换语料 —— 历史指标全部作废。

**微信文章的地位待定。** 按标题前缀统计:

```
643  【CSSA推荐】      商家推广、优选合集
471  (无前缀)
142  【CSSA活动预告】
 70  【CSSA招聘】
 66  【CSSA会员福利】
 50  【CSSA活动反馈】
 50  【CSSA提醒】
 29  【CSSA学术】
```

这是学生会的宣传号,不是留学知识库。如果真正的知识库是小助手问答,这 2312 篇在
`knowledge_base` 里可能不是资产而是**噪声** —— 它们会跟真答案争抢检索名额。三种
可能的定位需要产品侧拍板:

- **(a)** 次要补充,主力是小助手问答
- **(b)** 清出知识库,只留少数真正有信息量的
- **(c)** 与问答对平级,各答各的领域

**这个选择显著改变 eval 设计**(尤其是分源指标怎么解读),需要在 Step 0 之前定。

### 微信语料实测特征

| 特征 | 实测 | 影响 |
|---|---|---|
| 行数 / unique link | 2312 / 2312 | 一行即一篇;link 干净唯一,适合做 `doc_id` |
| 正文长度 | p50 1874 字,p90 5739 字,max 24517 字 | 文档部分需要 chunking |
| 正文完全重复 | 164 组 / 369 行(16%) | 必须聚簇 |
| 近重复 | 合集类跨年份 17–19 个版本 | 同上 |
| 正文 < 200 字 | 124 行,多为纯招聘/推广标题 | 标 `is_ragable: false`,不删除 |
| `source` / `tags` | 全部相同 | 元数据零区分度 |
| `post_date` | 2014-03 → 2026-04,跨 12 年 | 时效性必须进标注 guideline |

**时效性规则。** 语料跨 12 年,签证政策、学费、截止日期会失效。一篇 2018 年的
「学生签证 500 类别申请指南」对今天的 query 是**曾经正确但现在有害**:

- 事实已变更的旧版本 → **relevance = 1**(相关但不该排第一),不是 2 也不是 0
- 同一信息的最新版本 → 2
- 时效无关的内容(城市介绍、文化科普)→ 按内容本身判定,不因年份降级

标成 1 而不是 0,是因为它确实相关 —— 标成 0 会让模型学会「忽略这个话题」,而我们
想要的是「优先给最新的」。真正的时间衰减应该在检索后处理里按 `date` 加权,不是在
ground truth 里做。

### 隐私分层

各源的隐私风险不是一个量级:

| 数据 | 风险 | 关键问题 |
|---|---|---|
| 学校 handbook | 无 | 公开事实数据 |
| 微信公众号文章 | 无 | 已公开发布 |
| `/chat` query 日志 | 中 | ✅ **已定**:隐私声明中告知,可用于分析 |
| **小助手 1:1 问答** | **高** | 求助场景,内容可能相当私密;双方均可识别;会提及第三方 |
| 学科群聊天记录 | 最高 | 群内数百人,只有极少数同意过 |

**小助手问答虽然是知识库主体,但它是求助场景的私密对话。** 入库前必须过三道
工序(第一道见[下一节](#从聊天记录里提取问答对),后两道是同一次处理):

1. **PII 脱敏** —— 去掉真名、微信号、学号、手机号、具体地址
2. **个人化内容筛选** —— 1:1 答复常常针对个人情况(「你这种情况因为是 packaged
   offer,所以…」)。这类内容作为通用知识库条目会误导别人,必须剔掉或改写成通用
   表述

**工程硬要求:这两道工序必须是 pipeline 的一个 stage,在数据入库之前执行**,不能
放到数据集构造层 —— 否则原始 PII 已经进了 Postgres 和 S3,再脱敏就是掩耳盗铃。

学科群聊天不在 v1 范围。真要用,动手前必须先选定路径:(a) 彻底去标识化后仅用于
内部评估、不进模型训练;(b) 通过学生会正式渠道告知群成员并提供退出机制;
(c) 只提取「问题」、丢弃回答与上下文。

### 导出:先确认账号类型,再研究工具

小助手是一个专门对接新生的微信号,导出途径需要有人专门去探索。**第一件要确认的
不是「怎么导」,而是「这是哪种微信账号」** —— 三种情况可行性天差地别:

| 类型 | 导出可行性 |
|---|---|
| **企业微信** | ✅ 有官方**会话存档 API**,完整、合规、可自动化。最好的情况 |
| **公众号客服消息** | ⚠️ 有官方接口,但只保留有限时间,历史消息可能已经丢了 |
| **个人微信号** | ❌ 官方无 API。记录在手机 / PC 本地,只能靠备份 + 第三方工具解析,**有合规风险,也可能违反微信用户协议** |

如果是第三种,除技术难度外还有一层:这些是求助场景的私密对话,用第三方工具批量
导出再入库,需要走一遍学生会内部的授权流程,不是技术人员一个人能定的。

**先回答这一个问题再往下**,不要一上来就研究解析工具。

## 从聊天记录里提取问答对

**这是整个方案里工程上最难的一步。** 小助手的原始数据不是干净的问答对,而是一长串
连续的聊天记录:

```
[10:23] 用户: 你好
[10:23] 用户: 我想问一下
[10:24] 用户: 语言班是不是要提前申请
[10:31] 助手: 是的 建议提前3个月
[10:31] 助手: 具体截止日期看你offer上写的
[10:32] 用户: 好的谢谢
[10:33] 用户: 那学费什么时候交
```

三个问题:

- **消息碎片化** —— 一个问题拆成三条,答案拆成两条
- **上下文依赖** —— 「那学费什么时候交」的「那」指代前文,单独拎出来当 query 是残缺的
- **一场对话多个话题**,还夹杂寒暄、确认、乱序回复

### 做法:规则粗切 → LLM 精提取 → 人工抽检

**1. 规则粗切。** 同一说话人的连续消息合并成一个 turn;turn 间隔超过阈值(比如
30 分钟)切成不同话题段。这一步只是把噪声降下来,不指望它准。

**2. LLM 精提取。** 把整段对话丢给模型,输出结构化的 QA 列表,并且**必须消解指代**
——「那学费什么时候交」要改写成「墨大语言班的学费什么时候交」。

**3. 人工抽检 50 场**,核对抽出来的 QA 对。**这一步的质量直接决定整个数据集的
质量,不能省。**

### 必须丢弃的三类

- 纯寒暄(「你好」「在吗」)
- 纯确认(「好的谢谢」「收到」)
- **需要查个人档案才能答的**(「我的申请到哪一步了」「帮我看看我的邮箱」)

第三类最要注意 —— 它看起来是个正常问题,但知识库**永远**答不了。混进 eval set 会
污染 unanswerable 子集的含义:那个子集想测的是「知识库有覆盖缺口」,不是「这问题
本质上无法用知识库回答」。

### 两个必须提前知道的事

**指代消解会改写问题。** 改写之后它就不再是「用户原话」了。要单独标
`origin_detail: assistant_qa_rewritten`,与未经改写的区分开 —— 否则你以为在测
真实 query,实际测的是 LLM 改写过的 query。这一类严格说介于 `human_log` 和
`authored_blind` 之间。

**产出率比直觉低得多。** 大量对话是寒暄、重复追问、个人事务。保守估计
**1000 场对话只能出 300–500 个可用 QA 对**。所以「小助手有多少场对话」和「能出
多少 QA 对」是两个数,后者要按**三到五折**算 —— 排期和可行性判断都要用打折后的数。

## query 从哪来

这是整份数据集里最难、也最决定成败的一环。

### 五种泄漏

最省事的做法是让 LLM 从文档生成问题。它会产出**系统性高估、无法用于模型选型**的
数据集,而且泄漏不止一种:

| # | 泄漏 | 说明 |
|---|---|---|
| 1 | **措辞泄漏** | 问题从原文措辞长出来,词汇重叠虚高 |
| 2 | **存在性泄漏** | 每条合成 query **必定**有答案;真实用户会问答不了的问题 |
| 3 | **可答性偏差** | query 分布 = 语料分布,而非用户需求分布 |
| 4 | **难度偏差** | LLM 只生成「单篇文档答得了」的问题;真实问题常需跨文档、表述残缺 |
| 5 | **概念选择泄漏** | 就算换了措辞,问的仍是这篇文档强调的那个点 |

「把生成的问题改写成口语」(去措辞化)只挡住第 1 条。

**要分清两种后果:**

- **绝对指标被高估** —— 确定发生,幅度很大
- **模型之间的排序被扭曲** —— 这才是模型选型真正在乎的。措辞泄漏**系统性偏袒做
  字面匹配的模型**,也就是说它不只是把所有模型一起抬高,它会**改变谁赢**

第二条是不能接受的,所以合成 query 的占比必须压到很低。

### 纪律一:采集必须对语料盲

**人写的 query 一样会泄漏,只要写的时候看着文档。**

反面案例就在仓库里:`data/qa_clean_data.json`(221 条、6 人所写)中有一半根本不是
问句,而是**文档标题**(「墨尔本交通指南」「Myki卡使用指南」「巴士服务」)。那是
人对着文档列表写出来的,不是从需求出发写的。(该文件因指向外部语料**已弃案**,
但它作为反面教材仍然有效。)

| 采集方式 | 是否对语料盲 |
|---|---|
| 真实日志 / 历史对话 | ✅ 天然盲 |
| **闭卷人工编写** | ⚠️ 必须强制执行:写的人不许看语料、不许看检索结果 |
| LLM 从文档生成 | ❌ 默认违反 |

#### 闭卷编写协议

**人选比方法重要:**

- ❌ 别找 CSSA 核心干事 —— **知识的诅咒**:在这儿待了两年的人,想不起来「Myki 是
  什么」也是个问题
- ✅ 找大一新生、刚来半年的、非本专业的
- ✅ 或者问干事:「**上周有人在群里问你什么**」—— 二手的真实问题远好过凭空想

**给场景,不要给主题清单。** 给「签证 / 选课 / 租房」这种分类让人填空,产出的是
教科书式问题。改成给情境:

> 「回想你刚落地那一周,你当时最不知道该问谁的三件事是什么?」
> 「你室友上个月为了什么事发愁?」

**明确允许写得难看。** 写之前就说清:按你真的会打字的样子写,不用润色,不加标点
也行,有错别字更好。不这么讲,人本能会写得很正式。

**每人只写 10–15 条。** 一个人写到第 30 条必然开始硬编,宁可多找几个人。

**不要过滤掉「语料好像答不了」的问题。** 那些正是 unanswerable 子集,有用 ——
而且编的人本来也不知道语料里有什么,让他判断反而破坏了闭卷。

**残留偏差(必须承认)**:编的人不是用户。表现为太规整(真实用户打的是
「26fall 语言班 啥时候截止」)、只写得出典型问题(真实分布是长尾的)、没有对话
上下文。这是**分布偏移**,不是泄漏 —— 它大体上对所有模型一视同仁地压低分数,
主要影响绝对值,对排序的影响是二阶的。**闭卷编 ≫ 从文档生成。**

### 纪律二:语料与 query 互斥

**一条内容,要么进语料,要么产 query,不能两者兼有。**

小助手对话里,用户那一侧是最好的 query 来源,助手那一侧是最好的语料 —— 是同一场
对话。若不处理,query 会**逐字出现在文档里**,任何检索器都能命中,Recall 直接 1.0。
这比合成 query 更严重(合成的至少还换了措辞)。

做法见[去重簇:从坑变成机制](#四去重簇从坑变成机制):**按簇抽一条划走,而不是
整簇划走**。划走的那条完全不进语料,只提取用户提问当 query;同簇其余留在语料里
充当 ground truth。

**必须用编辑距离筛一遍**:划走的那条若与留下的某条一字不差,仍是逐字泄漏,要换
一条划走。

#### 一个容易踩的运维坑

这个切分**必须在源头打标记,不能只写在文档里**。

语料是管线定期重建的。如果 held-out 那批只是「这次没导进去」,下次重跑 ingest 时
会被静默地拉进语料 —— eval set 当场作废,而且没有任何报错,你只会看到指标莫名
其妙变好了。

所以要在原始记录上落一个 `held_out_for_eval: true`,**由 ingest 阶段强制排除**。
这是管线的一个约束,不是一次性的操作步骤。

### v1 配方

| 来源 | 目标条数 | 状态 |
|---|---|---|
| 小助手问答(按簇划走的那批) | ~100 | ⚠️ **取决于能否导出 + 簇够不够** |
| 闭卷人工编写 | ~50 | ✅ 现在就能做 |
| LLM 合成 + 去措辞化 | 0–20 | 只补 handbook 侧盲区 |

> **已删除的来源**:公众号后台留言(该功能不存在)、学校论坛(尚未建成,上线前
> 无法抓取)。早期版本的本文列过这两项,是错的。

**若小助手问答导不出来**,v1 只能是闭卷编 150 条 —— 那就**没有真实 query 可以用来
交叉验证闭卷这个方法可不可信**,v1 的结论要打折扣,得等 `/chat` 上线积累真实流量。

#### 三类 origin,分别报指标

```
human_log       真实日志 / 历史对话捞的
authored_blind  闭卷人工编的
llm             合成的
```

这样等 `/chat` 真实流量积累起来之后,可以做一件事:

> **同一批模型,在 `authored_blind` 和 `human_log` 上跑,看排名是否一致。**

- 排名一致 → 闭卷编这条路可信,以后可放心用它快速扩样本
- 排名不一致 → 这条路不能走,老实等真实日志

这就把「闭卷编到底行不行」从一个争论,变成一个**可以被数据回答的问题**,成本只是
多一个字段。

#### answerable / unanswerable 拆分

| 子集 | 规模 | 定义 | 用途 |
|---|---|---|---|
| **answerable** | ~150 | 有 relevance = 2 的文档 | 检索指标**只在这上面算** |
| **unanswerable** | ~30 | **人工定向查找确认**语料里确实没有答案 | 不参与检索指标;测生成器拒答行为 |

`rag-config.yaml` 的 system prompt 明确要求「如果资料中没有答案,请说明资料不足,
不要编造」—— 这条行为目前完全没有测试,而它正是 RAG 系统最容易出事的地方。

**关键:unanswerable 的判定不能由池子单独决定。** 否则是循环论证:

> 答案确实在语料里,但三路检索器全没捞出来 → 池子里没有相关文档 → 标注全 0 →
> 判为 unanswerable → 踢出指标。

**这恰恰是检索失败最严重、信息量最大的一条,却被当垃圾扔了。** 剩下的全是「至少
有一路能找到」的 query,指标当然好看。

所以候选 unanswerable 必须由人做一次**不依赖检索器的定向查找**(关键词全文搜索、
按 `subject_code` 直接查 handbook),然后分两种:

- 人也确认语料里真没有 → 真 unanswerable,进拒答测试集
- **人找到了,但三路检索器都没捞到 → relevance = 2,留在 answerable,打上
  `pool_miss: true`**

第二类是整份数据集里最珍贵的样本,同时也是 pool bias 的直接度量。

## 数据集设计

### Step 0:冻结语料

一切的底座。**三个源合并进同一份 `corpus.jsonl`**,统一 schema,靠 `source` 字段
和 `doc_id` 前缀区分:

```json
{
  "doc_id": "qa_00417",
  "source": "assistant_qa",
  "question": "墨大语言班什么时候截止",
  "generated_questions": [],
  "text": "语言班的申请截止日期是……",
  "url": null,
  "date": "2025-11-03",
  "cluster_id": "qc0031",
  "is_ragable": true,
  "n_chars": 186
}
{
  "doc_id": "hb_2026_comp90042_assessment",
  "source": "handbook",
  "question": null,
  "generated_questions": [],
  "text": "Assessment Description Timing Percentage ……",
  "url": "https://handbook.unimelb.edu.au/2026/subjects/comp90042",
  "date": "2026-01-01",
  "cluster_id": null,
  "is_ragable": true,
  "n_chars": 1832,
  "subject_code": "COMP90042",
  "section": "assessment"
}
```

设计决定:

- **`doc_id` 带 source namespace**:`qa_` 小助手问答 / `hb_` handbook /
  `wx_` 微信 /(将来)`fm_` 论坛、`ch_` 聊天。前缀不只是可读性 —— 它让「分源统计
  指标」变成一行 `groupby`。
- 微信 `doc_id` = `"wx_" + url 末段`(微信文章标识,稳定唯一可反查)。
  handbook `doc_id` 含**年份** —— 2026 和 2027 的同一门课是**两篇不同的文档**,
  不是同一篇的两个版本。**不用 `knowledge_base.id`**:它是 SERIAL,重新导入会重新
  分配,跨版本不稳定。
- **`question` 与 `generated_questions` 分开**。前者是真实存在的问题(小助手问答
  才有);后者留给 doc2query 架构填充,**现在留空但字段必须存在** —— 否则实验矩阵
  里的 B 类配置要改 schema 重跑。微信的标题**不填进 `question`**,它是标题不是
  问题,填进去就是在重复现在那个退化用法。
- **`date` 三个源都要有**。微信用 `post_date`;handbook 用 `year + "-01-01"`;
  小助手用对话时间。保证时效性规则对所有源都能算。
- **`is_ragable: false` 保留不删**。微信有 124 行 < 200 字的纯推广标题,handbook
  有约 1600 门课 section 为空。它们在线上 KB 里存在、会被检索到,删掉会让离线指标
  比线上乐观。保留并标记,才能统计「检索到无效内容」的比率。
- **`cluster_id` 对 handbook 为 null**(每个 section 天然唯一,自成一簇);微信和
  小助手问答都要聚簇,但用途不同(见[第四节](#四去重簇从坑变成机制))。
- **不在数据集里做 chunking**。chunking 是待评估的变量,数据集提供文档级原文,由
  实验代码自行切分。`qrels` 是文档级标注,切分后的映射规则:**任一 chunk 命中即视
  为该文档命中**(计算指标前先按 `doc_id` 去重)。

### Step 1:收集 query

见 [query 从哪来](#query-从哪来)。产出:

```json
{"query_id": "q001", "text": "26fall墨大 语言班啥时候截止",
 "origin": "human_log", "origin_detail": "assistant_qa",
 "split": "test", "answerable": true, "source_cluster": "qc0031"}
```

### Step 2:pooling 生成候选

按[基础知识第二节](#二pooling为什么不用标-17-万篇)的非对称深度:baseline 取
top-**50**、dense 候选也取 top-**50**、BM25 取 top-20,union 去重,约 90 篇/query。

**三路都在合并后的全量语料上检索**,不分源单独 pool —— 否则跨源竞争的 query 永远
不会把不同源的文档放进同一个池子,而那正是最有价值的部分。

每条候选记录 `pooled_by`,服务于:分析各路独特贡献、计算 judged fraction、日后
新模型踩到盲区时定位补标范围。

### Step 3:标注

**分级含义按主任务(问题匹配)定义:**

- **2 = 同一个问题**,答案直接适用
- **1 = 相关问题**,答案部分适用或需要调整(`master` 语言班 vs `bachelor` 语言班),
  或是**已过期的正确版本**
- **0 = 不同问题**

注意「1」这一档比 document RAG 设定下**窄很多** —— 问题匹配里中间地带没那么多,
这会让标注一致性更容易做高。

**跨源竞争的约定**:同一个问题,handbook 的当期权威内容 = 2,提到同一话题的旧微信
推文 = 1。gold set 里要**刻意设计约 20 条跨源竞争 query** —— 能不能把 handbook 排到
微信推文前面,正是 reranker 存在的意义,而这是整份数据集里信息量最高的部分。

**LLM 预标注 + 人工复核**,而不是纯人工。先用 GPT-4o 对 pool 里每个 (query, doc)
给出 0/1/2 + 一句理由,再人工复核三类:LLM 打 2 的(误报代价最高)、LLM 判断不
确定的、随机抽样的 10%。这套流程能省掉约 70% 的人工时间。

#### 标注一致性检验:Cohen's kappa

**两个人独立标同样的 100 对,算 Cohen's kappa。**

**为什么不能只看「一致率」。** pool 里绝大多数 pair 是不相关的,假设 90% 该标 0。
那么两个人**闭着眼睛全标 0**,一致率就是 90%,看着极高,实际零信息。

kappa 扣掉了「瞎蒙也能蒙对」的那部分:

```
κ = (Po − Pe) / (1 − Pe)

Po = 实际一致的比例
Pe = 按各自的标注习惯随机分配时,期望的一致比例
```

κ = 0 表示和瞎蒙一样,κ = 1 表示完全一致。

**一个具体例子。** 两人各标 100 对:

|  | B 标 0 | B 标 2 |
|---|---|---|
| **A 标 0** | 85 | 5 |
| **A 标 2** | 5 | 5 |

- 一致率 `Po = (85 + 5) / 100 = 0.90` ← 看着很好
- A 标 0 占 90%,B 标 0 占 90%
- `Pe = 0.9 × 0.9 + 0.1 × 0.1 = 0.82`
- `κ = (0.90 − 0.82) / (1 − 0.82) = 0.44`

**一致率 90%,kappa 只有 0.44 —— 不合格。** 那 90% 的一致里绝大部分是「两人都在标 0」
这件几乎必然发生的事贡献的;在真正需要判断的少数样本上,两人有一半时候不一致。

| κ | 含义 |
|---|---|
| < 0.4 | 差 —— 标注标准根本没定清楚 |
| 0.4 – 0.6 | 一般 —— 需要改 guideline |
| **0.6 – 0.8** | **好 —— 本项目的可接受门槛** |
| > 0.8 | 很好 |

`sklearn.metrics.cohen_kappa_score(a, b)` 一行就能算。

**不到 0.6 就回去改 guideline 再来,不要硬着头皮把 13,500 对标完** —— 标完才发现
两人对「部分相关」的理解不同,整份数据作废。`data/qa_clean_data.json` 的作者记录
显示团队里有 6 个人做过标注,人力足够做双标。

标注以**簇**为单位:同簇标一次,标签广播到全簇。

### Step 4:挖难负例、切分

**挖难负例**(仅对训练集 query):baseline 取 top-50,剔除正例及其同簇成员,取
rank 10–50 区间,每个正例配 8 个难负例。

**切分**:按**簇**切,随机抽 15% 的簇标记为 test-only。

- test-only 簇里的文档,其相关 query 只进 eval set,绝不进 train
- 训练 query 若其正例落在 test-only 簇,整条丢弃
- 抽样**按源分层**,保证 test-only 里各源比例与全量一致 —— 否则可能抽出一个几乎
  全是 handbook 的测试集,分源指标失去意义
- **语料本身不切分** —— eval 时检索全部约 1.7 万篇,这才和线上一致

### Step 5:打包交付

产出 `manifest.json`,记录版本、构造时的 git sha、分源行数,以及**语料 sha256**。
最后一项是关键:模型指标只有在同一份语料上才可比。DS team 报告结果时必须带上这个
hash。

DS team 应该 clone 仓库之后就能开始跑。配一个 `load_dataset()` 的 20 行 helper 和
一段能跑通的 baseline 示例(含 judged fraction 与分源指标的计算)即可。

选 BEIR/MTEB 三件套格式,是为了让 DS team 能直接用
`sentence_transformers.evaluation.InformationRetrievalEvaluator` 和 `mteb`,
零适配成本。

## 规模与工时

| 产物 | 规模 | 主要成本 |
|---|---|---|
| **handbook 重跑抓取** | 1589 门课待补 | 半天–1 天(取决于限流),**必须在冻结前做** |
| **聊天记录 → QA 对** | 对话场数 × 三到五折 | **1–2 天** —— 规则粗切 + LLM 提取 + 人工抽检 50 场 |
| 冻结语料 + 聚簇 | 小助手 QA ? + handbook ~14700 + 微信 2312 | **约 2 天** —— 三种结构完全不同的源,含脱敏与个人化筛选、聚簇阈值人工抽检 |
| Gold eval set | 150 answerable + 30 unanswerable | pooling 后约 13,500 对判断;LLM 预标 + 人工复核约 4,000 对 → **4–5 人天** |
| 训练池 | 2000–5000 query × (1 正 + 8 难负) | 纯脚本,**问题匹配设定下正负例都来自真实簇**,约 1 天 |

150 query 是**最小可信规模**。低于 100,配对比较的置信区间会宽到区分不出两个模型;
即使 150 条,几个点的差距也需要 bootstrap 置信区间才能判断显著性,不能只看均值。
分源报告时每个源至少要有 60 条,否则单源的置信区间同样不可用。

## 已知偏差与禁止事项

这一节必须原样写进 `DATASET_CARD.md`。

**已知偏差:**

1. **Pooling 偏差**。未进入 pool 的文档默认 relevance = 0。缓解手段是三路互补召回
   + baseline 深度 50,但偏差无法消除,只能靠 **judged fraction 监控**。新模型若
   judged fraction < 80%,或表现异常好/异常差,必须把它的 top-10 补进 pool 重标
   再下结论。**这份数据集适合回答「A 比 B 好吗」,不适合回答「A 的真实 recall
   是多少」。**
2. **只覆盖被问过多次的问题**。eval query 靠「按簇抽一条」产生,只被问过一次的
   问题无法用这个方法生成 query(划走就没有 ground truth,留着又不能当 query)。
   所以 eval set 偏向高频问题,**低频长尾的检索能力这套 eval 测不出来**。
3. **闭卷编写的分布偏移**。`origin: authored_blind` 的 query 太规整、偏典型、
   缺对话上下文。指标必须按 `origin` 分开报;真实流量到位后要做交叉验证。
4. **源覆盖不完整**。v1 没有论坛和学科群聊天,它们的文本风格(口语、碎片、多轮)
   与现有源差别很大。在 v1 上选出的模型,接入后需在 v2 重新验证。
5. **元数据可用性各源不对等**。微信部分 `source` / `tags` 零区分度;handbook 有
   `subject_code` / `section` / `year`;小助手问答有对话时间。**写实验代码时不要
   假设字段通用。**
6. **时效性是标注约定,不是客观事实**。「过期版本 = 1」是本项目的取舍。

**禁止事项:**

1. **`split: test` 的 query 绝不能用于训练**,包括用作 few-shot 示例、prompt 调优、
   或任何形式的超参搜索。
2. **不要在 test-only 簇的文档上做任何监督训练。**
3. **不要修改 `corpus.jsonl` 后沿用旧指标**。新语料请开 `v2/` 目录,不要覆盖 `v1/`。
4. **不要用微信的 `question_text`(文章标题)作为 query** —— 它在被嵌入的文本里,
   构成直接泄漏。
5. **不要只报聚合指标**。任何结论都必须附带分源拆分 + judged fraction。聚合数字
   会把不同源上相反的表现平均成无意义的数。
6. **不要把 unanswerable 子集算进检索指标**。它的 ground truth 为空,算 recall 会
   得到 0.0 并拉低全局均值。
7. **不要让 held-out 的对话回流进语料**。`held_out_for_eval` 标记必须由 ingest
   阶段强制排除。

## 实施顺序

每一步单独产出、单独验证,再进入下一步。

0. **走完[开工前必须确认的事](#开工前必须确认的事)** 的五项。其中两项是动手活,
   不是等结论:**handbook 重跑抓取**(补齐 A–F 之后的 1589 门课)和
   **聊天记录 → QA 对的提取管线**(规则粗切 + LLM 提取 + 人工抽检 50 场)。
   handbook 重抓**必须在冻结之前完成**,否则冻结后再补就是换语料、历史指标作废。
1. **冻结语料**:三个源各自的 loader → 统一 schema → `doc_id` 生成 + 聚簇 +
   质量标记 + 小助手侧脱敏与个人化筛选 → `corpus.jsonl` + `clusters.json` +
   聚簇阈值的人工抽检报告。
2. **定标注 guideline**:0/1/2 判定标准、时效性规则、跨源竞争约定;试标 50 对 →
   算 kappa → 修 guideline。**这一步不通过不要往下走。**
3. **收集 query**:按簇抽取小助手问答(打 `held_out_for_eval`)+ 闭卷编写;
   刻意设计约 20 条跨源竞争 query。
4. **pooling + 标注**:非对称深度三路召回 → LLM 预标 → 人工复核 → `qrels.jsonl`;
   顺带产出 answerable / unanswerable 拆分(含人工定向查找确认)。
5. **挖难负例 + 切分 + 打包**:`train_pairs.jsonl` + `manifest.json` +
   `DATASET_CARD.md` + `load_dataset()` helper + baseline 示例。

**管线从第一天就按多源写**(`source` 字段、`doc_id` 前缀、分源统计),这样 v2 接
论坛和聊天记录时方法零改动,只需加一个 loader。

**前置依赖:没有(除了上面第 0 步)。** 数据集直接读文件快照,`doc_id` 从各自的
URL / 课程编号 / 对话 ID 派生,全流程不碰 Postgres、不碰 `pg_retriever`。

[ROADMAP_platform.md](../../roadmap/ROADMAP_platform.md) 第 18.1 项(a)的 `Article.id` 链路修复是**并行的、
另一件事**:它让线上 `/chat` 和在线 eval harness 返回的 id 与本数据集的 `doc_id`
对得上。两者最终必须用同一套 ID 规则,但数据集的构造不需要等它。
