## 为什么先定架构,再选模型

本项目的知识库是**混合的**:

| 部分 | 检索类型 | 长度 |
|---|---|---|
| 小助手问答(主体) | 对称 —— 问题 ↔ 问题 | 短 |
| handbook section | 非对称 —— 问题 → 段落 | 中 |
| 微信文章 | 非对称 | 长(正文 p50 1874 字) |

**塞进同一个向量空间会坏掉排序,而且坏法很具体:分数不可比。**

问句和问句的余弦相似度天然高(同义问法常在 0.85+),问句和答案段落的天然低(哪怕
完美回答也就 0.55–0.65)。而 [pg_retriever.py](../../../app/services/rag/retriever/pg_retriever.py)
现在是一条 SQL 直接 `ORDER BY embedding <-> query`:

```
0.88  某条问答对(其实问的不是一回事,只是句式像)
0.86  某条问答对
0.84  某条问答对
...
0.61  handbook 里真正回答了这个问题的那段   ← 排到十几名开外
```

**问答对会系统性压住文档,与谁更相关无关。** 这不是「换个更强的模型」能解决的
问题 —— 换任何 bi-encoder 都有这个尺度差。所以架构是比模型更上位的变量,先定
架构再选模型。

## 三种架构

### A. 都当文档 —— 非对称检索

问答对也是短文档,用检索型模型(bge-m3 这类)统一处理。

- ✅ 一个索引一个模型,现有代码基本不用改
- ❌ 丢掉最强的信号:**新问题和历史问题字面就很像**,这个便宜不占白不占

### B. 都当问题 —— doc2query

给每个 handbook section、每篇微信文章生成几个「这段能回答的问题」,索引问题,
文档作为答案挂在后面。检索永远是问句对问句。

**这正是本仓库原本的设计。** 证据:

| 证据 | 说明 |
|---|---|
| `knowledge_base(question_text, content)` | 一行 = 一个问题 + 一份内容 |
| 唯一索引 `(link, question_text)` | 允许同一个 link 有多行,每行一个不同的问题 |
| `build_embedding_text = question + "\n\n" + content` | 问题放最前面当抓手 |
| `app/services/question_generator/` | 现成的服务,给文章生成 3 个中文问题 |
| `Article.questions: List[str]` | 复数 |

而微信管线**跳过了生成这一步**:`question_text` 填的是标题,2312 篇文章 2312 行。
所以现在跑的是 B 的退化版 —— 每篇只有一个「问题」,而那个问题是标题。

- ✅ schema 和 question_generator 都现成,是接线不是重写
- ✅ 一个索引一个模型 —— **不碰镜像大小和 ECS 规格**,不影响 AWS 那条线
- ✅ 小助手问答天然就是这个形态,不需要任何生成
- ❌ **已知弱点**:一篇 5739 字的长文只挂 3 个生成问题,用户问的要是这 3 个都没
  覆盖到,这篇就检索不到。缓解办法是长文多生成几个、以及 `build_embedding_text`
  保留正文作部分兜底。**这个弱点的严重程度是可以量出来的,不用猜**

### C. 双索引 —— 各用各的模型,靠 reranker 合并

问答对走 paraphrase 模型,文档走检索模型,各取 top-k,再用 cross-encoder 重新打分
合并。

**cross-encoder 天然解决尺度问题** —— 它直接对 (query, text) 打分,不经过共享向量
空间,所以两个源的分数本来就在同一把尺子上。这是它作为「异构源合并层」的价值,
比单纯提升排序更重要。

- ✅ 每个任务用最合适的模型
- ❌ 两个模型进镜像,**直接顶到 AWS 那边的镜像大小和 ECS 规格约束**
- ❌ `pg_retriever`、import 管线、`/ready` 检查、migration 关卡都要处理两套

#### 双索引一定要两张表吗

不一定 —— **卡住的是维度,不是「双索引」本身**。

现有 schema 已经支持一张表放多套向量:

```sql
WHERE embedding_model = %s AND embedding_revision IS NOT DISTINCT FROM %s
```

`knowledge_base` 有 `embedding_model` / `embedding_revision` 两列,检索时按模型
过滤。同一张表塞两个模型产出的向量、查询时各查各的,逻辑上就是双索引。

但 `embedding VECTOR(384)` 维度写死。paraphrase-MiniLM 是 384、bge-m3 是 1024,
塞不进同一列。

| 情况 | 要不要两张表 |
|---|---|
| 两个模型维度相同 | ❌ 不用,一张表按 `embedding_model` 区分 |
| 维度不同(大概率) | ✅ 要,或一张表两个向量列(更难看) |

## 为什么 C 是条件分支,不是第三个选项

**C 只有在 A 和 B 的分源结果打架时才值得做。**

- B 在三个源上**全面**领先 → 直接用 B,C 是白花力气(还要付两张表 + 两个模型进
  镜像的代价)
- B 在小助手问答上赢、A 在 handbook 上赢 → **这才是 C 存在的理由**

所以 C 不是「第三个要试的方案」,而是「A/B 结果的一个条件分支」。

这也是为什么
[数据集设计](eval-dataset.md)里反复强调**指标必须分源报** ——
聚合成一个数,就永远看不出该不该做 C。

## 实验矩阵

### 先跑 baseline

**当前线上配置**(标题当问题 + 正文,`paraphrase-multilingual-MiniLM-L12-v2`,
单索引)必须先跑出一个数。没有它,后面所有数字都没有参照 —— 你不知道「B 拿了
0.62」到底是进步还是退步。

### 然后跑 2×2,不要排成一条线

如果直接跳到 B,你**同时改了架构和模型**,赢了也不知道是哪个带来的。这是典型的
混淆。拆开:

| | paraphrase 模型 | 检索模型(bge-m3 等) |
|---|---|---|
| **都当文档** | A1 | **A2**(标准 document RAG) |
| **doc2query** | **B1**(标准问题匹配) | B2 |

对角线是「匹配的」配置,非对角线是「错配的」。四格全跑,可以拆开回答:

- **架构的贡献**有多大(纵向比)
- **模型的贡献**有多大(横向比)
- **错配的代价**有多大(对角 vs 非对角)

离线跑一格几分钟,四格的成本远低于「跑错了重来」。

### 模型候选:任务类型要对

主任务是问题匹配(对称),所以候选清单和 document RAG 不一样:

| | 该找的 | 不该找的 |
|---|---|---|
| **bi-encoder** | paraphrase / STS 族;中文 STS 微调过的模型 | 纯 passage retrieval 模型 |
| **cross-encoder** | STS / 句对分类型 | `ms-marco` 族(训练的是 query → 段落) |

两个具体的坑:

- **`paraphrase-multilingual-MiniLM-L12-v2` 本来就选对了。** 它是 paraphrase 模型,
  在问题匹配上是对的族,不是随便挑的。要换应该换同族更强的,不是换成检索模型。
- **`bge` 系列默认是非对称检索模型**,官方文档明确说对称任务不要加 query
  instruction 前缀。**加了就是用错了** —— A 格加、B 格不加,别搞混。

关于 reranker:早期判断「先做 reranker 收益最高」在这个新认知下**更站得住** ——
不管最后选 A、B 还是 C,cross-encoder 都是把异构源拉到同一把尺子上的那一层,
**是三种架构的公共部分,先做不会白做**。而且 `cross-encoder/ms-marco-MiniLM-L12-v2`
不只是英文模型的问题,**任务类型也是错的**。

## 评估口径

每一格都要产出这几组数,缺一不可:

**1. 分源指标**

wechat / handbook / assistant_qa 各自的 Recall@k、nDCG@10、MRR@10。**聚合数字会把
不同源上相反的表现平均成无意义的数**,不能作为结论依据。

**2. Recall@50**

决定线上 `top_k` 该设多少 —— 候选池召回率是 reranker 的天花板,reranker 再强也捞不
回没检索到的文档。

这也是数据集里 **baseline 和最强 dense 候选都要 pool 到深度 50** 的原因:上线的
很可能不是 baseline 而是换掉之后的新模型,所以**新模型的前 50 名也必须被标注过**,
否则它的 Recall@50 是垃圾。BM25 只 pool 到 20 —— 它不会真的上线,作用只是补 dense
的盲区。

**3. judged fraction**

每个模型的 top-k 里被标注过的比例。**< 80% 说明踩到 pool 盲区,该格的数字不可用**,
必须把它的 top-10 补进 pool 重标再下结论。

**4. 配对显著性**

150 条 query 上,几个点的差距很可能是噪声。要做 **per-query 配对比较 + bootstrap
置信区间**,不能只看均值。分源报告时每个源至少 60 条,否则单源的置信区间同样不
可用。

**5. 成本**

p50 / p95 延迟、内存占用、模型文件大小。cross-encoder 给 50 个候选打分的延迟是硬
上线约束;模型大小直接决定镜像能不能塞得下(见[落 schema 的时机](#落-schema-的时机))。

## 离线执行,不碰数据库

**A、B、C 三种架构全部可以在内存里用 numpy 跑完。**

语料约 1.7 万篇(handbook 补齐后),而且现有迁移里**没有建 ivfflat / hnsw 索引** —— pgvector 就是精确
全表扫描,内存精确检索与线上行为等价。三种架构的差别只是「embed 什么文本、用哪个
模型、怎么合并」,全是离线代码的事。

**建表是部署动作,不是实验动作。** 这保证了:

- 不需要为实验做维度迁移 / 建第二张表
- 这条线**完全不阻塞 AWS 那条线**(见 [ROADMAP_platform.md](../../roadmap/ROADMAP_platform.md) 第 18.2 项)
- 只有胜出的配置才走「改维度迁移 + 全库重嵌入 + 进 DB」这条重路径

## doc2query 先做 pilot

别一上来给全部一万多篇生成。**先挑 200 篇跑一遍**,看:

- 生成的问题像不像真实用户会问的
- 一篇长文 3 个问题够不够覆盖(微信正文 p90 有 5739 字)
- 生成质量在 handbook 和微信文章上差别大不大(handbook 结构化、术语密集,微信是
  推广文,预期差别不小)

> **前置**:handbook 现有数据只覆盖字母序 A–F(2946 门课里 1589 门五个 section
> 全空,是抓取中途失败,不是没内容)。**pilot 之前要先把抓取补完**,否则你验证的
> 只是计算机和教育两个学院。详见数据集设计里的警告框。

pilot 通过了再全量跑。全量批处理成本不高,但跑错了重跑很浪费时间。

**注意 pilot 的 200 篇不要只从一个源抽** —— 按源分层抽,否则你只验证了其中一种。

## 落 schema 的时机

赢家出来之后才谈这些,而且这里是**与 AWS 那条线的收敛点**:

| 决定 | 影响 |
|---|---|
| 向量维度 | `VECTOR(384)` 写死。换 1024 维需 ALTER + 全库重嵌入重导。**在建 RDS 前做,成本差一个数量级**(现在 DB 是一次性容器,迁移=删了重来) |
| 一张表还是两张 | 见[上文](#双索引一定要两张表吗);两张表会牵动 `pg_retriever`、import 管线、`/ready`、migration 关卡 |
| 模型文件大小 | 模型烤入镜像。bge-m3 + bge-reranker-v2-m3 约各 2.2GB,镜像会从 3.35GB 冲到 ~7GB,**Phase 1 的验收基线(冷启动 7.5s / idle 944MiB)全部要重测**,并可能推翻 Phase 5 第 4.1 项的「烤入镜像」阈值 |
| `top_k` | 5 → 50 会让每请求 CPU 差 10 倍,直接决定第 13/14 项(worker/扩容策略、资源基线) |

**理想时序**:第 1–3 步(离线实验)与 Phase 2 的 IaC 骨架并行;等实验出结论时,
Phase 2 大概也就到了要定 ECS 规格的环节,正好一起收敛。

## 对数据集的要求

本文的实验设计对 `corpus.jsonl` 提出两条约束,**必须在冻结语料时就满足**,否则
B 类配置要改 schema 重跑:

1. **`question` 与 `generated_questions` 两个字段分开存在。** 前者是真实存在的问题
   (小助手问答才有),后者留给 doc2query 填充 —— **现在留空,但字段必须存在**。
2. **微信的标题不填进 `question`。** 它是标题不是问题,填进去就是在重复现在那个
   退化用法,会让 A / B 两格的对比失真。

另外 **`source` 字段和 `doc_id` 前缀**是分源指标的前提,同样在冻结时就要有。

## 实施顺序

```
0. 冻结语料(见数据集设计 Step 0)—— 必须先满足上面两条 schema 约束
1. baseline:当前线上配置                      ← 必须有,否则没有参照系
2. doc2query pilot(200 篇,按源分层)          ← 通过了才做全量生成
3. 2×2 网格:A1 / A2 / B1 / B2                 ← 离线,一格几分钟
4. 看分源结果 → 决定要不要做 C
5. reranker 单独一轮(固定候选池,只比提升量 Δ) ← 三种架构的公共部分
6. 赢家落 schema:维度迁移 / 建表 / 镜像重测      ← 与 AWS 那条线的收敛点
```

**第 1–5 步全程不碰数据库**,与 Phase 2 零冲突。
