## 背景

在此之前,CSSA-DA 只能在笔记本上用 `docker-compose` 跑起来。要给内测用户用,它得在
一台**别人也能访问、而且我们不关机它就一直在**的机器上跑。这就是上 AWS 的全部动机。

但「上 AWS」不是一个动作,是十几个零件的拼装:网络、镜像仓库、身份、数据库、容器编排、
负载均衡。**前七步只做地基**——建完之后 AWS 上一个容器都没跑,但后面每一步都有地方落脚。

### 为什么用 Terraform 而不是在网页上点

两条理由,第二条更重要:

1. **可重复。** 点出来的东西,你不记得点了什么,别人看不到你点了什么,重建要再点一遍。
2. **可回答「线上和我以为的一样吗」。** `terraform plan` 随时能对比代码和现实,告诉你
   有没有人手工改过什么。手点做不到这件事——你只能一个页面一个页面去看。

代价是多学一门语言(HCL)和一个概念(state)。对一个会长期维护、而且人会换的社团项目,
这个代价值得。

> **一条纪律:一个资源只能有一个主人。** 要么归手点管,要么归 Terraform 管,不能两个都
> 管——Terraform 不认识手点建的东西,`apply` 会建出重复的一套。
>
> 按这条,**账号级的一次性设置留在控制台**(预算告警、异常检测、root MFA、IAM 用户),
> **基础设施归 Terraform**(VPC、ECR、安全组……)。

## 大图:一个请求会经过什么

到第 11 步为止,下面这张图**每一格都是真的**——有东西在里面跑,而且从你家里的浏览器就
能打到它:

```text
                     互联网
                        │
                        │  ① 只有这一个入口
                        ▼
        ┌───────────── VPC(你的私有网络)──────────────┐
        │                                              │
        │   公有子网 a          公有子网 b              │
        │   ┌──────────┐       ┌──────────┐            │
        │   │   ALB    │ ····· │   ALB    │  ② 第 11 步  │
        │   └────┬─────┘       └──────────┘            │
        │        │ ③ 只准 8000                          │
        │   私有子网 a          私有子网 b              │
        │   ┌────▼─────┐                               │
        │   │ 容器 ×1  │        (可扩到这边)   ④ 第 10 步 │
        │   └──┬───┬───┘                               │
        │      │   │ ⑤ 只准 5432                        │
        │      │   └──────────┐                        │
        │      │          ┌───▼──────┐                 │
        │      │          │  RDS     │        ⑥ 第 9 步 │
        │      │          └──────────┘                 │
        │      │ ⑦ 出网                                 │
        │   ┌──▼───────┐                               │
        │   │ NAT 网关 │(在公有子网)         ⑧ 第 8 步 │
        │   └──────────┘                               │
        └──────────────────────────────────────────────┘
                        │
                        ▼
                   OpenAI(公网)
```

**七条边各是什么**:①用户进来 ②ALB 收下 ③转给容器 ④容器在跑 ⑤查数据库
⑥数据库在私有子网 ⑦容器要出网调 OpenAI ⑧出网只能走 NAT。

另外三样不在图里、但同样是这套东西的一部分:

- **ECR** —— 镜像仓库,容器启动时从这里拉代码
- **Secrets Manager** —— 三个密钥的存放处(OpenAI key、前端用的 key、数据库密码)
- **CloudWatch** —— 容器打的日志落在这里

一句话概括这十一步:**从一台空账号,到公网上有一个地址,后面跑着你的代码、连着你的
数据库——只是数据库还是空的。**

### 簇 A:用代码管理云资源

> **这一簇解决**:怎么把「AWS 上应该有什么」写成文件。

#### 声明式:描述结果,不描述步骤

你熟悉的代码是命令式的——「先做 A,再做 B」。Terraform 反过来:**你描述最终应该长什么
样,它自己算出现在是什么样、怎么变过去。**

所以 `.tf` 文件里**没有顺序**,把 VPC 写在子网后面一样能跑。同一份文件跑一百遍,第一遍
建出来,后面九十九遍发现「已经符合描述了」,什么都不做。

这个性质有个直接的好处:`plan` 能回答「线上和代码一致吗」。不一致的部分就是 plan 里
列出来的那些。

#### 引用就是依赖

```hcl
resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id      # ← 不是抄一串 vpc-0f5e...
}
```

写引用而不是写 ID,带来两件事:一是不会抄错,二是**Terraform 由此知道要先建 VPC 再建
网关**。依赖顺序是算出来的,不是排出来的。

这解决了手点 ECS 时最大的痛苦:手点要你把执行角色 ARN、日志组名、子网 ID、安全组 ID
一个个复制粘贴,抄错一个字符,报错信息和出错的地方隔着十万八千里。

#### state:那本账

Terraform 把「我建过什么」记在 state 文件里,它是**代码和真实资源之间的那根线**。

丢了 state,Terraform 就失忆:它认为什么都没建过,再 `apply` 会建出重复的一套,而真正
在跑的那套变成孤儿——没人管,但还在收费。

目前 state 是**本地文件**(`infra/terraform.tfstate`,已被 gitignore)。这在资源全免费
的阶段可以接受,**但在建 RDS 之前必须迁到 S3**——见[还没做的](#还没做的)。

#### 三个命令

| 命令 | 做什么 | 碰 AWS 吗 |
|---|---|---|
| `init` | 下载 provider 插件,生成 lock 文件 | ❌ 只连插件仓库 |
| `plan` | 读现状,和代码比对,列出差异 | ✅ 只读 |
| `apply` | 执行差异 | ✅ 会改 |

`destroy` 是特殊的 apply:把 state 里记的东西全删掉。

### 簇 B:网络——包怎么走

> **这一簇解决**:机器之间怎么找到对方,以及怎么出去上网。

#### 地址与网段

IP 地址定位机器,端口定位机器上的哪个程序:

```
10.0.130.5 : 8000
└─哪台机器─┘ └哪个程序┘
```

**网段**是一段连续的地址范围,写成 `地址/位数`。斜杠后面的数字是「前多少位固定」:

| 写法 | 范围 | 地址数 |
|---|---|---|
| `10.0.0.0/16` | 10.0.0.0 – 10.0.255.255 | 65,536 |
| `10.0.0.0/20` | 10.0.0.0 – 10.0.15.255 | 4,096 |
| `0.0.0.0/0` | **所有地址** | 全部 |

最后一行值得单独记:`0.0.0.0/0` = 零位固定 = 一切。路由表里它表示「默认路由」,安全组
里它表示「任何人」。

#### VPC、子网、可用区

**VPC** 是 AWS 圈给你的一块私有网络,别人的东西进不来——相当于 `docker-compose` 自动
建的那个内部网络,只是大得多。

**子网**是 VPC 里切出来的一块,而且**一个子网只能待在一个可用区(AZ)里**。AZ 是同一
区域内**物理上分开的机房**。

为什么本项目要两个 AZ:**不是我们想要冗余,是 AWS 强制**——ALB 要求至少铺在两个 AZ,
RDS 的子网组也要求覆盖两个 AZ(哪怕只跑一个单实例)。

于是 2 个 AZ × 2 种子网 = **4 个子网**。

#### 公有和私有的真正区别

**只有一行路由。**

子网本身没有「公有」属性。它公有,是因为**它的路由表把 `0.0.0.0/0` 指向了互联网网关**:

```
公有子网的路由表              私有子网的路由表
10.0.0.0/16 → local          10.0.0.0/16 → local
0.0.0.0/0   → igw-xxx        (没有这一条)
```

私有子网的路由表里没有默认路由,所以里面的东西**哪儿也去不了**。

#### 互联网网关 vs NAT 网关

这两个最容易混。关键在于:**走互联网网关出去的机器,必须自己有公网 IP。**

原因是物理的——`10.0.130.5` 这种地址在公网上不可路由,对方收到包也不知道往哪儿回。

|  | 互联网网关(IGW) | NAT 网关 |
|---|---|---|
| 方向 | **双向**,外面能主动连进来 | **单向**,只有里面能出去 |
| 机器要公网 IP 吗 | **要** | **不要** |
| 价格 | **免费** | 按小时 + 按流量 💰 |

NAT 的做法是替私有机器**借一个公网身份**:包先到 NAT,NAT 把源地址换成自己的公网 IP
发出去,回包再换回来转交。

落到本项目:ALB 必须被公网主动访问 → IGW;容器要能出去调 OpenAI 但绝不能被公网连到 →
NAT。**NAT 是第 8 步,目前还没有,所以私有子网现在完全封闭。**

#### 网关端点:一条免费的近路

容器要从 ECR 拉镜像,而**ECR 的镜像层实际存在 S3 里**。默认情况下这些流量要绕到公网
再拐回 AWS,经过 NAT 并按 GB 计费。

**S3 网关端点**是 VPC 到 S3 的一条私有通道。它之所以免费,是因为它不是一台跑着的设备,
**就是路由表里的一条规则**——「发往 S3 的流量走这里,别走 NAT」。

对本项目收益立竿见影:API 镜像压缩后接近 1GB,每次启动任务都要拉一遍。

> ⚠️ 端点必须挂到**私有子网的路由表**上才生效。挂错路由表不会报错,只是不起作用。

### 簇 C:边界——谁准进来

> **这一簇解决**:机器之间能不能连。前提是簇 B——先有路,才谈准不准走。

#### 安全组是一张白名单

**贴在机器上的名单**,写着谁可以敲我的哪个端口。不在名单上的,包直接丢弃——连接方那边
表现为**超时**,不是「被拒绝」。

三个反直觉的特点:

**① 只能写允许,写不了禁止。** 纯白名单,没有拒绝规则。

**② 它是有状态的。** 你允许别人进来敲 8000,**你回给他的包自动放行**,不用配对应的出站
规则。传统防火墙要写两条,安全组只写一条。

> 这解释了 [security_groups.tf](../../../infra/security_groups.tf) 里最奇怪的一处:
> RDS 那个组**一条出站规则都没有**,却照样能把查询结果返回给容器。回包不受出站规则管;
> 出站规则管的是它**主动发起**的连接——而数据库从不主动连谁。

**③ 可以引用别的安全组。** 规则里可以写「凡是戴着 ecs-tasks 牌子的机器」,而不是写 IP
段。容器重启换 IP、扩容出新容器,规则都不用动。

#### 一次连接需要两条规则

既然是有状态的,为什么「ALB 的出站」和「容器的入站」都要写?

因为它们是**两台机器各自的名单**:

```
ALB 的出站名单   ←  规定 ALB 可以主动去连谁
容器的入站名单   ←  规定谁可以来连容器
```

**一次主动连接 = 发起方出站 + 接收方入站,共两条;回包零条。**

还有个容易错的点:**端口是谁的**。

| 方向 | 那个端口属于 |
|---|---|
| 入站 | **我的** ——别人来敲我的这个端口 |
| 出站 | **对方的** ——我去敲对方的这个端口 |

所以 ALB 的出站规则里写 8000,指的是容器的 8000;ALB 自己根本没有 8000 端口。

#### 和路由表的区别(粘合簇 B 与簇 C)

| | 管什么 | 不通时的表现 |
|---|---|---|
| **路由表** | 包该往哪走——地图 | 找不到路 |
| **安全组** | 这个包准不准进——门卫 | 到了门口,但进不去 |

**两个都得通。** 排查网络问题时先分清是哪一类:「不知道怎么去」还是「到了但被挡住」。

> 顺带:AWS 还有个**网络 ACL**,是子网级别的、有拒绝规则、无状态。它默认全放行,基本
> 不用碰。知道它是另一层就行。

### 簇 D:身份与制品——ECS 替你干活需要什么

> **这一簇解决**:容器还没跑起来之前,谁去拉镜像、谁去开日志流。

#### 为什么需要角色

到目前为止,是**人**在操作 AWS,用一对长期密钥证明身份。

但接下来的动作没有人参与:**凌晨三点容器挂了,ECS 要自动拉起一个新的**。它得去 ECR 要
镜像、去 CloudWatch 开日志流,而这两边都会问「你是谁」。

ECS 不能回答「我是 ECS」——全世界的 ECS 都是 ECS,它必须出示**这个账号里的一个身份**。

|  | 用户(User) | 角色(Role) |
|---|---|---|
| 长期密钥 | **有** | **没有** |
| 怎么用 | 拿密钥直接调 | 临时「扮演」,拿几小时后过期的凭据 |
| 给谁 | 人 | **服务** |

ECS 启动容器时自动扮演指定的角色,把临时凭据注进去。**容器里不会有任何长期密钥。**

#### 角色的两半

一个角色由两部分组成,缺一不可:

```
信任策略   ←  谁可以扮演我?      →  只有 ecs-tasks.amazonaws.com
权限策略   ←  扮演之后能干什么?  →  拉 ECR 镜像、写 CloudWatch 日志
```

用门禁卡类比:信任策略是「这卡发给谁」,权限策略是「这卡能开哪几扇门」。只写后者,就是
一张放在地上谁捡到谁能用的卡。

信任策略本身也是一份普通的 IAM 策略文档,语法和权限策略相同——只是资源固定是角色自己,
所以省掉了 Resource 那一栏。这解释了为什么里面还要写一个看起来多余的动作
`sts:AssumeRole`:那一栏真的有别的值,比如 **`sts:AssumeRoleWithWebIdentity`**,正是
Phase 4 用 GitHub OIDC 免密钥部署时要用的那个。

> ⚠️ 信任策略里必须是 `ecs-tasks.amazonaws.com`,不是 `ecs.amazonaws.com`。写错了任务
> 起不来,报错只说「不能扮演这个角色」。

#### 执行角色 ≠ 任务角色

ECS 文档里有两个长得很像的角色,混淆会浪费很多时间:

|  | **任务执行角色** | **任务角色** |
|---|---|---|
| 谁在用 | **ECS 服务自己** | **容器里的你的代码** |
| 什么时候 | 容器**启动之前** | 容器**运行期间** |
| 干什么 | 拉镜像、开日志流、取密钥 | 代码调用 AWS API |

**判断标准:动作发生在容器启动前 → 执行角色;由容器里的代码发起 → 任务角色。**

**本项目目前只需要执行角色。** 应用调的是 OpenAI(第三方 HTTP)和 Postgres(数据库
协议),都不是 AWS API,所以没有任务角色要建。Phase 3 管线读写 S3 时才需要。

#### 镜像是带 CPU 架构的

容器**不是虚拟机**——它和宿主机共享内核和 CPU,隔离的只是文件系统和进程视图。而镜像里
装的是**已经编译好的二进制**(Python 解释器、torch 的 `.so`)。

所以镜像分架构,而且**架构来自构建时的机器,不来自 Dockerfile**:

```
在 Apple Silicon 上 docker build  →  arm64 镜像
在 x86 机器上 docker build        →  x86_64 镜像
```

给错架构的表现是 `exec format error`,看起来像镜像坏了。

**本项目选 arm64**:开发机是 Apple Silicon(原生构建,不用 QEMU 模拟)、Fargate 的
Graviton 便宜约 20%。选之前扫过 `uv.lock`——**所有带 C 扩展的包都有 aarch64 wheel,
没有任何一个只有 x86_64**,torch 也有 `manylinux_2_28_aarch64` 的 CPU 版。

代价:[ROADMAP_platform](../../roadmap/ROADMAP_platform.md) Phase 1 记录的那批基线
(冷启动 7.5s、idle 944MiB)是在 x86 上测的,全部作废。但那批数字**本来就作废**——同一节
里已经注明「两者的测量机器不同且未对齐」。

### 簇 E:配置与密钥怎么进容器

> **这一簇解决**:容器怎么知道数据库在哪、密码是什么,而这些东西又不进代码、不进 state。

#### 两类配置,两条路

配置分成两类,进容器的方式完全不同:

| | 例子 | 怎么进 |
|---|---|---|
| **普通配置** | 数据库主机名、端口、库名、日志级别 | 任务定义里的环境变量,明文,进 git |
| **密钥** | OpenAI key、数据库密码 | **ECS 在容器存在之前**去 Secrets Manager 取,注入成环境变量 |

第二条的关键在「容器存在之前」:**容器里没有任何可以用来取密钥的凭据**,取的动作是
[执行角色](#角色的两半)做的。这也是为什么那张工牌需要一条读密钥的权限。

#### 密钥为什么不放进 Terraform

把密钥写进 `.tf` 或 `.tfvars`,它就会**明文躺在 state 里**。state 桶是私有且加密的,所以
这不是「泄露到互联网」的问题,但有三条后果:

1. **state 对能读它的人是明文的** —— 而你没法只给组员「能跑 plan」却不给「能看到所有
   密钥」,这两件事在 state 里是绑死的
2. **桶开了版本控制** —— 轮换之后,旧密码永远留在历史版本里
3. **数据库密码本来就不用进 state** —— RDS 可以自己生成、自己保管(见第 9 步),所以
   放进去等于同时跑两套规矩

因此这套的做法是:**Terraform 声明「这里需要一个密钥」,值由人一次性灌进去**。代码里看
得见需求,state 里看不见值。

#### 一个具体的摩擦:`DATABASE_URL` 拼不出来

应用要的是一个完整字符串:

```
postgresql://用户:密码@主机:5432/库名
```

而 RDS 的密钥里是一个 JSON:

```json
{"username": "cssa_admin", "password": "……"}
```

ECS 能**挑出其中一个字段**注进去(语法是 `密钥ARN:username::`),但**不能把两个字段拼成
一个字符串**。

三条路:改应用、自己建一个存完整 URL 的密钥、容器启动脚本里拼。第二条是死路——Terraform
要拼就得先读到密码,密码就进 state 了。最后选了**改应用**:加几个可选的分件配置,
`DATABASE_URL` 没设时拼出来。见 [settings.py](../../../app/core/config/settings.py)。

> ⚠️ **拼的时候必须做百分号编码。** RDS 生成的密码不保证 URL 安全,里面一个 `@` 或 `/`
> 会把 URL 拆在错误的位置,而失败表现为「主机名解析不了」——指向的地方和真正的原因隔着
> 十万八千里。而且**本地永远测不出来**,因为 docker-compose 用的是 `rag_password`。

### 簇 F:运行——任务、服务、两层健康检查

> **这一簇解决**:容器怎么被跑起来、坏了谁管、以及「它好了没有」由谁判断。
> 前提是[簇 D](#簇-d身份与制品ecs-替你干活需要什么)和[簇 E](#簇-e配置与密钥怎么进容器)。

#### 三个长得像的词

| 词 | 是什么 | 类比 |
|---|---|---|
| **任务定义** | 一张说明书:用哪个镜像、多少 CPU 内存、注入什么 | `docker-compose.yml` 里的一段 |
| **任务** | 按说明书真正跑起来的一个容器 | `docker run` 出来的那个 |
| **服务** | 一个管家:保证永远有 N 个任务活着,死了重启,换版本时逐个替换 | 没有直接类比,这是新东西 |

**Fargate** 是「你别管服务器」的模式:给说明书和规格,AWS 负责找机器跑。

#### 规格是离散档位,不是连续的

Fargate 的 CPU 和内存只能选**固定组合**。后果很实际:多 200MB 可能不花钱,也可能把你推到
下一档、内存成本翻倍。

这条反过来约束了模型选型——换一个大一点的 reranker,可能不是「多花一点」,而是「跳一档」。

#### 部署是滚动的,而且可以自动回滚

改了任务定义(比如换镜像 tag)再 apply,服务会**起新任务、等它健康、再停旧任务**。中途
不中断。

**熔断**(`deployment_circuit_breaker`)是这件事的安全网:新版本一直起不来就自动回滚到
上一个能跑的版本。没有它,一个坏镜像会把好的那个替换掉,然后服务躺下。

#### ⭐ 健康检查有两层,问的是不同的问题(粘合簇 C 与簇 F)

这是最容易搞混、也最容易配错的地方:

| | 谁在问 | 问什么 | 答错的后果 |
|---|---|---|---|
| **容器健康检查** | ECS | 这个容器**死没死** | 判死 → 杀掉重启 |
| **目标组健康检查** | 负载均衡器 | 这个容器**该不该收流量** | 判不健康 → 不转发 |

两层都指向应用的两个端点,而这两个端点回答的也是不同问题:

- **`/health`** —— 进程活着吗。不碰数据库
- **`/ready`** —— 能以全速服务吗。查数据库、查模型

**正确的搭配是:ECS 看 `/health`,负载均衡器看 `/ready`。**

> ⚠️ **配反了会得到一个骗人的故障。** 如果让 ECS 去看 `/ready`,而数据库恰好是空的,
> ECS 会不停杀掉一个其实健康的容器——你看到的是任务反复起停,而排查方向会指向网络或镜像。
>
> 本项目**目前故意偏离**了这个搭配:两层都看 `/health`,因为库里还没有表,`/ready` 会
> 永远 503、负载均衡器会永远不导流。这是临时状态,见[还没做的](#还没做的)。

#### 还有第三个时间窗:宽限期

新任务启动要时间(这里实测 57 秒,其中 14 秒在加载和预热两个模型)。这期间它**还没开始
应答**,而健康检查已经在敲门了。

所以两层各有一个「先别当真」的窗口:容器检查的 `startPeriod`,和服务的
`health_check_grace_period_seconds`。**给短了的症状是无限重启,而日志里完全看不出「它只是
还没启动完」。**

## 十一个步骤

### 第 1 步:本机工具链

> 前置知识:无

装 Terraform 和 AWS CLI,配好凭据。

两个值得记下的实际问题:

- **Terraform 不在 Homebrew 主仓库里了**(2023 年改成 BUSL 许可后被移除)。这里直接下载
  官方二进制并核对 SHA256——它是单文件静态程序,不需要编译器。装的是 **1.16.2**。
- **凭据不进代码**。`aws configure` 写的是 `~/.aws/credentials`,在仓库之外。provider
  自己按顺序去找(环境变量 → 凭据文件 → 实例角色),所以 [infra/](../../../infra/) 里
  没有任何密钥,可以放心进 public 仓库。

> **为什么用凭据文件而不是环境变量**:环境变量看起来「不落盘」,但要持久化就得写进
> `~/.zshrc`——那是个 644 权限、每次开终端都执行的文件,比 600 权限的凭据文件更糟。
> 更关键的是**环境变量会被所有子进程继承**:你在那个终端里跑的任何脚本、任何 npm 包都
> 读得到。凭据文件只有主动去读它的程序才拿得到。
>
> 环境变量的正确场合是 CI——那里环境一次性、跑完销毁。

**诚实的边界**:这对密钥是长期有效的管理员凭据,**永不过期**。笔记本丢了、密钥泄露了,
在被发现之前一直有效。正路是 IAM Identity Center(登录换几小时过期的临时凭据),这是
一笔记下的债。

### 第 2 步:Terraform 骨架

> 前置知识:[簇 A](#簇-a用代码管理云资源)

三个小文件,不建任何资源:

- [versions.tf](../../../infra/versions.tf) —— 钉 Terraform `>= 1.9`、AWS provider
  `~> 6.0`(实际解析到 **6.64.0**)。`~>` 是悲观约束:允许 6.x 的小版本,不允许 7.0——
  provider 升大版本会有破坏性变更,不卡的话某天 `plan` 会突然要改一堆你没动过的东西。
- [providers.tf](../../../infra/providers.tf) —— 区域 `ap-southeast-2`(用户在墨尔本)
  和 `default_tags`。
- [variables.tf](../../../infra/variables.tf) —— 项目名、环境、区域、CIDR、AZ 数量。

`.terraform.lock.hcl` **要提交**,和 `uv.lock` 同理:保证每个人、以后的 CI 拿到的是同一
个 provider。而 `.terraform/`(插件本体,**761MB**)和 state 不提交。

### 第 3 步:VPC 与子网

> 前置知识:[簇 B](#簇-b网络包怎么走)

[vpc.tf](../../../infra/vpc.tf),14 个资源:

| | 数量 | 说明 |
|---|---|---|
| VPC | 1 | `10.0.0.0/16`,开 DNS 解析与主机名 |
| 互联网网关 | 1 | |
| 公有子网 | 2 | `10.0.0.0/20`、`10.0.16.0/20` |
| 私有子网 | 2 | `10.0.128.0/20`、`10.0.144.0/20` |
| 路由表 | 3 | 公有共用 1 张,私有每 AZ 1 张 |
| 路由表关联 | 4 | |
| S3 网关端点 | 1 | 挂在两张私有路由表上 |

三个设计决定:

**① 可用区是查出来的,不是写死的。** 用 `data` 源查询当前区域可用的 AZ,取前两个。AWS
把 AZ 名字映射到**不同账号的不同物理机房**,而且不是每个账号都有每个区——写死是在赌。

**② 私有子网放在地址空间的上半区**(`+8` 的偏移)。于是看到 `10.0.130.x` 不用查就知道
它在私有子网,看到 `10.0.16.x` 知道它在公有。

**③ 私有路由表每个 AZ 一张,而不是共用一张。** NAT 网关是按 AZ 建的,将来加 NAT 时每个
AZ 要指向自己那个。现在共用一张,到时候得拆——拆表比一开始就分开麻烦。

**DNS 那两个开关必须开**:RDS 给的是域名不是 IP,关掉 DNS 的话容器解析不了,而失败表现
为「连接超时」,读起来像安全组问题,会把排查引向错误的方向。

### 第 4 步:destroy 演练

> 前置知识:[簇 A 的 state](#state那本账)

跑一次 `destroy` 再 `apply`,确认「一条命令删光,一条命令建回来」。

**为什么值得花这五分钟**:这是以后敢「白天建、晚上删」省钱的底气来源。而且**必须趁现在
做**——等 RDS 建起来之后就不能再这么玩了,里面有数据。

重建之后**资源 ID 全变了**(VPC 从 `vpc-0da6...` 变成 `vpc-0f5e...`),证明它是真删真建,
不是假装。同理,将来重建后 ALB 的域名也会变。

### 第 5 步:ECR 与第一次推送

> 前置知识:[镜像是带 CPU 架构的](#镜像是带-cpu-架构的)

[ecr.tf](../../../infra/ecr.tf) 建仓库 `cssa-da-api`。名字**不带环境段**——镜像是同一份
制品,将来有测试环境也是跑同一个镜像、配不同参数。

三个设定:

- **`IMMUTABLE`** —— 一个 tag 永远对应同一份字节。这是「线上跑的到底是哪份代码」能被
  回答的前提。代价是重新构建同一个 commit 要先删旧镜像,少见到可以接受。
- **推送时扫描** —— 免费,但**只在推送时扫一次**,不会回头告诉你三个月前的镜像爆了新
  漏洞。当烟雾报警器用,别当安全方案。
- **生命周期策略:保留 5 个镜像**,未打 tag 的 1 天后删。
  > 这个数字是**回滚深度**的决定,不是成本的决定——镜像分层且层是共享的,多一个镜像
  > 主要只占它变化的那几层,不是又一个完整副本。

`force_delete = true` 是临时的,代码里留了 TODO:上线后要改回 `false`,那时候一次手滑的
destroy 抹掉镜像历史才是更大的风险。

**推送前发现的一个洞**:[.dockerignore](../../../.dockerignore) 原本没有排除 `infra/`,
而 `Dockerfile.api` 以 `COPY . .` 结尾——761MB 的 provider 二进制和 state 文件会被打进
一个会被分发的镜像。已修。

实测数字:

```
本地镜像     2.10 GB     ← 解压后
ECR 中       0.98 GB     ← 压缩后,传输和存储按这个算
模型         606 MB      ← embedding 477M + reranker 129M
```

### 第 6 步:执行角色与日志组

> 前置知识:[簇 D 的身份部分](#簇-d身份与制品ecs-替你干活需要什么)

[iam.tf](../../../infra/iam.tf) 与 [logs.tf](../../../infra/logs.tf)。

权限用 AWS 托管的 `AmazonECSTaskExecutionRolePolicy`,不自己写。理由:这是完全标准的
需求,AWS 自己维护;而手写容易漏(比如漏掉 `ecr:GetAuthorizationToken`),**漏了之后的
报错不会说缺哪一条**。

它**不含读 Secrets Manager**——那条随数据库密码一起加,而且要收窄到那一个密钥的 ARN,
不是整个 Secrets Manager。

日志组 `/ecs/cssa-da-prod-api`,**保留 30 天**。自己建而不是让 ECS 自动建,是因为自动建
的那个不受 Terraform 管,而且**永不过期**——无止境增长、而且没人做过这个决定。

### 第 7 步:三个安全组

> 前置知识:[簇 C](#簇-c边界谁准进来)

[security_groups.tf](../../../infra/security_groups.tf),3 个组 + 5 条规则。

走一遍一个请求要过的检查:

```text
浏览器
  │ 主动连 ALB:80
【1】ALB 入站:0.0.0.0/0 → 80              ✅
  │ ALB 变成主动方,去连容器:8000
【2】ALB 出站:→ ecs-tasks 组的 8000        ✅
【3】容器入站:← alb 组                     ✅
  │ 容器主动去连数据库:5432
【4】容器出站:→ 0.0.0.0/0(全通)          ✅
【5】数据库入站:← ecs-tasks 组             ✅
  │
  ▼ 回包 ×3:不检查任何规则(有状态)
```

**5 条规则,一条不多一条不少。** 浏览器那次只要一条,因为浏览器不在这个账号里,管不着
它的出站。

**容器的出站是全通的**,这是有意的:收窄就得枚举 OpenAI 的地址,而那些会变且不通知。
一条会在生产环境静默失效的规则,比一条宽规则更糟。**这一层真正的保护在入站**——只有 ALB
进得来。

> ⚠️ **AWS 默认给新安全组加一条「允许所有出站」,而 Terraform 会把它删掉。** 所以出站
> 要什么必须明写,否则连接以「超时」的形式失败——超时最难查,因为没有哪条规则能指着说
> 是它拦的。

**目前只开 80,没有 443。** 因为证书必须签给自己的域名,而 ALB 自带的
`xxx.elb.amazonaws.com` 是 AWS 的域名。见[还没做的](#还没做的)。

### 第 8 步:NAT 网关——私有子网的出口

> 前置知识:[互联网网关 vs NAT 网关](#互联网网关-vs-nat-网关)

见 [vpc.tf](../../../infra/vpc.tf) 末尾。**这套东西里第一个按小时计费的资源**,也是私有子网不再密闭的原因:应用要调 OpenAI,而
OpenAI 不是 AWS 服务,没有端点可以私有地到达。

两个决定:

**只建一个,不是每个可用区一个。** 每区一个能扛住「一个机房的网关挂了」,代价是月费翻倍。
内测阶段不值得。**后果要说清楚:这一个挂了,两个可用区的容器都出不了网。**

> 第 3 步给每个可用区各建一张私有路由表,就是为这一刻留的:现在两张表都指向这一个网关;
> 以后要加第二个,只改一张表,不用拆表。

**Elastic IP 是固定出口地址。** 除了 NAT 必须有一个之外,它还有个以后才会用到的性质:
所有出去的流量在对方看来都来自这一个地址。**哪天某个第三方要求提供出口 IP 加白名单,
这就是答案**——而把容器直接放公有子网的方案给不出这个答案,因为每个容器的地址都不一样
且重启就变。

这一步也是 `depends_on` 在整份代码里第一次出场:NAT 网关的参数里没有提到互联网网关,
但它没有网关就无处可去。**引用能表达的依赖不用手写,这种隐含的必须写。**

### 第 8.5 步:把 state 搬到 S3

> 前置知识:[state:那本账](#state那本账)

排在建数据库**之前**,这个顺序是有意的:

| | state 丢了会怎样 |
|---|---|
| 搬之前 | Terraform 忘记建过什么。但资源便宜可重建,控制台删干净重来就行 |
| **有了 RDS 之后** | Terraform 不知道数据库存在 → 再 apply 会建**第二个** → 而第一个带着数据继续收费,没人管 |

现在做风险为零,晚一步做风险就变成「花钱且有数据」。

backend 配置在 [versions.tf](../../../infra/versions.tf)。三个设定:

- **桶不归 Terraform 管。** 描述自身存储位置的 state 是个死结,而要解开它的时刻恰好是最难
  解的时刻。所以它和预算一样,是 Terraform 之外的账号级引导设施
- **开版本控制。** 于是 state 有了完整历史,而不只是本地那个单代 `.backup` 文件
- **`use_lockfile = true`。** 防止两个人同时 apply 把账本写坏。Terraform 1.10 之前这需要
  额外建一张 DynamoDB 表,现在 S3 自己就能做

> backend 块里的值**不能是变量**——Terraform 要先找到 state 才能读变量。所以桶名是写死的
> 字面量,会原样进 git。这也是桶名用随机后缀而不是账号 ID 的原因:仓库是公开的。

搬完之后的实际收益:**换台电脑、组员克隆仓库,`terraform init` 之后直接接着干。**

### 第 9 步:数据库

> 前置知识:[簇 E](#簇-e配置与密钥怎么进容器)

见 [rds.tf](../../../infra/rds.tf)。PostgreSQL **16.15**,对齐本地 docker-compose 的 pg16,所以迁移脚本和 `VECTOR(384)` 这一列
在两边含义相同。`db.t4g.micro` 是 Graviton,和应用镜像同架构。

几个决定与它们的理由:

| 项 | 值 | 为什么 |
|---|---|---|
| Multi-AZ | 关 | 开了价格翻倍,换来的是自动故障切换。内测阶段停机半小时没有后果 |
| 存储 | 20GB gp3,自动扩到 100GB | 20GB 是最小值且远够用;自动扩容防的是「磁盘写满 → 数据库直接不可用」 |
| 加密 | 开 | 免费、无性能影响,而且**建完改不了**(要快照+恢复) |
| 公网可达 | 否 | 私有子网。这正是首次导语料需要想办法的原因 |
| 备份保留 | **1 天** | 见下 |

**备份 1 天是被迫的。** 原本设 7 天,apply 直接被拒:

```
FreeTierRestrictionError: The specified backup retention period
exceeds the maximum available to free tier customers.
```

这个账号在 **AWS 免费计划**上,它不是「免费额度」而是一种账号类型,对配置有硬限制。这条
错误顺带暴露了一个更值得处理的问题:**免费计划的额度耗尽时,AWS 的处理是暂停资源而不是
从卡里扣钱**——绑卡不等于升级成付费计划。在给内测用户之前必须确认这一点。

#### 密码:让 RDS 自己管

`manage_master_user_password = true` —— AWS 生成密码、放进 Secrets Manager、**Terraform 从
头到尾看不到它**,state 里只有一个 ARN。

代价是人要手工连库时得先去取一次。收益是[簇 E](#密钥为什么不放进-terraform) 那三条全部
白拿。

执行角色随之多一条权限,**收窄到那一个密钥的完整 ARN**——不是「能读 Secrets Manager」。
下一个出现的密钥应该需要它自己的决定,而不是搭便车。

> ⚠️ ARN 结尾有 AWS 加的随机后缀(`…-ndArXl`)。写 IAM 策略时**必须用完整 ARN**,只写到
> 名字是不生效的。从资源属性里读出来就不会错,手写很容易漏。

### 第 10 步:把服务跑起来

> 前置知识:[簇 F](#簇-f运行任务服务两层健康检查)

见 [ecs.tf](../../../infra/ecs.tf)。集群、任务定义、服务三样,加一个只为 `ecs exec` 存在的任务角色。密钥容器的声明在 [secrets.tf](../../../infra/secrets.tf)。

**规格 1 vCPU / 4GB 是故意开大的。** 唯一在册的内存数字(944MiB)来自 x86、而且是预热之前
测的,在这里只能算猜测。**排查 OOM 被杀比多付几天钱贵得多**——先跑起来,量了再砍。

**任务角色是第 6 步判断的一个补充。** 第 6 步说「应用不调 AWS API,所以不需要任务角色」,
这句在**运行应用**这件事上仍然成立。但 `ecs exec` 需要容器里的代理与 AWS 建立会话通道,
那要一个任务角色。所以它存在的唯一理由是 exec,代码注释里写明了:**exec 如果去掉,这个
角色也该去掉。**

> 这也是全篇唯一一处 `resources = ["*"]`。SSM 的四个通道动作不指向任何有 ARN 的资源,
> 没有更窄的写法。注释标了这一点,免得后来者以为是偷懒。

#### 首次启动踩到的一个坑

第一次 apply 失败:

```
InvalidParameterException: Error retrieving subnet information …
AWS was not able to validate the provided access credentials (AuthFailure)
```

**报错完全指错了方向**——凭据没有任何问题。真相是:ECS 要替你查子网,这需要一个叫
`AWSServiceRoleForECS` 的服务关联角色,而那个角色是账号第一次用 ECS 时才被创建的。
**创建它的正是这次失败的调用本身**,于是第一次必然失败、第二次必然成功。

每个 AWS 账号只会撞一次,但在一个全新账号里重建这套东西的人会再撞一次。

#### 实测的冷启动

```
03:53:23  任务创建
03:53:36  开始拉镜像        +13s
03:54:01  镜像拉完          +25s   ← 982MB
03:54:06  容器启动          +5s
03:54:20  应用就绪          +14s   ← 加载两个模型 + 各跑一次推理
─────────────────────────────────
总计 57 秒
```

**这是 arm64 Fargate 上的第一组真实数字**,取代 [ROADMAP_platform](../../roadmap/ROADMAP_platform.md)
Phase 1 那批来自不同机器的 x86 记录。25 秒拉完 982MB 说明 S3 网关端点确实在起作用——走的
是 AWS 内网,不经过 NAT。

### 第 11 步:负载均衡器——那个 URL

> 前置知识:[簇 C](#簇-c边界谁准进来)、[两层健康检查](#-健康检查有两层问的是不同的问题粘合簇-c-与簇-f)

见 [alb.tf](../../../infra/alb.tf)。三个资源:负载均衡器本体、目标组、监听器,再把服务接进目标组。

**目标类型是 `ip` 不是 `instance`** —— Fargate 任务是网卡,不是机器。

**注销延迟从默认 300 秒改成 30 秒。** 这里的请求几秒就结束,剩下的四分半会被加到每一次
部署上。

**宽限期 180 秒。** 冷启动 57 秒,不给这个窗口的话:新任务还在加载模型 → 负载均衡器判它
不健康 → ECS 换一个 → 新的在同一个点上又被判死。**一个日志里完全看不出原因的重启循环。**

**健康检查暂时指 `/health`。** 这与[上面那条规则](#-健康检查有两层问的是不同的问题粘合簇-c-与簇-f)
相反,是临时偏离:库里没有表,`/ready` 会永远 503,负载均衡器会永远不导流。代码里留了
TODO。

#### 只有 80,没有 443

443 需要证书,而证书必须签给**你自己的域名**——负载均衡器自带的 `xxx.elb.amazonaws.com`
是 AWS 的域名,签不了。

**这不只是「不够安全」,而是「跑不通」**:v1 的架构是浏览器直连本服务,而前端页面是
HTTPS 的,**浏览器会硬拦截从 HTTPS 页面发往 HTTP 接口的请求**(混合内容),连发都不发。
所以域名是接前端的硬前提,不是锦上添花。

#### 从外面实测

```
GET  /health    200   {"status":"ok"}                   96ms
GET  /ready     503   database: ok,缺表
POST /v1/chat   401   {"error":{"code":"unauthorized",…}}
```

三条各证明一件事:链路通;数据库连得上而只差数据;**鉴权在公网上真的生效**,而且错误
形状就是约定的那个契约。

> 负载均衡器的域名里那串数字是 AWS 分配的,**重建就会变**。别写进任何配置或文档。

## 命名与标签约定

**资源名**:`cssa-da-prod-<是什么>`,全小写连字符。

- 只有「每个环境各有一份」的东西,名字里才写环境。ECR 仓库就没有 `prod` 段。
- 不要把会变的东西写进名字(金额、规格、日期、人名)——AWS 里很多资源**改名等于删了重建**。

**标签**:键首字母大写,值全小写。

```
Name       = cssa-da-prod-vpc     ← AWS 定义的键,控制台靠它显示名字,必须大写 N
Project    = cssa-da              ← default_tags 自动加
ManagedBy  = terraform            ← default_tags 自动加
```

后两个写在 [providers.tf](../../../infra/providers.tf) 的 `default_tags` 里一次,**这个
provider 建的每个资源自动带上**,所以单个资源里只写 `Name`。一致性靠工具保证,不靠人。

`ManagedBy` 的实际用途:三个月后看见一个资源,它告诉你**该去控制台删还是去改 Terraform**。

> ⚠️ 标签要在 Billing 设置里手动激活成「成本分配标签」,才会出现在账单报表里。

## 成本:现在花了多少

前七步建的东西**几乎全部免费**:VPC、子网、路由表、互联网网关、S3 网关端点(它是路由
规则,不是设备)、安全组、IAM 角色都不要钱;CloudWatch 日志和 ECR 存储按量计,这个规模
下是几毛钱。

**从第 8 步开始才有按小时计费的东西。** 悉尼区的量级大致是:

| 项目 | 约每月 | 性质 |
|---|---|---|
| NAT 网关 | $45 | 睡觉时也在扣 |
| Fargate 任务(1 vCPU / 4GB) | $34 | 同上 |
| 负载均衡器 | $18 | 同上 |
| RDS(db.t4g.micro + 20GB) | $15 | 同上 |
| Elastic IP | $4 | 公网 IPv4 自 2024 年起收费 |
| **合计** | **约 $116** | **超出 100 美元的月度预算** |

(精确数字以 AWS 定价计算器为准,这里只给量级。)

**最容易砍的两处**:Fargate 规格是故意开大的,量过实际内存之后往下调能省一部分;NAT 则是
[前面那个 A/B 选择](#互联网网关-vs-nat-网关)——把容器放公有子网、给它公网 IP 能省掉 $45,
代价是防线从两层变成一层(安全组配错的那一刻就暴露,而 A 方案里还有「没有公网地址」兜着)。

> ⚠️ **这个账号在 AWS 免费计划上**,花的可能先从信用额度里扣,账单显示 0——所以那个月度
> 预算告警暂时不会响。额度消耗要去 Billing 的 Free Tier / Credits 页面单独看,**而额度
> 耗尽时免费计划的处理是暂停资源,不是从卡里扣钱**。

账号级的护栏(手点建的,不归 Terraform 管):

- `cssa-da-account-tripwire` —— 日预算 1 美元。**预期永远不响**;响了说明有没预期的东西
  在跑。它只在「预期花费≈0」的窗口里有效,开始建付费资源后应当关掉。
- `cssa-da-account-monthly` —— 月预算 100 美元,三档告警,其中**预测类那档**是唯一能提前
  反应的。
- Cost Anomaly Detection —— 比的是「和你自己的历史模式相比」,忘关一个 NAT 这类问题靠它
  发现。需要几周学习期。

> **预算告警不是支出上限。** AWS 不会因为超预算停服务,它只发邮件。真正的刹车只有
> Budget Actions(能挂拒绝策略、停实例),但它的动作太钝——停 RDS 等于自己把服务弄挂,
> 给自己挂拒绝策略可能连进去关掉烧钱的东西都做不了。**目前不配**,留到有真实用户之后
> 再考虑「超 150% 时禁止新建资源」这类温和动作。

## 演练:destroy 与重建

整个栈仍然可以删光重建,**这是刻意保持的性质**:

```
白天  terraform apply      建出来,折腾
晚上  terraform destroy    全删,停止计费
明天  terraform apply      半小时后原样回来
```

手点做不到这件事——你不确定自己是不是全删干净了(尤其 NAT,忘删一个就一直烧)。

**重建的实际代价**(截至第 11 步,数据库还是空的):

| | 时间 |
|---|---|
| `terraform apply` | ~15 分钟(RDS 5–10、ALB 2–4、NAT 2) |
| 重新 `docker push` | ~10 分钟(仓库被一起删了,982MB 全量重传) |
| 重新灌两个密钥 | 2 条命令 |

**没有一步需要重新思考或重新写代码。**

> ⚠️ **一个会卡住重建的坑**:两个应用密钥设了 `recovery_window_in_days = 7`,删除后进入
> 七天恢复期,**期间名字被占着**,于是重建时 Terraform 建同名密钥会失败。要么先
> `delete-secret --force-delete-without-recovery` 彻底删掉,要么 `restore-secret` 把旧的
> 捞回来(那样连值都不用重新灌)。

**这个性质在语料导入之后就会打折**:那时 destroy 会连着丢掉导入成果,重建要多花十几分钟
重导。真有用户之后更要把 `deletion_protection`、`skip_final_snapshot`、ECR 的
`force_delete` 三个开关翻过来——代码里都留了 TODO。

## 还没做的

按优先级:

| 事项 | 为什么重要 | 什么时候 |
|---|---|---|
| **建表 + 导语料** | `/ready` 现在是 503,而负载均衡器暂时看的是 `/health`——**等于有一个没人查的就绪检查** | 第 12 步,下一步 |
| **健康检查切回 `/ready`** | 不切的话,流量会被导给一个连不上数据库的容器 | 第 12 步之后立刻 |
| **域名 + ACM 证书** | 没有它就只能 HTTP,而**浏览器会硬拦截 HTTPS 页面发往 HTTP 的请求**;`ALLOWED_ORIGINS` 也等它 | 接前端之前 |
| **确认账号计划** | 免费计划的额度耗尽时是**暂停资源**而不是出账单 | 给内测用户之前 |
| **砍 Fargate 规格** | 现在超预算 $16,而 4GB 是故意开大的 | 量过内存之后 |
| **应用不该用主用户连库** | 见下 | v1 期间 |
| root MFA | 账号最高权限目前只靠一个密码 | 越早越好 |
| 收窄 Terraform 身份的权限 | 目前是 `AdministratorAccess` 的长期密钥,正路是 IAM Identity Center 的临时凭据 | Phase 4 做 CI 时一并处理 |

### 两笔明确欠下的债

**应用和迁移用的是同一个数据库身份。** 容器现在拿的是 RDS 主用户 `cssa_admin`。这让
`CREATE EXTENSION vector` 能跑通(普通用户建不了扩展),但它违反了本项目自己写下的规矩
——[ROADMAP_platform 第 20 项](../../roadmap/ROADMAP_platform.md)说「跑 migration 的身份和
跑应用的身份不该是同一个」。正确的形状是:迁移用主用户,应用用一个只有读写权限的普通
用户。

**Dockerfile 的模型下载层依赖过宽。** builder 阶段为了拿到模型清单 `COPY` 了整个
`app/core/config/`,于是**任何对 `settings.py` 的改动都会让 600MB 的模型层失效**、重新
下载、重新推送。实测代价:一次本该 5MB 的推送变成了 600MB、十分钟。它只需要
`rag-config.yaml` 一个文件。

### 一句话的现状

**公网上有一个地址,后面跑着这个服务,连着一个空数据库。** 缺的是数据,以及把就绪检查
接回它该在的位置。
