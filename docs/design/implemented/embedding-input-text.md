# 嵌入输入文本:标题只编码一次 —— 设计说明

向量检索里,一篇文章只有开头一小段文字真正进了向量。这次改动把那一小段里**重复的
标题**去掉,把位置还给正文。对应 issue #117 的第 1 步。

> **状态:设计已确认,代码未写。** 本文先于代码提交,供评审设计;实现完成后,
> [测试策略](#测试策略)和文中的数字会按实际结果更新。

本文只讲第 1 步。#117 的后两步 ——「一篇一向量 + 清理文本」与切块的对比测量、选定
方案的落地 —— 还没有做,见[已知边界](#已知边界)。

## 背景

线上的嵌入模型 `paraphrase-multilingual-MiniLM-L12-v2` 一次最多读 128 个 token,
超出的部分直接丢掉。知识库里一行的向量,是用「`question_text` + 空行 + `content`」
这段文本算出来的。而微信文章的 `question_text` 就是标题,`content` 又以标题开头。
于是模型读到的是:

```
标题   标题   正文开头……          ← 128 个 token 的窗口
└──┘  └──┘  └─────────┘
 22    22       82                 ← 各占多少 token(中位数,可用的共 126 个)
```

对仓库里的 2312 行,用线上同一个 tokenizer 实测:

- 2197 行(95%)超出窗口,被截断
- 标题中位数 31 个字、22 个 token,占可用窗口的 17%
- 所以典型的一行里,窗口的六分之一花在把标题再读一遍上

窗口小这件事本身有多伤,是 PR #108 做 reranker 选型时顺带量出来的:真实风格的
中文提问,正确文章能进入向量检索前 30 名的只有 36.8%,而重排只能在这 30 条里挑。
**标题重复不是这个问题的全部,只是其中最便宜的一块**:它不解决「一篇文章只有开头
被编码」,只是把被重复占掉的那部分窗口还回去。

## 基础知识

### 一、嵌入窗口:模型只读开头一小段

> 这一簇讲:为什么区区三十来个字的重复值得专门改一次。

**从哪来。** 向量检索要在提问到来之前,就把每篇文档变成一个向量存好。做这件事的
模型有输入长度上限:它训练时每段文本最多 128 个 token,使用时超出的部分被直接截掉。
128 个 token 对中文大约是 160 个字,而这批文章正文的中位数是 1900 字。

所以一行的向量代表的不是整篇文章,而是**它的开头**。窗口之外的内容不是「权重低」,
是从来没有被模型读到过。一个问题的答案如果在文章第 600 个字,向量里没有它的任何
痕迹。

**看一篇真实的文章。** 标题 32 个字,正文 2225 个字:

```
标题:【CSSA学术】周六『雅拉讲堂』26S1第三期：蛋白质专题讲座！

改之前,窗口里的正文到这里为止(124 个字):
  ……墨尔本大学Arts West第三期 详细信息本专题将带▌

改之后(161 个字):
  ……详细信息本专题将带你从“看见蛋白质”出发，走进一个不断变化的分子世界，
  并进一步揭示它们如何在▌
```

多读到的那 37 个字,正好是这场讲座讲什么。

**全量实测。** 窗口里的正文字数:

| | 改之前 | 改之后 |
|---|---|---|
| 中位数 | 129 字 | 162 字(多四分之一) |
| 平均 | 131 字 | 165 字 |

逐行看:2197 行变多,47 行不变(全文本来就装得下),**没有一行变少**。这就是 issue
里「收益没量过,但不可能为负」的依据 —— 删掉的是一份副本,原件还在。

**为什么不干脆把窗口调大。** 把 `max_seq_length` 从 128 改成 512 是最顺手的想法,
PR #108 的评测试过:前 30 名的命中率从 36.8% 掉到 7.4%。这个模型只在 128 以内训练过,
而且它把所有 token 的向量取平均来代表整段文本,文本越长,平均值越被稀释成一篇
「泛泛的中文文章」。记在这里,是为了没有人再试一次。

### 二、一行数据有三个读者

> 这一簇讲:标题该从哪里去掉,为什么不是「删掉就完了」。

**从哪来。** 这张表最初是按「一个问题 + 一份答案」设计的:`question_text` 存问题,
`content` 存答案,向量由两者拼起来算。微信文章没有「问题」,转换阶段就把标题填进了
`question_text`。同时为了让正文自带标题,转换阶段还保证 `content` 以标题开头,没有
就补一个。两处各自说得通,合在一起,标题在嵌入文本里就出现了两次。

**最容易想到的做法有一个坑。** 把标题从 `content` 里删掉,嵌入那边就对了,因为它
自己会把 `question_text` 拼在前面。但重排模型读的是 `content` 本身,不读
`question_text`。标题一删,它就再也看不到标题了。标题是一篇文章最浓缩的一句话,
对重排是有用的信息;而且在重排这边标题本来就只出现一次,删掉是纯损失。

**三种做法。**

| 做法 | ③ 嵌入读到 | ④ 重排读到 | 重导后向量会更新吗 |
|---|---|---|---|
| **A. 转换阶段去掉,重排自己拼回(采用)** | 标题一次 | 标题一次,等效于今天 | 会 |
| B. 只在转换阶段去掉 | 标题一次 | **没有标题** | 会 |
| C. `content` 不动,只在算向量时跳过重复 | 标题一次 | 不变 | **不会**(见[下一簇](#三重导为什么会真的刷新向量)) |

B 和 C 各有一个**不报错、只是悄悄变差**的失败方式:B 让重排的输入变了而没有人量过,
C 让重导不生效。A 的代价是明面上的:

- 要动请求路径上的一处代码(重排)
- `/v1/chat` 返回的 `sources[].article.text` 不再以标题开头(标题仍在
  `sources[].article.questions[0]`)

顺带的好处:⑤ 生成器拿到的每一条资料里,`A:` 不再把 `Q:` 里的标题重复一遍。

「标题」和「正文」分开存,也是之后做切块时需要的形状:切的是正文,每一块再各自带上
标题。

### 三、重导为什么会真的刷新向量

> 这一簇讲:转换阶段改了之后,库里的旧向量是怎么被换掉的,以及做法 C 为什么换不掉。

**从哪来。** 导入必须能重复执行,跑两遍不能多出一倍的行。所以每一行有一个唯一键
`(link, question_text)`,导入用的是「有就更新,没有就插入」。再进一步,同一份语料
导第二遍应该什么都不改,这样「改动了 0 行」才能当作「库里已经是这份语料」的证据。
于是更新带了一个条件:只有某个字段真的变了才更新。

```sql
INSERT INTO knowledge_base (...) VALUES (...)
ON CONFLICT (link, question_text) DO UPDATE SET
    content = EXCLUDED.content, embedding = EXCLUDED.embedding, ...
WHERE knowledge_base.content         IS DISTINCT FROM EXCLUDED.content
   OR knowledge_base.embedding_model IS DISTINCT FROM EXCLUDED.embedding_model
   OR ...                 -- 其余元数据字段。注意:比较里没有 embedding 本身
```

由此得出三件事:

1. **采用的做法下,重导即生效。** 每一行的 `content` 都变了(开头的标题没了),所以
   每一行都会被更新,向量跟着重算。
2. **做法 C 下,重导什么都不会发生。** `content` 没变,模型没变,条件里没有一项为真,
   一行都不更新。旧向量留在库里,导入照常报告成功。
3. **导入不删行。** 这次被丢弃的 68 行如果已经在库里,重导之后它们还在,要另外处理
   (见[上线步骤](#上线步骤))。

**为什么不顺手把 `question_text` 也清洗一下。** 有些标题里带着零宽字符。但
`question_text` 是唯一键的一半:改了它,重导时旧行匹配不上,结果是**新插入一行、
旧行原样留下**,行数悄悄变多。所以标题原样保留。

### 四、新代码遇到旧数据

> 这一簇把前两簇粘起来:代码和数据分两次上线,中间那段时间不能出错。

这次改动的两半不是同时生效的:代码随镜像部署;数据要等有人重跑转换、重导。中间
一定有一段时间是「新代码 + 旧数据」。

如果重排的新代码不管三七二十一都给正文拼上标题,那段时间里它读到的就是「标题
标题 正文」—— 把刚从嵌入那边修掉的问题,搬到了重排这边。

所以重排在拼标题之前先看一眼:正文如果已经以标题开头(旧数据的形状),就原样使用。

| | 旧数据(正文带标题) | 新数据(正文不带标题) |
|---|---|---|
| 旧代码 | 今天的行为 | 重排读不到标题;不报错,排序可能变差 |
| **新代码** | **重排读到的文本与今天逐字相同** | 标题一次 |

正常的上线顺序是先代码、后数据,走的是左下 → 右下。右上那一格只在一种情况下出现:
重导之后又把镜像回滚到了旧版本。

## 实现

### 1. 转换阶段:去掉正文开头的标题

> 前置基础:[一](#一嵌入窗口模型只读开头一小段)、[二](#二一行数据有三个读者)

[wechat_articles.py](../../../pipelines/transform/wechat_articles.py) 清洗完正文之后,
从开头去掉标题,直到开头不再是标题为止。

「开头是不是标题」不能逐字比较。标题来自抓取到的 `title` 字段,正文开头那一份则
经过了 Markdown 转换和清洗,2312 行里有 26 行两者差了一点:

| 差在哪 | 行数 | 例子 |
|---|---|---|
| 标题里有零宽字符或连续空格,清洗后的正文里没有 | 15 | 标题 `【CSSA转发】​​ 两只国宝…`(中间有两个看不见的零宽字符) |
| 正文里的方括号、下划线被 Markdown 转义了 | 11 | 标题 `[CSSA活动反馈] 电竞大赛…`,正文 `\[CSSA活动反馈\] 电竞大赛…` |

所以比较时忽略空白、零宽字符、反斜杠和星号(星号在清洗时会被整体删掉),只看剩下的
字符是不是一一对得上。标题通常有三十来个字,这个宽松程度不会把正文误认成标题。

去掉的份数:2286 行一份,26 行两份(正文开头本来就把标题写了两遍;这 26 行和上表那
26 行不是同一批,只是数字碰巧相同)。改之后,没有任何一行的正文以自己的标题开头。

改之前的逻辑正好相反:正文不以标题开头时,转换阶段会**补**一个 `# 标题`。上面那
26 行因为逐字比不上,被补了一份,它们的嵌入文本里标题其实出现了三次。

### 2. 质量门槛只数正文

> 前置基础:[一](#一嵌入窗口模型只读开头一小段)

转换阶段原有一条规则:清洗后有效字符(汉字、字母、数字)少于 30 个的文章丢弃,注释
写的是「正文所剩无几,直接抛弃」。但数的时候标题也算在里面,所以一篇只有标题的文章,
只要标题够长就能过关。

标题去掉之后,这类文章显形了:68 行,都是只有图片的转发,多数是招聘海报。

```
标题:【CSSA招聘】隆基股份2022届海外校园招聘岗位OFFER 等您接！
正文:(空)                                     ← 这样的有 18 行

标题:【CSSA招聘】为青春，奔赴梦想之旅 | 携程集团2022海外秋季校园招聘正在进行时
正文:携程 携程 [阅读原文](javascript:;)        ← 另外 50 行是这类不足 30 字的样板
```

门槛改成只数正文,这 68 行被丢弃。语料从 2312 行变成 **2244 行**,转换报告里的
`dropped_count` 从 234 变成 302。

**为什么丢而不是留。** 留下的话,正文要么是空的(过不了导入校验),要么只能再拿标题
顶上,回到「标题 + 标题」。而且检索到这样一行,生成器拿到的只有一个标题。

### 3. 重排自己拼标题

> 前置基础:[二](#二一行数据有三个读者)、[四](#四新代码遇到旧数据)

[cross_encoder_reranker.py](../../../app/services/rag/reranker/cross_encoder_reranker.py)
交给重排模型的文本,从「正文」改成「标题 + 空行 + 正文」。两种情况例外:正文已经以
标题开头的行(重导之前的旧数据)原样使用;没有标题的行只用正文。

对新数据,这和改之前重排读到的文本只差一处:标题和正文之间多了一个空行(以前两者
是连着的)。

### 4. 嵌入这一侧不用改

> 前置基础:[二](#二一行数据有三个读者)、[三](#三重导为什么会真的刷新向量)

[knowledge_base_text.py](../../../pipelines/embedding/knowledge_base_text.py) 本来就是
「`question_text` + 空行 + `content`」。`content` 不再带标题之后,它拼出来的自然只有
一份标题。

## 上线步骤

顺序按[基础知识四](#四新代码遇到旧数据):先代码,后数据。

1. **部署代码。** 此时库里还是旧数据,线上行为不变。
2. **重跑转换,生成新语料**:`python -m pipelines transform-wechat`,并把产物放到导入
   读取的位置(生产环境是 S3 数据桶)。
3. **重导**:`python -m pipelines import-knowledge-base --reset-checkpoint`。每一行的
   `content` 都变了,所以每一行都会更新、向量重算。
4. **处理被丢弃的 68 行。** 库是新建的(比如整个栈重建过)就没有这一步。库是沿用的,
   这 68 行还在,而且是唯一还保持旧形状的行,用下面的查询可以数出来:

   ```sql
   SELECT count(*) FROM knowledge_base
   WHERE starts_with(content, question_text)
      OR starts_with(content, '# ' || question_text);
   ```

   ⚠️ **只能在重导之后跑。** 重导之前这个查询命中的是**全表**。先数:结果是 68,才把
   `SELECT count(*)` 换成 `DELETE` 再跑一次;结果是 2312,说明重导还没有发生。
5. **抽查**(#117 的第一条完成标准):上面的 `SELECT` 返回 **0**。

## 已知边界

- **收益没有量过。** 只知道不为负。量它需要问题集和离线评测工具,那是 #117 的第 2 步
- **窗口之外的正文仍然没有被编码。** 这次只是让窗口多装了约 33 个字,2193 行(98%)
  依然被截断
- **正文开头的样板没有清。** 110 行以「以下文章来源于……」的转载声明开头,它们仍然
  占着窗口。清不清、清了能换来多少,同样属于第 2 步
- **正文里残留的 Markdown 转义没有清**(`\[`、`\_`)。它们只在比较标题时被忽略
- **仓库里的 `data/wechat_articles_processed.json` 没有重新生成**,它仍是改动前的形状
  (2312 行,正文带标题)。生产导入用的是数据桶里的那一份,由上线步骤第 2 步重新生成
