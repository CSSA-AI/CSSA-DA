## 背景

线上 reranker 是 `cross-encoder/ms-marco-MiniLM-L12-v2`:英文 WordPiece 词表,只在「英文
query → 英文段落」上训练过。而用户用中文提问,知识库里既有中文公众号文章,也即将有英文的
墨大 handbook 页面。[ROADMAP_rag.md 0.4](../../roadmap/ROADMAP_rag.md#04-reranker-的任务类型是错的)
早就从原理上判断它不合适;issue #90 又补了一条约束:**延迟必须作为选型判据**,因为
reranker 是每个请求都要付的 CPU 成本,而 2 vCPU 下它已经是整条链路里最慢的一段。

这次要回答三个问题:ms-marco 到底有多不合适;替代品里谁最好;「最好」要花多少 CPU。

## 先看全局:reranker 在一次请求里的位置

```
用户提问 ──► embedding 模型编码 ──► pgvector 取最相近的 30 条  (retriever.top_k)
                                          │
                                          ▼
                              cross-encoder 给 30 条逐条打分      ◄── 本文换掉的就是这一步
                                          │
                                          ▼
                              取分数最高的 5 条                  (reranker.top_k)
                                          │
                                          ▼
                              交给 OpenAI 生成回答
```

两个事实决定了后面怎么评估:

1. **reranker 只能在 30 条候选里挑。** 正确文档没进这 30 条,reranker 再好也救不回来——
   这就是[基础三](#三为什么要看端到端而不只看-reranker)要讲的「端到端」。
2. **真正进入回答的是前 5 条。** 所以 R@5(正确文档排进前 5)比 R@1 更贴近线上效果,
   两个都报。

## 基础知识

### 一、为什么 cross-encoder 贵,而且贵在哪

> **这一簇讲什么**:延迟到底由哪几个数决定,从而知道哪些旋钮能拧。

检索用的 embedding 模型(bi-encoder)把文档**提前**编码好存进数据库,请求时只编码一次问题。
cross-encoder 做不到这一点:它必须把「问题 + 候选文档」拼成一段一起过模型,才能看到两者
之间逐词的对应关系——准,但**每个请求要对 30 个候选各做一次完整前向**。

所以一次重排的成本近似是:

```
候选数(30) × 截断后的 token 数 × 每个 token 的计算量(由层数和宽度决定)
```

三个数都能拧:候选数是 `retriever.top_k`;token 数是截断长度 `max_length`;每 token
计算量由模型尺寸决定。实测印证了这个公式:同一模型,截断从 512 降到 256,延迟几乎正好减半;
`bge-reranker-base`(12 层 × 768 宽)每 token 约是 MiniLM(12 层 × 384 宽)的 3 倍,
`bge-reranker-v2-m3`(24 层 × 1024 宽)约 11 倍。

**一个容易漏的点**:截断长度默认跟着模型的 tokenizer 走。MiniLM 系是 512,但长上下文的
reranker(比如 v2-m3)默认 8192。**如果不在配置里写死,换个模型就可能让每次请求的计算量
悄悄涨一个数量级,而配置文件没有任何改动**——所以这次顺带把它钉进了 `rag-config.yaml`。

另一个值得知道的点:多语言模型体积大,主要是因为词表大(25 万词 vs 英文的 3 万)。
词表是查表操作,几乎不花算力。这就是 `mmarco`(470MB)和 `ms-marco`(129MB)体积差 3.6 倍、
延迟却几乎一样的原因——**体积和延迟是两根独立的轴**,这也是 issue 坚持把延迟单列为判据的原因。

### 二、为什么「自己找自己」的测试会骗人

> **这一簇讲什么**:为什么第一版评估的结论是错的,以及怎么修。

最省事的评估是:拿一篇文章的标题当问题,看模型能不能从一堆文章里把这篇排到第一。本次
第一版就是这么做的,结果 ms-marco 得了 95%,和多语言模型打平——看起来它根本没问题。

问题在于**标题和正文共享大量原词**:地名、学校名、数字、专有名词。一个完全不懂中文的模型,
光凭「这几个字符在两边都出现了」就能蒙对。真实用户不会照着标题提问,他们会说「我这边
还没收到短信通知,是得等下一批才发吗?」。

修法是两件事一起做:

- **用真实风格的提问**:让本地 LLM 读文档,写学生口吻的问题,并过滤掉抄了标题的
- **用真实的候选池**:不是随机抽 29 篇无关文章当干扰项(一眼就能排除),而是用线上同一个
  embedding 模型取最相近的 30 条——这些干扰项主题相近,才考得出区分能力

然后**保留**「标题当查询」作为一组对照(下文的 QT)。它的作用不是衡量效果,而是**揭示一个
模型靠不靠字面匹配**:如果它在 QT 上很高、在真实提问上很低,说明它只会字面匹配。
ms-marco 正是这样:QT 82.7%,真实中文提问 7.4%。

### 三、为什么要看端到端,而不只看 reranker

> **这一簇讲什么**:reranker 的上限由谁决定。

为了单独衡量 reranker,评估时如果正确文档不在检索器的 top-30 里,会把它强行塞进候选池。
这回答的是「给它机会,它能不能挑出来」。

但线上没有人会帮它塞。所以同时报一个**端到端命中率**:正确文档**既**被检索器召回进 top-30,
**又**被 reranker 排进前 5。两者之差揭示的是瓶颈在哪一段——这次的答案是**检索器**。

## 评估方法

### 语料

6578 篇去重后的文档,混合了知识库的真实形态:

| 来源 | 语言 | 篇数 | 说明 |
|---|---|---|---|
| `data/current/wechat_articles_processed.json` | 中文 | 正文 > 300 字的全部 | 线上知识库现有的数据 |
| `data/unimelb_subjects_2026.json` | **英文** | 1338 | 概述 > 200 字的课程页,测跨语言 |
| `data/myoffer.json`、`data/aoji.json` | 中文 | 其余 | 同领域留学文章,作为主题相近的干扰项 |

同一篇文章被多个公众号转发时,内容相同却分属不同条目,会让「正确答案」被判成错。按正文前
300 个非空白字符的指纹去重,只保留第一份。

### 查询集(五组分开记录,从不合成平均分)

| 代号 | 查询 → 目标 | 条数 | 来源 |
|---|---|---|---|
| **QP-zh** | 中文提问 → 中文文章正文 | 190 | 本地 LLM 生成 |
| **QP-xling** | 中文提问 → **英文** handbook 页面 | 232 | 本地 LLM 生成 |
| **QP-aoji** | 已有的 GPT 问题 → 文章正文 | 72 | `data/aoji.json` 里现成的 `question` 字段(每篇 3 个,不是本次生成的) |
| **QQ** | 中文提问 → 知识库的 `question_text` | 190 | 同 QP-zh 的问题;公众号行的 `question_text` 就是文章标题 |
| **QT** | 文章标题 → 文章正文 | 150 | **字面重合对照组**,不代表真实用户 |

生成方式:`Qwen/Qwen3-4B-Instruct-2507` 在本机 RTX 5080 上运行,随机抽 120 篇公众号文章和
120 个 handbook 课程,每篇要求写 2 个「在澳洲留学的中国学生会在聊天框里问」的口语化问题,
不许抄标题、不许写课程代码。抄了标题(与标题有 8 字以上连续重合)或写了课程代码的一律丢弃,
实际丢弃 0 条;3 篇输出无法解析被丢弃。QP-zh 从生成的 215 条变成 190 条,是因为其中一些问题的
源文章在去重时被判为转发副本。

### 候选池

完全按线上方式构造:用线上钉死的 embedding 模型
(`paraphrase-multilingual-MiniLM-L12-v2@e8f8c21`)编码 `标题\n\n正文`(与
[`knowledge_base_text.py`](../../../pipelines/embedding/knowledge_base_text.py) 一致),问题单独编码,
余弦相似度取前 30。正确文档不在前 30 时强行替换进去,并单独记录这一事实用于端到端指标。
QQ 的候选池只在中文文档的 `question_text` 上检索。候选池构建一次后冻结,所有模型、所有截断长度
比的是**完全相同的题**。

### 打分与统计

- 质量打分在 GPU 上跑(`torch 2.12.1+cu129`,`sentence-transformers 5.6.0`,`transformers 5.12.1`,
  与项目锁定版本一致)。打分结果不依赖硬件,所以用 GPU 加速是合法的;延迟另外在 CPU 上测
- 所有差异用**配对 bootstrap**(同一批题上两模型的差,重采样 5000 次)给 95% 置信区间。
  区间跨过 0 就不算有差异

### 延迟

用本次新增的 [`ops/benchmark_reranker.py`](../../../ops/benchmark_reranker.py) 在 CPU 上测:
候选池 30 条真实文章,线程数显式钉在 2 和 4,每组 20 次请求(v2-m3 太慢,12 次),先热身 2 次,
报 p50 / p95。硬件:x86 AMD Ryzen 7 9800X3D,Windows,`torch 2.12.1+cpu`。p95 和 p50 相差都在 2% 以内。

## 决策

### 判断规则

**在不增加 reranker CPU 延迟的前提下(以原线上 ms-marco @512 为上限),选真实查询集上质量
最好的;配对置信区间分不出差异时,选更快的。**

为什么是这条规则:Fargate task 规格还没定,而 [ROADMAP_rag.md 0.3](../../roadmap/ROADMAP_rag.md#03-top_k-的结构性问题)
已经记录「2 vCPU 下 `top_k=30` 线上不可用」——现在的延迟已经是约束本身。一个更慢的模型会让
这个约束在平台线做决定之前变得更糟。

**必须说明**:这条规则是在看到数据之后写下的,而不是之前。为了不让它变成「拿结果凑判据」,
上面给出了完整的质量-延迟表,换一个延迟预算的人可以直接在表上重新读出结论。

### 按规则逐个排除

| 候选 | 结论 | 依据 |
|---|---|---|
| **mmarco @256** | ✅ **选中** | 延迟 1666ms,只有原线上的 45%;真实查询集上相对 ms-marco:QP-zh R@1 **+40.5** [+33.7, +47.9],QP-xling **+44.4** [+37.9, +50.9],QP-aoji **+22.2** [+12.5, +33.3],QQ **+18.4** [+11.6, +25.3];对照组 QT +6.0 [−1.3, +14.0],**没有退化** |
| mmarco @512 | ❌ 慢一倍、没有更好 | 相对 @256:QP-zh R@1 +4.2 [−2.1, +10.5]、QP-xling +1.7 [−3.4, +6.9]、QP-aoji −5.6 [−15.3, +2.8],**都分不出差异**;QP-zh R@5 +6.3 [+0.0, +12.6] 恰好压在边界上;对照组 QT −20.7 [−28.7, −13.3] **显著更差**(甚至比 ms-marco 还差 14.7 个点)。端到端只多 1.1 个点,却多花 2.2 倍 CPU |
| mmarco @128 | ❌ 质量不够 | 相对 @256:QP-zh −10.0、QP-xling −13.4、QP-aoji −19.4,区间都不含 0 |
| **bge-reranker-v2-m3** | ❌ **因延迟被拒** | 各组质量最好,但 2 线程下 9.3–39.9s,是原线上的 2.5–11 倍;权重 2.3GB。即使在最短的 128 截断下也超出预算,而且那时质量已经不如选中方案(QP-zh −6.8 [−13.7, −0.5]) |
| **bge-reranker-base** | ❌ **因延迟被拒** | @256 5.5s、@512 11.8s,超出预算。@128 虽然 2.7s 在预算内,但比选中方案**又慢又差**:QP-zh −8.9 [−15.3, −2.6],QP-xling −19.4 [−25.9, −12.9] |
| gte-multilingual-reranker-base | ❌ 无法运行 | 需要 `trust_remote_code`,且建模代码不在它自己的仓库、而是从 `Alibaba-NLP/new-impl` 拉取——钉住 gte 的 revision 钉不住实际执行的代码。实测在项目锁定的 `transformers 5.12.1` 下,连 200 字的短句都报 `IndexError`(RoPE 的 `position_ids` 查表越界,索引是未初始化的垃圾值),CPU、GPU 都一样 |
| jina-reranker-v2-base-multilingual | ❌ 无法运行 | 需要 `trust_remote_code`,远程代码依赖项目里没有的 `einops`;补装之后仍报 `ImportError: cannot import name 'create_position_ids_from_input_ids'`——它依赖的函数在 `transformers 5.x` 里已被删除。许可证 `cc-by-nc-4.0`,本身也不适合 |

**issue #90 要求写明有没有候选因延迟被拒:有,两个 BGE 模型都是。**

### 升级路径(给平台线的输入)

- **如果平台线给到 4 vCPU**:`bge-reranker-base @256` 在 4 线程下是 3771ms,和原线上 2 线程的
  成本相当。它在 QP-aoji(长而复杂的问题)上显著更好(R@1 +20.8 [+9.7, +31.9]),但在跨语言
  上 R@5 显著更差(−11.2 [−16.8, −5.6])。**不是无条件的升级**,换之前要重测
- **更大的 reranker 端到端收益有限**:在检索器召回 37% 的现状下,v2-m3 @512 的端到端只比选中
  方案多 3.7 个点。下一步的钱应该花在**召回**上(分块、混合检索、换 embedding 模型),而不是
  更大的 reranker

### 副作用:分数尺度变了

两个模型输出的都是原始 logit,但分布不同。已检查应用代码,**没有任何地方拿 rerank 分数做阈值
判断**;但有两处会看到数值变化:

- 生成器把 `检索分数: {score}` 写进给 OpenAI 的上下文([context_formatter.py](../../../app/services/rag/generator/context_formatter.py))
- `/v1/chat` 响应的 `sources[].score` 和 `chat_interactions.retrieved[].score`

换模型前后的历史分数**不能直接比较**。`chat_interactions.config` 里的配置指纹能区分两者——
本次也把 `reranker_max_length` 加进了指纹,否则同一个模型换了截断长度,两批记录在指纹上无法区分。

### 镜像实测:`docker build` + `--network none`

同一台机器上把 `origin/main` 和本分支各构建一次 `Dockerfile.api`(构建上下文只含 git 跟踪的文件),
容器不给网络、不给数据库,各启动 3 次:

| | main(ms-marco) | 本分支(mmarco @256) | 变化 |
|---|---|---|---|
| `--network none` 下模型加载 | `/ready` 的 `models` 全部 `ready` | 同左 | 离线加载成立 |
| `/models`(`du -sm`) | embedding 477 + reranker 129 MiB | 477 + 471 MiB | **+342 MiB** |
| 镜像压缩后大小(推送 / 拉取的量) | 1.04 GB | 1.32 GB | +283 MB(+27%) |
| 容器文件系统解压后 | 2293 MiB | 2635 MiB | +342 MiB |
| `docker image ls`(本地占用,与 Phase 1 的 3.35GB 同口径) | 3.45 GB | 4.09 GB | +0.64 GB |
| 冷启动到 `/health`(3 次) | 5.6 / 5.1 / 5.6 s | 6.9 / 6.2 / 6.1 s | 中位数 +0.6 s |
| 空闲内存(`docker stats`) | 960 MiB | 1064 MiB | +104 MiB |

`/ready` 报 `not_ready` 是因为容器里故意没配数据库,`reason` 是 `DATABASE_URL is not configured`,
与模型无关。冷启动包含模型预热;Dockerfile 的 `HEALTHCHECK` 给了 60 秒的 start-period,余量充足。

空闲内存只涨了 104 MiB、远小于权重多出的 342 MiB,是因为 safetensors 以文件映射方式加载,
`docker stats` 不把可回收的文件缓存算进去。**给 task 定内存时应该按保守值估:再加上权重差,
约 1.3 GiB。**

**会不会把 Fargate task 推到更大的档位**:不会,前提是 task 至少 1 vCPU。Fargate 的内存档位跟着
vCPU 走——1 vCPU 起步就是 2GB,2 vCPU 起步 4GB——保守估的 1.3 GiB 在两者下都有余量。唯一受影响的
是 0.5 vCPU / 1GB 这一档,而原模型在那一档空闲就已经占到 960 MiB,本来就放不下;而且 reranker
单段在 2 线程下就要约 1.6 秒,把这个服务放到 1 vCPU 以下本身就不现实(这是根据本次测量的推断,
task 规格仍由平台线决定)。峰值内存(推理时)本次没有测。

## 已知局限与未完成

**评估本身的局限**

- **问题是 LLM 生成的,不是真实用户写的。** 它们比真实查询更「可回答」,每题只有一个标注的正确
  文档(其他同样相关的文档会被算作错),所以**绝对值偏低、只适合模型之间比较**
- 问题是 LLM 读了文档前 1500–2000 字写的,可能涉及 256 token 之后的内容。这个偏差**有利于长截断**,
  而 256 仍然与 512 打平,所以对本次选择来说是保守的
- 评估语料 6578 篇,比线上现有的 2312 行大,线上的检索器召回可能略高
- 质量评估脚本和生成的问题集**没有随本次提交入库**:评估工具属于 Phase 5 的规划范围
  ([eval-experiments.md](../planned/eval-experiments.md)),以什么形态入库应该在那里决定。
  延迟基准工具已经入库

**本次没有处理的相关遗留**

- [`train_lora.py`](../../../app/services/rag/reranker/train_lora.py) 的基座模型仍写死为
  `ms-marco-MiniLM-L12-v2`。**不要**把按它训出的 adapter 填进 `reranker.adapter_path`:两个模型词表
  不同(3 万 vs 25 万),加载会失败。这个脚本本身在 `transformers 5.x` 下也无法运行
  (`from transformers import AdamW` 已被移除),需要单独修

**issue #90 仍未完成的部分**

- ❌ **arm64 上的延迟绝对值。** 本次在 x86 上测。选中模型与原模型是**同一个编码器形状**,
  而截断 token 数减半,计算量严格更少——「新模型比旧模型快」这个相对结论不会因为 NEON 与
  AVX-512 的差异而翻转。但 issue 要求的 arm64 数字本身仍需在 Graviton(或至少 Apple Silicon)
  上跑一次:`python ops/benchmark_reranker.py --threads 2 --threads 4`
