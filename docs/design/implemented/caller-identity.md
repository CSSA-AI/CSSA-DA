## 背景

改这件事之前,鉴权函数的返回类型是 `None`。它检查 `X-API-Key` 对不对,对就放行、不对
就 401 —— **放行之后什么都不说**,尽管它在验证的过程中明明已经知道调用方是谁。

于是两条需要鉴权的路由只能把它丢掉,写成 `_: Annotated[None, Depends(...)]`。那个下
划线是 Python 里「这个值我不要」的写法,而这里的实情是**根本没有值可要**。

限流则完全是另一条线:它在自己的模块里,从请求上又翻了一遍客户端地址,和鉴权毫无关系。

**现在这不是缺陷。** v1 只有一把共享 key,所有调用方长得一模一样,「是谁」这个问题没有
有意义的答案。这一项是买期权,不是修 bug。

但 v2 会有三个地方**同时**需要这个答案:

| 谁要 | 要来干什么 |
|---|---|
| 限流 | 按谁计数 |
| `chat_interactions.user_id` | 这条问答记在谁头上 |
| 结构化日志的 `auth_path` | 这个请求走的是 key 还是 token |

信息在鉴权里被验证完就扔掉,这三处就只能各自再去解析一遍 header 或解一遍 token ——
**三份解析逻辑、三个出错的机会**,而且以后改鉴权方式要同时改三处,必然有一天漏掉一处。
那才是真正意义上的「两套鉴权」。

目标:**让「调用方是谁」在一个地方被决定一次,其他地方读结论。** 现在做成本是零(纯
重构,不改任何行为);等 v2 做,就得在三个地方同时动。

## 先看全局:一个 `/v1/chat` 请求经过了什么

整份文档的所有结论都挂在这条链路上:

```
HTTP 请求进来
  │
  ├── 中间件(请求 id、安全响应头、CORS)
  │
  ├── FastAPI 解析依赖 ───────────────────────────────────────┐
  │     require_caller                                         │
  │       ① 验证 X-API-Key      不对 → 401,到此为止           │
  │       ② 算出 Principal      「这次的调用方是谁」            │
  │       ③ 写进 request.state   ← 给够不着依赖的代码留个便签  │
  │       ④ return              ← 交给路由函数                 │
  │                                                             │
  ├── slowapi 的限流检查 ─────────────────────────────────────┤
  │     读 request.state 里的便签,拿到限流 key                 │
  │       全站层(在外)   超了 → 429                           │
  │       per-IP 层(在内) 超了 → 429                          │
  │                                                             │
  ├── 路由函数体 chat() ──────────────────────────────────────┘
  │     跑 RAG 流水线,返回答案
  │
  └── 响应发出后,后台任务写 chat_interactions
```

**要注意的是 ②③④ 和限流那一段的先后关系** —— 鉴权跑在限流之前,所以限流读便签的时候,
便签一定已经写好了。这个顺序是整个方案成立的前提,[基础知识四](#四requeststate交给不是路由函数的代码粘合二--三)
会讲为什么它成立。

后面每一节都可以挂到这张图上:[一](#一依赖把进门前的检查抽出来)和
[二](#二依赖不只把关它还能交东西出来)讲「FastAPI 解析依赖」那一段是什么,
[三](#三限流的-key每人的人怎么算)讲限流那一段里的 key 是什么,
[四](#四requeststate交给不是路由函数的代码粘合二--三)讲 ③ 那个便签为什么必须存在。

## 基础知识

四个概念。前两个是「请求怎么到达我的代码」,第三个是「限流怎么数数」,第四个把前两者
粘起来。

### 一、依赖:把「进门前的检查」抽出来

写一个接口,最朴素的写法是把所有检查都堆在函数体里:

```python
def chat(payload):
    if 请求头里的钥匙 != 正确的钥匙:
        return 401
    if 这个人这分钟问太多次了:
        return 429
    ...真正干活...
```

每加一个接口就要抄一遍这段,而且抄漏一行不会有任何提示。

FastAPI 的办法是把这些检查抽成独立函数,在签名里声明「跑我之前先跑它」:

```python
def chat(payload, _=Depends(require_caller)):
```

这就是**依赖(dependency)**。FastAPI 会在调用 `chat` 之前先执行它;它要是抛异常,
`chat` 压根不会被调用。

**取舍:为什么不用装饰器或中间件?** 中间件对所有路由生效,想排除某几条就得在里面写
路径判断,很快变成一团 if。依赖是**按路由声明**的——哪条路由要,就写在哪条路由的签名
里,看签名就知道这个接口需要什么。代价是它和框架绑得更紧。

### 二、依赖不只把关,它还能交东西出来

上一节的例子里,依赖只起了「拦住」的作用。但依赖是可以**返回值**的,返回的东西会作为
参数传进路由函数。

这个项目里就有现成的例子:

```python
orchestrator: Annotated[RAGOrchestrator, Depends(get_rag_orchestrator)]
```

这个依赖负责把 RAG 流水线取出来(顺便把启动失败转成一个像样的 503),然后**把流水线本
身递给** `chat` 用。

对照之下,改动前的鉴权依赖返回的是 `None`:

```python
_: Annotated[None, Depends(require_internal_api_key)]   # 改动前
caller: Annotated[Principal, Depends(require_caller)]   # 改动后
```

**同一个机制,一个用了、一个没用。** 这条改动的全部内容,就是让鉴权也把它知道的东西交
出来。

### 三、限流的 key:「每人」的「人」怎么算

限流是「每人每分钟最多 10 次」。要实现它,先得回答一个不那么显然的问题:**「每人」的
「人」按什么算?**

做法是给每个请求算出一个字符串,叫 **key**,然后按这个字符串分桶数数:

```
key = "1.2.3.4"   →  这个桶这分钟用了 7 次,还剩 3 次
key = "5.6.7.8"   →  另一个桶,跟上面互不影响
```

算这个 key 的函数叫 **key_func**。改动前用的是 slowapi 自带的
`get_remote_address`,也就是「按客户端 IP 算」。

这个项目上有两层限流,各自的 key 不同:

| 层 | key | 效果 |
|---|---|---|
| per-IP | 客户端地址 | 每个地址一个桶 |
| 全站 | 常量 `"global"` | 所有请求共用一个桶,封顶当天总花费 |

全站那一层的 key 是个**常量**——正因为常量,所有人才会落进同一个桶,换 IP 也绕不开
(设计依据见 [ROADMAP_platform.md](../../roadmap/ROADMAP_platform.md) 19.4)。

### 四、`request.state`:交给不是路由函数的代码(粘合:二 × 三)

现在把[二](#二依赖不只把关它还能交东西出来)和[三](#三限流的-key每人的人怎么算)接起来,
会撞到一个障碍。

依赖的返回值**只到得了路由函数**。而限流不是路由函数——它是包在路由函数外面的一层装饰
器,FastAPI 解析出来的那些参数它一个都够不着:

```
FastAPI 解析依赖  ──►  拿到 Principal  ──►  交给 chat()    ✅
                                        └──►  限流装饰器    ❌ 够不着
```

**`request.state` 是绕过这个障碍的通道。** 它是 Starlette 在每个请求对象上挂的一块便签
板:任何拿得到 `request` 的代码都能往上写、往上读;它跟着请求生灭,请求一结束就没了,
不会串到别的请求上。

而限流虽然够不着依赖的返回值,**它是拿得到 `request` 的**。于是:

```
require_caller:      request.state.principal = principal   ← 写便签
chat_rate_limit_key: getattr(request.state, "principal")   ← 读便签
```

**这条路走得通的前提是「鉴权一定先跑」。** 这一点查过 slowapi 的源码确认:它的 wrapper
是被 FastAPI **带着已经解析好的依赖参数**调用的,进到 wrapper 里面之后才做限流检查 ——
也就是[全局图](#先看全局一个-v1chat-请求经过了什么)里那个顺序:

```
FastAPI 解析依赖(require_caller 在这儿跑,写便签)
   └─► slowapi wrapper 做限流检查(在这儿读)
         └─► 路由函数体
```

**取舍:为什么不用「上下文变量」(contextvar)?** Python 的 `contextvars` 也能跨调用栈
传值,而且不用把东西挂在请求对象上。但它是隐式的——读的人看不出值是谁放的,测试里也更
难布置。`request.state` 是 Starlette 给这件事的既定答案,读写两端都显式带着 `request`,
代价只是多一个参数。

## 实现步骤

四步,每一步都能独立跑通、独立回滚。

### Step 1:鉴权产出一个 Principal

> Prerequisite basics: [一](#一依赖把进门前的检查抽出来)、[二](#二依赖不只把关它还能交东西出来)

新增一个小类([deps.py:21](../../../app/api/deps.py#L21)),装三个字段:调用方的类别、
用户 id、限流该按什么算。鉴权函数改名
[`require_caller`](../../../app/api/deps.py#L39),**验证逻辑一个字不动**,只是最后
`return` 一个它而不是 `None`。两条路由的 `_` 换成 `caller`。

**本步不碰限流** —— 限流键算出来放着,没人读。这样这一步的 diff 是纯粹的:出问题只可能
出在鉴权。

三个设计选择:

**`frozen=True`(创建后不可改)。** `Principal` 记的是「这次请求的调用方是谁」,是一个
已经发生的事实,下游任何代码都不该有能力改写它。冻起来之后,这类 bug 从「靠自觉」变成
「不可能」。

**限流键从一开始就带 `ip:` 前缀。** v1 只有地址一种来源,前缀看着纯属多余。但 v2 会有
`user:<id>` —— 不带前缀的话,一个 id 恰好是 `10.0.0.5` 的用户会和**真的来自那个地址**
的流量共用一个桶。这种 bug 不报错,只表现为偶尔有人被莫名限流,极难发现。**现在加成本
是零,以后加要迁移所有已存在的计数器。**

**保留一个只有单一取值的「类别」字段。** 它现在恒等于同一个值,存它没有任何用处。留着
是因为 v2 的分叉点在这儿:有了它,v2 的改动是「加一个分支」;没有它,v2 的改动是「改结
构」,要动的地方多得多。

### Step 2:限流去读它

> Prerequisite basics: [三](#三限流的-key每人的人怎么算)、[四](#四requeststate交给不是路由函数的代码粘合二--三)

`require_caller` 多做一件事:把 Principal 写进
[`request.state`](../../../app/api/deps.py#L76)。新增
[`chat_rate_limit_key`](../../../app/core/rate_limit.py#L35) 去读它,并在
[`/v1/chat` 的装饰器](../../../app/main.py#L258)上显式传这个 key_func。

**行为没有变化**:限流键在整个 v1 里都是 `ip:<地址>`,跟原来 limiter 默认算出来的是同一
个桶。

**那个「读不到就回退到地址」的兜底不能省。** 有两种情况便签是空的:鉴权失败(其实这时
根本到不了限流器),以及**将来某条路由挂了限流却忘了挂鉴权**。第二种是真会发生的。直接
读便签会抛 `AttributeError`,而且是在 slowapi 的 wrapper 内部抛——用户看到的是 500,日志
里是一条跟限流毫不相干的报错。回退让它**降级而不是崩掉**。

**取舍:为什么按路由传 key_func,而不是改全局默认?** 改
[`Limiter` 的默认 key_func](../../../app/core/rate_limit.py#L17) 会对所有路由生效,而这
次只想改 `/v1/chat`。按路由传也是这个仓库的既有做法——全站那一层就是这么挂的。

### Step 3:修一句被这次改动弄错的注释

> Prerequisite basics: [三](#三限流的-key每人的人怎么算)

[`global_rate_limit_key`](../../../app/core/rate_limit.py#L54) 的注释原本写着:slowapi
调用「路由级」的 key_func 时不传参数,不像 limiter 级的默认那样会收到请求。

**这个归因是错的。** 真正的判据不是路由级还是 limiter 级,而是**函数签名里有没有一个叫
`request` 的参数**(见[下一节](#两个陷阱))。

不改的话,Step 2 新加的 key_func 就是一个「路由级、而且确实收到了请求」的反例,紧挨着这
句注释——代码库里会留下一句直接否定隔壁函数的话。

### Step 4:证明接线真的通了

> Prerequisite basics: [四](#四requeststate交给不是路由函数的代码粘合二--三)

见[测试策略](#测试策略)——这一步单独拿出来,是因为它要解决一个不显然的问题:**这条链路
在 v1 里天然无法从行为上观察。**

## 两个陷阱

**一、key_func 的参数必须叫 `request`,不能叫别的。**

slowapi 是这么决定要不要传请求进去的:

```python
if "request" in inspect.signature(lim.key_func).parameters.keys():
    limit_key = lim.key_func(request)
else:
    limit_key = lim.key_func()
```

**它 inspect 的是参数名。** 把参数改名叫 `req`,这个函数就会被无参调用,当场 `TypeError`
—— 而且是**每个请求都炸,不是导入时炸**,静态检查一点忙都帮不上。

这跟路由函数里那个 `request: Request` 是同一类坑(那里也有一句
`# required by slowapi (looked up by this exact name)`)。新函数的 docstring 里写了同样
的警告。

**二、两个限流装饰器的顺序不能动。**

[main.py](../../../app/main.py#L257) 上全站层在外、per-IP 层在内。slowapi 会**先扣计数再
判断**,并且从最靠近函数的那个装饰器开始算 —— 所以 per-IP 的 429 会在全站计数器被扣之前
就中断请求。

顺序反过来,一个刷接口的 IP 就能用**被拒绝的请求**烧光全站当天的预算。

这次只换了 per-IP 那一层的 key_func,**顺序一个字没动**。有一条测试专门盯着这件事:
[`test_per_ip_429s_do_not_burn_the_global_budget`](../../../tests/unit/test_api_middleware.py#L318)。

## 测试策略

**主要标尺是「原有测试不用改」。** 这是纯重构最硬的验收:哪个测试需要跟着改,就说明行为
被改了。改动前基线 254 passed,改完 **257 passed**。

原有测试确实动了 **10 行**,但全部是同一种机械替换 —— 3 个测试文件里 `import` 的函数名和
`dependency_overrides` 的键跟着改名走。**没有任何断言或 setup 逻辑变动。**

### 一个不显然的问题:这条链路在 v1 里观察不到

新增的三条测试里,有一条是专门对付这个的。

限流键在整个 v1 里是 `ip:<地址>` —— **而这恰好和「读不到便签、回退到地址」产出的结果一模
一样。** 也就是说,从 HTTP 层面看,「限流读了 Principal」和「限流压根没读、走了回退」是
完全无法区分的两件事。

后果很实际:把 `chat_rate_limit_key` 的函数体整个换成回退逻辑,**其余 256 条测试照样全
绿**。这条新链路等于没有被测到。

**绕开的办法是种一个故意不长得像地址的键**,然后从两个不同的客户端地址各打一次请求:

- 限流读了 Principal → 两个请求同一个桶 → 第二个 **429**
- 限流没读、按地址算 → 各自一个桶 → 第二个 **200**

「落进同一个桶」这件事只有读了 Principal 才可能发生。这就是
[`test_chat_rate_limit_keys_on_the_principal_not_the_address`](../../../tests/unit/test_api_middleware.py#L280)。

### 这条哨兵测试本身也验证过

一条声称能抓问题的测试,如果没见它红过,它的价值是未知的。所以把
`chat_rate_limit_key` 的函数体临时换成永远走回退,跑全套:

```
FAILED test_chat_rate_limit_keys_on_the_principal_not_the_address
FAILED test_chat_key_uses_the_principal_when_one_is_present
2 failed, 255 passed
```

**正好红这两条,其余 255 条照常绿。** 这同时证明了两件事:哨兵有效,以及它出现之前那个
盲区是真实存在的。随后把文件还原,257 全绿。

另外两条新测试直接调
[`chat_rate_limit_key`](../../../tests/unit/test_rate_limit.py#L42) 本身:有便签时用便签
的值,没便签时回退到地址且不抛异常。

**未覆盖:** integration 测试需要真的 Postgres,本地没跑,由 CI 承担。

## 已知取舍与未完成

**现在就存在、但还没有意义的东西:**

| | 说明 |
|---|---|
| 类别字段只有一个取值 | v2 分叉点的占位,见 [Step 1](#step-1鉴权产出一个-principal) |
| 用户 id 恒为空 | v1 没有用户体系 |
| 限流键恒为 `ip:` | 同上;前缀是为 v2 的 `user:` 预留的命名空间 |

**这次没有改的既有行为:**

鉴权失败的请求**不计入限流**。因为鉴权跑在限流之前,一个带错误 key 的请求在到达限流器之
前就已经 401 了。这是既有的已知取舍,不在本次范围内 —— 想改属于「按用户限流」那一项,已
