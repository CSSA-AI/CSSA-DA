## 背景

现在改表结构是没有风险的,因为**现在没有生产环境**。本地是 `docker compose`:停掉、
改完、一起起来。只有一份代码在跑,不存在中间状态,想怎么改都行。

上了 ECS 之后这个前提消失。届时会同时出现两件本地没有的事:一是**回滚**(重新部署上
一个镜像),二是**滚动更新**(新旧 task 并存几分钟)。这两件事都会制造出一个本地从未
出现过的状态:**旧代码跑在新表结构上**。

规则本身在 [ROADMAP_platform.md](../../roadmap/ROADMAP_platform.md) 第 11.1 项里已经
写了一段时间了,而且被遵守过 —— `chat_interactions` 建表那个 migration
([20260824_0005](../../../migrations/versions/20260824_0005_create_chat_interactions.py))
的 docstring 里主动引用了它。**但那是因为写的人恰好读过 roadmap。**

所以这次要解决的不是「规则不存在」,是「规则不在会被读到的地方」。目标:让一个第一
次给这个项目写 migration 的人,**在动手那一刻**就被问到这个问题。

顺着这个目标往下做,发现原来那份规则本身也有三处需要修 —— 记在
[已知取舍与未完成](#已知取舍与未完成)之前的正文里。

## 先看全局:一次部署里,代码和表结构各自怎么走

整份文档的所有结论都从这张图里来:**代码可以来回切,表结构只能往前走。**

```
时间 ────────────────────────────────────────────────────►

代码      部署0 ────► 部署1 ────► 部署2
(镜像)                  ▲            │
                        └─── 回滚 ───┘        可以来回,秒级

表结构    没这列 ────► 可空 ────► NOT NULL ────► NOT NULL ...
(数据库)                                ▲
                                   回滚后停在这,不会退
```

一次部署内部的顺序是这样(关卡部分见
[ROADMAP_platform.md](../../roadmap/ROADMAP_platform.md) 第 11 项,尚未实现):

```
① 构建镜像并推到 ECR
      │
② 跑一个一次性的 migration task ──── 失败 → 部署中止,服务不受影响
      │                                     ← 这一步之后表结构已经是「新」的
      │
③ ECS 开始滚动替换 task
      │     task-1 新   task-2 旧   task-3 旧   ┐
      │     task-1 新   task-2 新   task-3 旧   ├─ 这几分钟里
      │     task-1 新   task-2 新   task-3 新   ┘  新旧代码同时跑在新表结构上
      │
④ 全部替换完
```

**②③ 之间那个窗口是本文的全部动机。** 它不是异常路径 —— 每一次正常部署都会经过它,
出不出事都一样。而回滚只是同一件事的另一种触发方式:回滚把 ③ 倒过来放,表结构仍然
停在 ② 之后的状态。

后面每一节都可以挂到这张图上:[基础知识一](#一一次部署实际发生了什么)讲 ①→④ 各步
到底动了什么,[二](#二回滚只换镜像数据库只能往前)讲那个 ▲ 为什么不会退,
[三](#三expandcontract约束是追认不是开路)讲怎么让 ② 永远安全,
[五](#五n-1这套保证的边界粘合二--三)讲这个保证到哪儿为止。

## 基础知识

四个概念 + 一个粘合。前三个是「为什么需要规则」,第四个是「规则不管的那部分」,第五
个把前面串起来并划出边界。

### 一、一次部署实际发生了什么

先说一个大多数人第一次都会想错的地方:**「部署」不是一个原子操作**。

朴素的想法是:我把新代码和新表结构一起推上去,某一瞬间系统从旧状态切到新状态。本地
`docker compose down && up` 确实就是这样 —— 停服,改完,起来。中间没人在看。

生产环境不能停服,于是这个瞬间被拉长成了一段过程,而且**代码和表结构是分两步走的**:
migration 先跑(它必须先跑,否则新代码上线时要读的列还不存在),task 后换。

这就产生了一个顺序上的事实:

> **表结构永远先于代码变新。**

这个事实本身没问题 —— 有问题的是它意味着「新表结构 + 旧代码」这个组合一定会出现,
而且不止一次:滚动更新期间出现一次,任何一次回滚又会让它出现。

### 二、回滚只换镜像,数据库只能往前

「回滚」这个词有很强的误导性,它听起来像是「回到昨天的状态」。

实际上回滚只做一件事:**把容器镜像换回上一个版本**。它不碰数据库。那句已经执行过的
`ALTER TABLE` 就留在那儿了,没有任何东西会去撤销它。

为什么不能让它也撤销?因为**数据库的变更不是可逆的**。代码是一堆文件,存着每个版本,
切过去切回来都行;数据库只有一个「当前状态」,一张表现在长什么样就是什么样。你可以
再执行一次 migration 把列加回来,但**那一列里原来的数据已经没了**。

这里有一个直接的推论,而且是读者最容易自己推错的一步:

> Alembic 给每个 migration 都生成了 `downgrade()`,**它不是退路**。
> `downgrade()` 能把删掉的列重新建出来,但建出来的是一列空值。

正确的姿势是**往前滚**:某个 migration 做错了,就再发一个改正它,而不是试图把表结构
倒回去。「回到昨天的表结构」这个操作不存在。

### 三、expand/contract:约束是追认,不是开路

有了前两节,规则就只剩一句话:

> **每个 migration 执行之后,上一版代码必须仍能正常工作。**

问题是:那我还怎么加 NOT NULL 约束?旧代码根本不知道有这一列,它不会填。

答案是**把一次危险的改动拆成两次安全的改动**。这个模式有名字,叫
**expand/contract**(也叫 parallel change):先「扩张」出一个新旧都能接受的中间状态,
等所有人都迁过去了,再「收缩」掉旧的那部分。

拿加 NOT NULL 举例,关键在于**代码的改动和约束的改动不放在同一次部署里**:

```
部署 1   加可空列  +  代码开始填它
         └─ 旧代码不填 → NULL → 表允许 → 安全

  (中间:等滚完,回填历史行)

部署 2   加 NOT NULL 约束
         └─ 退回部署 1 的代码 → 它本来就在填 → 安全
```

**顺序不能反,而且反过来的后果是立刻的:** 先上约束再改代码,那一刻所有在跑的代码都
不填这一列,当场全挂。

这条顺序可以概括成一句话,它是整个模式里最值得记住的部分:

> **约束是来「追认」一个已经成立的事实,不是来「制造」这个事实的。**

数据库层面的约束只应该在「所有写入方都已经满足它」之后才加上去。它的作用是把一个既
成事实钉死,防止将来退化 —— 而不是用来强迫现状改变。

### 四、锁:一根本文不覆盖的轴

前面三节的判据全都是**逻辑兼容性**:旧代码认不认识这个列、会不会因为约束而写失败。

还有第二根完全独立的轴:**这个 migration 会把表锁多久。**

一个逻辑上完全无害的操作,操作上可能是一次故障。最清楚的例子就是「加索引」:

```
CREATE INDEX ...      -- 旧代码根本不认识索引,逻辑上百分之百安全
                      -- 但建索引期间,这张表写不进去
```

在大表上这就是一次写入停摆。躲开它的办法是 `CREATE INDEX CONCURRENTLY`,但它有个
限制:**不能在事务里跑**,而 [migrations/env.py](../../../migrations/env.py) 把每个
migration 都包在一个事务里。也就是说**当前的代码结构写不出 CONCURRENTLY**,真要用得
先改那里。

同类的还有两个:直接 `SET NOT NULL` 要全表扫描并拿排他锁(PG 12+ 可以先加一个已验证
的 `CHECK` 约束绕过扫描);以及**锁排队** —— migration 在等锁时,后面所有查询会排在
它后面,连读都排,一个「只是在等待」的 migration 能把整个服务拖死,解法是
`lock_timeout` + 重试。

**为什么本次不做这些:** 当前 `knowledge_base` 是 2312 行,`chat_interactions` 在 v1
内测(几十人)下也就几千行。这个量级上,上面每一个操作都是毫秒级,全部不咬人。

把整套锁的防护现在就搭起来是过度工程。**但「不知道有这根轴」和「知道有、且知道它现在
不咬人」是两回事** —— 所以它被写进了 CONTRIBUTING,连同一个明确的重估门槛:**任何一张
表到十万行量级时回来看。**

### 五、N-1:这套保证的边界(粘合:二 × 三)

把[二](#二回滚只换镜像数据库只能往前)和[三](#三expandcontract约束是追认不是开路)
合起来看,就能看出这套东西到底承诺了什么 —— 以及没承诺什么。

规则的原文是「**上一版**代码必须仍能工作」。**上一版,不是上上版。** 这个保证在业界
叫 **N-1 兼容**。

用[全局图](#先看全局一次部署里代码和表结构各自怎么走)里那三个版本来看就很清楚:

| 回滚到 | 表结构 | 那一版代码填 user_id 吗 | 结果 |
|---|---|---|---|
| 部署 1 | NOT NULL(不会退) | 填 —— 部署 1 就开始填了 | ✅ |
| 部署 0 | NOT NULL(不会退) | 不填 —— 它压根不知道有这列 | ❌ 每次写入都炸 |

**退一版安全,退两版不安全。** 这不是漏洞,是这个模式公认的范围。实践上够用,因为回
滚基本都是「刚上的这版有问题,退回上一版」;真要退两版,得手工处理(比如临时把约束
去掉)。

还有一处边界值得单独说:规则里的「上一版代码」指的是**所有会写这张表的东西**,不只是
API。哪天有个离线脚本或 pipeline 也往 `chat_interactions` 写,而它没跟着改,那它就是
一个永远停在「部署 0」的写入方 —— 约束一上它立刻炸,跟回不回滚没关系。

现在 `chat_interactions` 只有 API 的 BackgroundTasks 一个写入方,所以暂时不是问题。
**但表一旦有第二个写入方,这条规则的适用范围要跟着扩。**

## 实现步骤

三步,全是文档和模板,没有运行时代码改动。

### Step 1:规则搬进 CONTRIBUTING

> Prerequisite basics: [二](#二回滚只换镜像数据库只能往前)、[三](#三expandcontract约束是追认不是开路)、[四](#四锁一根本文不覆盖的轴)

[CONTRIBUTING.md](../../../CONTRIBUTING.md#database-migrations) 新增
`## Database migrations` 一节,内容是**可直接照做的那部分**:规则本身、安全 / 危险两
类改动的清单、两步走每一步做什么、`downgrade()` 的告诫、锁这根轴的说明和重估门槛。

**为什么是 CONTRIBUTING 而不是继续放 roadmap:** 读者不同。roadmap 是给规划的人看的,
一个刚接手、准备写第一个 migration 的人没有理由去读它;CONTRIBUTING 是这个仓库唯一
一份「动手之前先看这个」的文档。

### Step 2:把问题前移到 alembic 模板

> Prerequisite basics: [三](#三expandcontract约束是追认不是开路)

[migrations/script.py.mako](../../../migrations/script.py.mako) 是 `alembic revision`
生成新 migration 文件时用的模板。在它的 docstring 里预置了那个问题,于是**每个新生成
的 migration 文件一打开就带着它**:

```
Backward compatibility (CONTRIBUTING.md, "Database migrations"): after this
migration runs, the previous version of the code must still work. Say why it
does — or which of the two deploys this one is.
```

**为什么这里比 PR 模板有效:** 时机。PR 模板的勾是在写完之后、提交时才看到的,那时
改动已经成型,而且勾这种东西人会随手打。写在 migration 文件里,是在**动手那一刻**,
成本最低的时候。

**这个位置是有证据的,不是拍脑袋。** PR #84 的作者在没有任何模板提示的情况下,自发
在 migration 的 docstring 里写了这段:

> Everything else the table will eventually carry — feedback, user_id,
> session_id, token_usage, refused — is a nullable ADD COLUMN later, which
> satisfies the hard rule in ROADMAP_platform.md 11.1

也就是说,**这件事本来就想写在这儿**,模板只是把它变成默认动作。

**取舍:** 模板文字会出现在每一个生成的文件里,作者应当把它替换成真实回答。有人原样
留着不删是可能的 —— 这个代价接受,因为它至少保证了问题被看到一次。

### Step 3:roadmap 只留「为什么」

> Prerequisite basics: [一](#一一次部署实际发生了什么)

[ROADMAP_platform.md](../../roadmap/ROADMAP_platform.md) 第 11.1 项保留论证部分(回滚
的不对称、滚动部署也会撞、expand/contract 这个名字、N-1 的边界、`chat_interactions`
那个例子),**两张表移走,只留一个指向 CONTRIBUTING 的指针。**

**为什么不两边都留一份:** 两份会飘。规则改一次而只改了其中一份,读者就会拿到两个互相
矛盾的答案,那比只有一份差的文档更糟。一份操作清单 + 一份论证,各有各的读者,不重叠。

## 走一遍完整的例子:给 chat_interactions 加 user_id NOT NULL

把前面所有东西串一遍。这个例子不是假想的 —— `chat_interactions` 建表时就已经在
docstring 里预告了 `user_id` 是「将来的可空加列」。

现在的表是六列(`request_id` / `created_at` / `query` / `answer` / `retrieved` /
`config`),见
[20260824_0005](../../../migrations/versions/20260824_0005_create_chat_interactions.py)。
目标:加一个非空的 `user_id`。

**如果一次做完 ——**

```sql
ALTER TABLE chat_interactions ADD COLUMN user_id TEXT NOT NULL;
```

两个问题。第一,表里已经有行了,这句会被 Postgres 直接拒绝(那些行拿什么填?)。第二,
就算表恰好是空的、执行成功了,一旦回滚,旧代码 INSERT 不带 `user_id`,**每一次写入都
炸**,而你已经退到上一版、没有更早的版本可退了。

**分两步 ——**

| | migration | 代码 | 此刻回滚会怎样 |
|---|---|---|---|
| 部署 1 | 加 `user_id TEXT`(**可空**) | 开始在 INSERT 里填 `user_id` | 旧代码不填 → NULL → 表允许 → ✅ |
| *(中间)* | 无 | 无 | 等滚完,回填历史行 |
| 部署 2 | `SET NOT NULL` | 不变 | 退回部署 1 的代码,它本来就在填 → ✅ |

中间那一段有两个实操要点,都容易做错:

1. **回填必须等部署 1 完全滚完。** 滚动更新期间还有 task 在跑旧代码,它们会继续插
   NULL 进来 —— 回填早了等于白填。
2. **上约束前必须确认没有 NULL 了:**

   ```sql
   SELECT count(*) FROM chat_interactions WHERE user_id IS NULL;
   ```

   得是 0。**不是 0 的话,部署 2 的 migration 会失败 —— 而这是正确的结果。** 它在服务
   被弄坏之前就把部署拦住了,这正是[全局图](#先看全局一次部署里代码和表结构各自怎么走)
   里第 ② 步作为关卡的意义。

**什么时候不值得这么干:** 如果这一列根本没有合理的回填值(历史数据里真的没有用户身
份,填 `'unknown'` 是在造假数据),那就别加 NOT NULL —— 让它保持可空,把「必须有值」
交给应用层校验。数据库层的约束更硬,但不是所有情况都值得为它多发一次版加造一批假数据。

## 为什么是文档而不是 CI 检查

规则目前靠 review 执行,没有任何自动检查。

**先说一个不成立的理由,因为它很容易被当成成立的:** 「自动判断一个 migration 向不向后
兼容太难」—— 这句话本身对(要解析 Alembic 的操作,再对照上一版代码对这些列的读写),
但它反驳的是一个**没有人在用的设计**。

真实世界的做法要笨得多:**一份危险操作黑名单**。不试图证明兼容,只拦几个词 ——
`drop_column`、`alter_column`、`drop_table`、`drop_constraint` —— 命中就让 CI 失败,
除非 migration 里写了显式的豁免理由。Rails 的 `strong_migrations`、Postgres DDL 的
`squawk` 都是这个路子。放到这个仓库大概十行以内。

**那为什么现在还不做:** 现在没有生产数据库要保护。所有 migration 都跑在可以随手删掉
重建的容器上,一个拦截器现在唯一的作用是给开发加摩擦。

所以这里的立场是**「顺序问题」而不是「否决」**:文档 + review 是第一步,黑名单检查是
明确的下一步,时机是有了 RDS 之后。这一点写进了 CONTRIBUTING,免得将来有人提这个提案
时被一句「我们讨论过了,不做」挡回去。

## 已知取舍与未完成

**这次没做,而且是有意的:**

**规则本身修掉的三处:**

1. 「加索引」原本被列为无条件安全 —— 逻辑上对,操作上它会阻塞写入。现在标注了,并说明
   了 `env.py` 的事务包裹让 `CONCURRENTLY` 当前写不出来。
2. 原本没有任何关于 `downgrade()` 的告诫。一个读到「回滚不会撤销 migration」的人很容
   易自己推出「那应该让它也撤销」,而那个结论更危险。
3. 「不做 CI」的理由原本是在反驳一个没人用的设计。改成了顺序问题。

**这条规则的执行强度,要诚实地说:** 它现在完全靠人。模板会让问题被看到,但不会阻止
任何人无视它。**在有生产数据库、也有自动检查之前,这份文档买到的是「知道该怎么做」,
不是「不可能做错」。**

**依赖关系:** 本文描述的规则独立生效,但它保护的那个场景(部署 → 回滚)要等
[ROADMAP_platform.md](../../roadmap/ROADMAP_platform.md) 第 11 项的 migration 关卡和
ECS 服务存在之后才真正出现。规则先立、关卡后建,是有意的顺序 —— 第一个有风险的
migration 可能出现在关卡就位之前。
