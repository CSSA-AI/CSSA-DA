## 背景

改这件事之前,RAG 流水线是**懒构建**的:PG 连接池、reranker、OpenAI client 都挂在一个
带 `lru_cache` 的构建函数上,直到第一个 `/chat` 请求到来才真正创建。

在本地这只是"第一次慢一点"。在 ECS 上它变成一个真实的用户问题:新 task 通过 `/ready`
之后 ALB 立刻开始导流,**第一个真实用户替所有人付这笔初始化成本**,而 `/ready` 此时
已经宣称自己 ready 了。也就是说,就绪信号在撒谎。

目标:把这笔成本移到启动期,并让 `/ready` 的含义真正等于「能以全速服务」。

顺着这个目标往下做,发现真正要解决的不止一件事 —— 「什么算准备好」本身需要被重新
定义。这份文档记录的就是这个定义,以及它带来的四个约束。

## 先看全局:一次容器启动的旅程

```
docker run
  │
  ├── uvicorn 进程启动,导入 app.main
  │
  ├── lifespan 的「启动段」 ─────────────────────────────────┐
  │     ① 校验限流配置        失败 → 直接崩掉,容器不启动      │
  │     ② 加载两个模型,并各跑一次真实推理(预热)             │
  │     ③ 构建 orchestrator:PG 连接池 + reranker + OpenAI    │
  │                                                          │
  │     ②③ 失败只记日志,不中断启动 ────────────────────────┘
  │
  ├── yield  ◄────── uvicorn 从这一刻才开始接受连接
  │
  ├── 服务中
  │     /health   → 永远 200(只要进程活着)
  │     /ready    → 200 仅当:DB 可连 + 表里有数据 + 两个模型 ready
  │     /v1/chat  → 直接用已经建好的 orchestrator,不再懒构建
  │
  └── SIGTERM → 走到 yield 之后 → 关闭连接池 → 退出
```

三个要点,后面每一节都挂在这张图上:

1. **`yield` 是一道闸门。** 它之前的代码不跑完,uvicorn 一个连接都不接。所以放在
   `yield` 之前的任何东西,都直接决定"多久之后这个容器能被访问"。
2. **`②③` 的失败是被容忍的。** 它们只记日志,不中断启动 —— 因为容器活着但降级,
   比容器起不来更好办。这个选择的完整理由见[基础二](#二活着-vs-能接活两个探针为什么不能合并)。
3. **两个探针答的不是同一个问题。** `/health` 回答"进程还在吗",`/ready` 回答"能接活
   吗"。图里它们并列,但它们的失败对应完全不同的处置动作。

## 基础知识

### 一、lifespan:接第一个请求之前的那段时间

> **这一簇讲什么**:Web 应用怎么表达"启动时做一次、关闭时收拾一次",以及为什么这个
> 位置对我们如此关键。

**朴素做法:在模块顶层初始化。** 直接在文件顶部写 `orchestrator = build()`,导入即执行。
三个问题:导入这个模块的**任何人**都会触发它(包括跑单元测试的 pytest);失败了没有
地方处理,只能让导入炸掉;而且没有对称的"关闭时收拾"钩子,连接池永远不会被优雅关闭。

**ASGI 的解法是 lifespan 协议。** 服务器(uvicorn)在开始接受连接**之前**,先给应用
发一个 `lifespan.startup` 事件;在退出前发 `lifespan.shutdown`。FastAPI 把这两件事包成
一个异步上下文管理器:`yield` 之前是启动,之后是关闭。

关键性质,也是这份设计的地基:

> **`yield` 之前的代码不返回,uvicorn 就不会进入服务状态。**

这是双刃的。好的一面:放在这里的初始化,保证在第一个用户请求之前完成。坏的一面:
放在这里的任何**阻塞**,都是整个容器的不可用时间 —— 而且此时连 `/health` 都还没上线,
外界完全看不见你卡在哪。第四簇会回到这一点。

**取舍:同步做还是丢后台?** 我们选择在 `yield` 之前**同步**完成预加载,而不是
`asyncio.create_task` 丢到后台让 uvicorn 立刻开始服务。后台方案能让容器更快"可访问",
但代价是 `/ready` 的语义变模糊(存在一段"正在预热"的窗口),而且要引入并发状态管理。
既然健康检查的 `start-period` 有 60 秒预算(见[启动预算](#启动预算60-秒怎么花)),
换取一个简单、确定的启动顺序是划算的。

### 二、活着 vs 能接活:两个探针为什么不能合并

> **这一簇讲什么**:为什么容器编排系统坚持要两种健康检查,以及把它们合成一个会发生
> 什么。

**朴素做法:一个 `/health` 端点,把所有依赖都查一遍。** DB 连不上就返回 500,让编排
系统知道"我不健康"。

这个设计有一个致命的循环:编排系统对"不健康"的处置是**重启容器**。但 DB 挂了,重启
应用治不好 —— 于是所有实例开始轮流重启,日志被启动噪声淹没,而 DB 恢复之后你还得等
重启风暴平息。更糟的是,重启期间连"应用本身是好的"这个信息都丢失了。

**解法是把问题拆成两个,因为处置动作不同:**

| 探针 | 回答 | 失败时该做什么 | 谁在用 |
|---|---|---|---|
| **liveness** `/health` | 进程还活着吗? | **重启容器** —— 重启能治的问题 | Docker HEALTHCHECK / ECS 容器健康检查 |
| **readiness** `/ready` | 现在能接活吗? | **摘掉流量** —— 等它自己好 | ALB target group |

判断标准很简单:**这个故障重启能治吗?** 进程死锁了、内存爆了 —— 重启能治,归
liveness。DB 挂了、模型没加载好 —— 重启不能治,归 readiness。

这条区分解释了大图里 `②③` 为什么只记日志:**模型或 DB 出问题时,我们要的是一个活着
但降级的实例**(`/health` 200 + `/ready` 503),而不是一个起不来的容器。反过来,限流
配置写错了属于"配置根本不对",让它直接崩掉才对 —— 所以 `①` 刻意放在容错之外。

> ⚠️ 一个常见误解:「`/health` 能应答」不等于「服务可用」。preload 失败只记日志,启动
> 照常走到 `yield`,`/health` 照样 200。承载"可用"这个含义的是 `/ready`,不是 `/health`。

### 三、「加载完」不等于「能用」:惰性初始化

> **这一簇讲什么**:为什么把模型对象创建出来,并不代表首次推理会快 —— 这是整个冷惩罚
> 问题里最反直觉的一环。

**朴素预期:模型加载完 = 准备好了。** 权重读进内存了,对象也构造好了,推理应该就是纯
计算了吧?

不是。深度学习框架为了启动快,把大量工作推迟到**第一次真正前向传播**时才做:选择并
编译算子实现、分配内存 arena、tokenizer 第一次调用的初始化、线程池启动。这些都不发生
在构造函数里。

结果是:`preload_models()` 把两个模型都构造好了,状态也标成 `ready` 了,但**第一次真实
推理仍然要付一笔一次性开销**,而这笔开销落在第一个用户身上。

隔离测量(同一进程内,预热前 vs 预热后,embedding `encode` + reranker `predict` 的首次
调用惩罚):

| | 未预热 | 已预热 |
|---|---|---|
| run 1 | 570.4ms | 36.9ms |
| run 2 | 511.8ms | 34.9ms |
| run 3 | 116.4ms | 35.9ms |

**跨度和均值一样重要。** 未预热时惩罚在 116–570ms 之间摆动(5 倍),意味着单次幸运的
测量可能通过阈值,而线上照样翻车;预热之后是稳定的 ~36ms。把一个赌博变成常量,可能
比把均值降下来更有价值。

> 上表在 macOS 上测得。**绝对值不迁移到 Linux 容器**,只有"预热前 vs 预热后"的对比可
> 迁移。

这一簇还带出一个后果:如果"能推理"才算准备好,那么**一个能加载但推理失败的模型,必须
被判定为没准备好**。Step 3 处理这件事。

### 四、连接的三种结局(粘合:lifespan × 探针)

> **这一簇讲什么**:把前三簇连起来 —— 一个没有上界的网络操作放进 lifespan,会让"进程
> 活着"这件事本身都无法被观测。

**朴素预期:连不上的数据库会很快报错。** 本地开发时确实如此:Postgres 没起,
`psycopg2.connect` 立刻抛 `Connection refused`。

真实网络有三种结局,差别巨大:

| 对方状态 | 回什么 | 客户端等多久 |
|---|---|---|
| 主机在,端口没人听 | 立刻回 `RST` | **~0ms**,ECONNREFUSED |
| **主机在,包被静默丢弃** | **什么都不回** | 内核不断重发 SYN 直到放弃,Linux 约 **127 秒** |
| 主机不存在 | 视情况 | 通常也很快 |

第二种是**防火墙/安全组配错的典型症状** —— 规则写成 DROP 而不是 REJECT,包被静静吃掉。
而 libpq(psycopg2 的底层)**默认不设连接超时**,意思是"完全交给操作系统的 TCP 重传"。

把这个和第一簇合起来看,后果是链式的:

```
DB 主机丢包
  → 连接池构造卡住 ~127s(没有异常,只是不返回)
  → lifespan 的启动段不返回
  → uvicorn 不进入服务状态
  → /health 不可达
  → 容器健康检查的 60s start-period 到期 → 判定 unhealthy
  → 容器被杀 → 重启 → 再卡 127s → 无限重启循环
```

注意这里**第二簇建立的整个 liveness/readiness 分工被架空了**:一个本该"降级但存活"
的实例,变成了重启循环。而且 `try/except` 挡不住它 —— 问题不是抛了异常,是**根本没抛
异常,只是不返回**。

这就是为什么 Step 4 存在:超时不是可选的健壮性装饰,它是让前面三簇的设计能够成立的
前提。

## 实现步骤

### Step 1:orchestrator 移进 lifespan

> Prerequisite basics: [一](#一lifespan接第一个请求之前的那段时间)、[二](#二活着-vs-能接活两个探针为什么不能合并)

把 `lru_cache` 包着的流水线构建,从"第一个请求触发"改成"在 `yield` 之前主动调用一次"。
构建函数本身保持不变,只是提前被调用。

对外暴露一个公开的预热入口([deps.py](../../../app/api/deps.py)),而不是让
[main.py](../../../app/main.py) 跨模块去引用私有的构建函数 —— lifespan 需要的语义只是
"现在就把它建好",`lru_cache` 和缓存清理是 `deps` 的内部事务。

**一个免费得到的好处:`lru_cache` 不缓存异常。** 如果启动时构建失败,缓存是空的,于是
第一个真实请求会自动退回原来的懒加载路径重试一次。一次短暂的 DB 抖动不会把进程永久
变成废物。

**另一个:关闭路径现在真的会执行。** 改之前,如果一个请求都没来过,连接池根本没建,
关闭是空操作;现在连接池一定存在,`SIGTERM` 时的清理是真的在跑。

---

### Step 2:预热两个模型

> Prerequisite basics: [三](#三加载完不等于能用惰性初始化)

在 `preload_models()` 里,加载完每个模型之后立刻跑一次真实前向传播。

**预热调用必须和真实调用形状一致。** embedding 用 `encode([...], normalize_embeddings=True)`,
reranker 用 `predict([(query, doc)])` —— 和
[pg_retriever](../../../app/services/rag/retriever/pg_retriever.py) 与
[cross_encoder_reranker](../../../app/services/rag/reranker/cross_encoder_reranker.py)
实际调用的形状相同。形状不一致的话,预热的是一条第一个请求根本不会走的代码路径,等于
白热。

**位置选在 registry 而不是 lifespan。** 模型归 `ModelRegistry` 所有,预热是"加载"这件事
的一部分;放在这里,以后加载逻辑变化时 lifespan 不需要跟着改。

---

### Step 3:预热失败必须标记 failed

> Prerequisite basics: [二](#二活着-vs-能接活两个探针为什么不能合并)、[三](#三加载完不等于能用惰性初始化)

模型状态原本只在"加载"这一步被跟踪:加载成功标 `ready`,失败标 `failed`。预热跑在这个
跟踪之外,于是出现一个危险的组合:**加载成功(`ready`)但推理失败**。

这不是假想。reranker 上可以挂 LoRA adapter,而适配不兼容这类错误往往在加载时不报,要到
真正 `predict` 时才暴露。

后果:`/ready` 的判定直接看模型状态,状态说 `ready`,`/ready` 就回 200 —— 于是 ALB 把
流量导给一个**每个请求都注定失败**的实例。

改法是让预热失败也标 `failed`。

**取舍:这个失败是永久闩死的,没有自愈。** 模型对象此时已经被缓存,不会有任何后续调用
重新触发预热,所以这个实例的 `/ready` 会一直红下去。

考虑过"顺手清掉缓存让它下次重试",**结论是那样更糟**:重新加载走的是普通加载路径,成功
之后会把状态设回 `ready`,而那条路径里没有预热 —— 灯会在一个仍然跑不动的模型上变绿,
而且是先红后绿,更容易让人以为问题已经解决。

**宁可红死,不可假绿。** 对确定性故障(不兼容的 adapter)这是对的;对偶发故障(首次推理
OOM)会误伤,代价是这个容器不进流量、编排系统起个新的 —— 可以接受。

---

### Step 4:给连接池加 connect_timeout

> Prerequisite basics: [四](#四连接的三种结局粘合lifespan--探针)

给检索器的连接池设置连接超时,值放
[rag-config.yaml](../../../app/core/config/rag-config.yaml) 的 `pgvector` 块,跟着已有的
池大小配置走。

**取舍:为什么作为参数传,而不是拼进 DSN 字符串。** 两种写法 libpq 都认。但
`DATABASE_URL` 是环境变量 / Secrets 注入的,改字符串意味着改部署配置;作为参数传是代码
内的事,可以被单元测试断言,而且不依赖任何一个部署环境把它配对。

**值选 5 秒。** 它要同时满足两个方向:比 TCP 的 ~127s 短得多(否则没意义),又要足够宽松
不会误杀跨可用区的正常连接。

**这个超时对连接池开的每一条连接生效,不只是启动那一条。** 流量上来时池子会继续新建连接,
DB 在服务过程中变成黑洞的话,那条路径同样受保护 —— 这是"给连接加超时"比"把预热丢后台"
更根本的地方:后者只挪开了启动那一次。

---

### Step 5:模型失败时跳过 orchestrator 预热

> Prerequisite basics: [一](#一lifespan接第一个请求之前的那段时间)

检索器和 reranker 都从 registry 取模型,而**加载失败是不缓存的**。于是模型加载失败之后
再去构建 orchestrator,会把同一次失败的加载**完整重试一遍**,串行地发生在启动路径上 ——
而且注定还是建不出可用的流水线。

模型预加载失败时直接跳过 orchestrator 预热。

**诊断信息没有丢失**:DB 那一侧的状态由 `/ready` 独立汇报,不依赖启动时是否尝试过建池。

## 启动的失败矩阵

四种失败,三种不同的处置 —— 这张表是前面所有取舍的汇总:

| 失败 | 启动是否中断 | `/health` | `/ready` | 编排系统的动作 |
|---|---|---|---|---|
| 限流配置串写错 | **是,直接崩** | — | — | 容器起不来,部署失败 |
| 模型加载失败 | 否,记日志 | 200 | 503 | 摘流量;跳过 orchestrator 预热 |
| 模型预热失败 | 否,记日志 | 200 | 503(永久) | 摘流量,不重启 |
| DB 不可用 | 否,5s 内超时并记日志 | 200 | 503 | 摘流量,DB 恢复后自动回来 |

第一行和其余三行的区别值得记:**配置写错是"这个部署根本不对",应该让它响亮地失败**;
其余三种是"环境暂时不行",应该降级存活。

## 启动预算:60 秒怎么花

容器健康检查给了 60 秒的 `start-period`([Dockerfile.api](../../../Dockerfile.api)),
在这段时间内 `/health` 失败不计入重试。预算怎么花:

| 项 | 耗时 |
|---|---|
| 加载两个模型(本地磁盘,`MODEL_DIR` 烤进镜像) | 主要开销 |
| 预热两次前向传播 | 约 +2s |
| 建 PG 连接池 | 正常几十毫秒;最坏 5s(超时) |

实测冷启动到 `/health` 可用:本机裸 uvicorn 12.99 / 13.23 / 13.43 / 15.43 秒(四次);
另有一次容器内实测 16.461 秒。

> ⚠️ **这两组数字来自不同机器,从未对齐。** 写 ECS task 规格时不要直接引用其中任何一个,
> 需要在目标硬件上重测。

即便取最坏的一组,离 60 秒仍有充足余量。

## 测试策略

lifespan 的测试有一个和普通单元测试相反的性质,值得单独写下来:

> 普通单测里,**你没提到的东西不会被执行**;
> lifespan 测试里,**你没替换掉的东西一定会被执行**。

用上下文管理器形式的 `TestClient` 会触发真实的启动流程。于是一个只想测"orchestrator 构建
失败时 `/health` 仍然 200"的测试,如果没有替换模型加载,就会在 CI 上**真的下载并加载
约 600MB 的模型**(CI 环境没有配 `MODEL_DIR`,走的是远程下载路径),还会把模块级的
registry 单例留在 `ready` 状态污染后续用例,让结果依赖执行顺序。

原则:**每个测试只让它要测的那一件事是真的,其余全部换成替身。**

这条原则被严格执行之后,`tests/unit` 的总耗时从 15.09s 降到 3.28s —— 那两个测试原本吃掉
了整个套件近八成的时间。

其余几条:

- **替身要像真东西。** 曾经有测试用裸对象冒充模型,导致生产代码里被迫加了"这个对象有没有
  `encode` 方法"的判断来迁就它 —— 生产代码为测试替身而变形,而且那个判断对 mock 恒为真,
  让断言失去意义。替身应该具备真实类型该有的方法。
- **锁住状态机,而不是具体的失败方式。** "预热失败 → 状态变 failed"这条,测的是状态转移,
  不是 PEFT 具体怎么报错。
- 当前 `tests/unit` 共 **233 passed**。

## 已知取舍与未完成

**只覆盖了我们能控制的那一段。** 完整 `/chat` 的首次-稳态差里,还有一块来自首次 OpenAI
连接建立(TLS 握手等)。那不是我们能优化的部分,因此 v1 的相关验收标准已收窄到**检索 +
重排**;生成段作为观测项、不设阈值。见
[ROADMAP_versions](../../roadmap/ROADMAP_versions.md) v1 退出标准。

**超时只做了一半,而且只做了一处。** 目前只有"建立连接"有上界,"执行查询"完全没有 ——
连上之后卡在锁等待或慢扫描一样会挂住。而且只有检索器的连接池被覆盖,`/ready`、`/status`
和运维 CLI 各自开的连接仍然是裸的。追踪见 GitHub issue
[#87](https://github.com/CSSA-AI/CSSA-DA/issues/87)。

**测试的默认行为仍然不安全。** 现有 lifespan 测试都补齐了替身,但没有任何机制阻止下一个
人再犯同样的错。让默认安全需要一个 autouse 的测试夹具;目前只靠约定。
